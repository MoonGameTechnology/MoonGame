# Триаж находок безопасности

## Что здесь устроено и почему так

`.github/workflows/security.yml` гоняет на **каждый push в любую ветку** намеренно
разнородный набор сканеров (разные методы и поверхности, не клоны друг друга), все SARIF
безусловно льются в `Security → Code scanning` одной панелью (SEC-4), а `report`-джоба
собирает сводку в job summary + sticky-комментарий PR'а.

**Блокирующие** (их gate-шаг валит джобу при ЛЮБОМ ненулевом коде выхода сканера):
`semgrep`, `gitleaks`, `osv`, `trivy-fs`, `trivy-image`. Ненулевой выход — это и находка,
**и сбой самого скана**: сканер, который не отработал, ничего не сертифицирует
(fail-secure, OWASP A10 — инвариант #4 `CLAUDE.md`). Именно это однажды и поймало
молча падавшую сборку образа: `trivy-image` вообще не сканировал ничего, а пайплайн был
зелёным (запись триажа в `docs/security/pipeline.md`).

**Информационные** (`continue-on-error`, ещё без триажа): `codeql`, `trufflehog`,
`zizmor`, `scorecard`, `dast-zap`, `sbom` и джоба `check` (её блокирующий близнец — в
`ci.yml`). Их находки не валят билд, но разбирать их всё равно надо: ратчет едет только
вверх — сканер становится блокирующим после первого честного триажа, назад не откатывается.

Каждая скан-джоба пишет сентинел `status-<key>.json` с реальным кодом выхода, а
`.github/scripts/summarize-security.mjs` начинает отчёт с таблицы подтверждения сканов:
неподтверждённый сканер помечается «⚠️ НЕ подтверждён», а не тихим «0 находок». Если
видишь такую пометку — сначала чини скан, потом смотри находки.

## Как разобрать одну находку

1. **Открой сам код**, а не только текст алерта. Категория в панели (`semgrep`, `codeql`,
   `gitleaks`, `osv-scanner`, `trivy-fs`, `trivy-image`, `zizmor`, `scorecard`) говорит,
   какой движок сработал и на что он вообще способен.
2. **Протяни данные до истинного источника.** Вопрос всегда один: может ли этим
   управлять атакующий? Сканер сопоставил паттерн — он не знает, что `SESSION_COLS` это
   константа модуля, а не пользовательский ввод. Соответственно и обратное верно: если
   значение приходит из `action`-конверта, из query-строки или из `localStorage`, оно
   контролируемо, каким бы безобидным ни выглядел вызов.
3. **Вынеси честный вердикт:**
   - _true positive_ → чини код;
   - _false positive_ → подавляй с обоснованием (правила ниже) либо, для CodeQL,
     dismiss в UI;
   - _safe, но стоит укрепить_ → часто лучший исход: код не эксплуатируем сегодня, но
     после правки перестаёт зависеть от аргумента «здесь пока не бывает чужих данных».
     Прецедент SEC-9: DOM-XSS в `prototype/src/main.ts` погашен не подавлением, а
     `safeHexColor` — validating-guard, который taint-анализ CodeQL признаёт санитайзером.
4. **Не верь severity вслепую, но начинай с HIGH/CRITICAL** (`pipeline.md`): шум
   medium/low разбирается после, иначе триаж не закончится никогда.

## Чинить, а не подавлять

Предпочитай фикс, который **убирает сам паттерн**, подавлению — подавление это долг,
который кто-то будет перечитывать через полгода без твоего контекста. Примеры из
SEC-9: ReDoS `js/polynomial-redos` в `packages/server/src/authApi.ts` снят заменой
`replace(/\/+$/, '')` на линейную посимвольную обрезку + тест; это дешевле, чем вечно
объяснять, почему регулярка «на самом деле безопасна».

Правка — хирургическая (инвариант «surgical changes»): трогай ровно ту строку, что
породила алерт, и добавляй тест, фиксирующий новое поведение. Ремедиация без теста
регрессирует при первом же рефакторинге.

## Подавления: где какой файл — и чего НЕТ

Из файлов подавления в репозитории **существует только `.trivyignore`**.
`.semgrepignore`, `.gitleaks.toml`, `osv-scanner.toml` **сознательно не созданы**: пустой
файл подменил бы собственные дефолтные списки игнора сканеров и молча ослабил бы их.
Создание любого из них — отдельное осознанное решение с обоснованием в PR, а не
рутинный шаг триажа. Сначала спроси себя, нельзя ли починить код.

- **Semgrep** — инлайн-комментарий на строке находки:
  `// nosemgrep: <rule-id> -- причина`. Работает и снимает результат из SARIF (проверено
  на `no-sql-string-interpolation` в `packages/server/src/store/postgres.ts`).
  Оговорка из SEC-2: для AST-правил (`patterns:`) GitHub Code Scanning не всегда уважает
  inSource-suppression на new-alert чеке PR'а — там законный выход это `paths: exclude:`
  в самом правиле (`.semgrep/rules/no-innerhtml-assignment.yaml` — единственный такой
  случай, с объяснением прямо в правиле).
- **Trivy** — `.trivyignore`, по CVE-id. Смотри существующий файл как образец формата:
  группа CVE под комментарием с пакетом, версией, severity, **причиной** («нет фикса для
  trixie», «нет runtime-пути в distroless-образе») и **датой ревью**.
- **Gitleaks** — сначала считай секрет скомпрометированным и **ротируй** его; allowlist
  только для заведомо публичных значений и тестовых фикстур.
- **OSV** — сначала апдейт зависимости; игнор только с `[[IgnoredVulns]]` + сроком.

Правило поверх всех: **каждое подавление несёт причину и дату** (конвенция
`.trivyignore`). Подавление без обоснования — технический долг безопасности, и на ревью
оно читается как «сканер мешал».

## CodeQL: false positive гасится в UI

CodeQL-находку, которую нельзя убрать кодом без искажения нормального кода, **закрывают
в `Security → Code scanning` кнопкой «False positive»** с объяснением. Не подгоняй
здоровый код под ограничения анализатора. Живой прецедент: два оставшихся
`js/missing-rate-limiting` — подтверждённый FP, потому что кастомный
`slidingWindowIpLimiter` (`packages/server/src/rateLimit.ts`, используется в
`authApi.ts`/`avaApi.ts`) не моделируется CodeQL как rate-limiter. Лимит там реально есть.

## Локальная проверка перед пушем

Те же сканеры гоняются локально — рецепты в `docs/security/pipeline.md` (раздел
«Запуск»); в CI образы закреплены по `sha256`, локально можно по тегу. Кастомные
Semgrep-правила имеют юнит-тесты (`semgrep --test .semgrep/rules`) — CI гоняет их
**до** самого скана, чтобы сломанное правило падало раньше находок; если правишь правило,
правь и парный `.ts`-файл с маркерами `// ruleid:` / `// ok:`.

Перед коммитом — обычный гейт: `pnpm run check` (lint + typecheck + test + docs-check).

## Закрыть петлю: записать триаж

Триаж не считается сделанным, пока решение не зафиксировано там, где его найдут:

- **`docs/security/pipeline.md`** — «Запись триажа»: что проверено, чем, с каким
  результатом, что принято как риск. Правило репо — **reconcile, don't append**: старое
  утверждение, которое ты опроверг, переписывается, а не соседствует с новым.
- **`docs/backlog.md`, блок SEC** — если работа шла кирпичиком (`SEC-*`), обнови его
  статус и суть по факту (образец подробности — записи SEC-1, SEC-2, SEC-9).
- Документируй только проверенное по коду и прогонам, а не по памяти — это отдельное
  правило `CLAUDE.md`, и в security-доках цена ошибки выше обычного: неверная запись
  триажа даёт ложную уверенность.

Один кирпич ≈ один PR ≈ одна зона; ветка от `main`, `main` защищён — регламент в
`CONTRIBUTING.md`. Зонтичный контекст (модель угроз, тир-план, гейт «secure-enough to
launch») — `docs/security/security-master-plan.md`.
