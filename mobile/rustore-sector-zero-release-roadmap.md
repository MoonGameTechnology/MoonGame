# Sector Zero — дорожная карта релиза в RuStore

**Дата исследования:** 30 сентября 2026 года.  
**Статус:** предложенный план, не подтверждение готовности APK и не утверждение новой модели монетизации.  
**Цель:** выпустить самостоятельную Android-версию Sector Zero через RuStore, сохранив общее игровое ядро и существующие dev/player-каналы.  
**Навигация:** [Android-упаковка и текущие каналы](README.md). Продуктовые решения остаются в [едином roadmap Sector Zero](../docs/sector-zero-roadmap.md); границы интеграций — в [платформенных адаптерах](../docs/platform-adapters.md). Этот документ описывает отдельный платформенный релиз, а не новый продуктовый roadmap.

## 1. Вывод исследования

Не нужен новый игровой движок или отдельный форк. Нужен самостоятельный релизный путь: сборка Sector Zero → Android-упаковка → защищённая подпись → проверка устройства и сохранений → предрелизное тестирование → модерация → управляемая публикация.

Проверены официальные материалы RuStore и отдельные файлы ветки `main` репозитория MoonGameTechnology/MoonGame. Не выполнялись сборка APK, анализ готового Manifest, запуск на телефоне, прохождение кампании и вход в RuStore Консоль. Готовность этих элементов предстоит доказать на этапах ниже.

### Подтверждённые различия между текущей упаковкой и релизом

| Наблюдение | Доказательство | Что требуется |
|---|---|---|
| Есть самостоятельный HTML-вход Sector Zero | README и продуктовый роадмап [G1, G2] | Использовать этот продукт, не основной клиент |
| Android-упаковщик принимает только `dev` и `player` | `mobile/sync-www.mjs` [G3] | Добавить отдельный профиль Sector Zero |
| Команды APK вызывают `assembleDebug` | `mobile/package.json` [G4] | Отдельная release-сборка с обязательной проверкой подписи |
| Нативный патч закрепляет публичный debug-ключ; существующий канал обновляется через GitHub | `mobile/patch-updater.mjs`, `mobile/README.md` [G5, G6] | Не переносить эти механизмы в магазинный канал |
| В package.json объявлены зависимости Capacitor `^8.5.2`, а README описывает Capacitor 6/JDK 17 | [G4, G6] | Проверить фактический lockfile и согласовать инструкции с рабочим toolchain |
| Платформенная граница уже описана; серверный логин основной игры не является входом Sector Zero | `docs/platform-adapters.md` [G7] | Подключать сервисы через существующий контракт, не создавать вторую архитектуру |

Это точечная сверка прочитанных файлов, а не утверждение, что в других ветках нет соответствующих разработок.

## 2. Решения, которые должны быть зафиксированы до публикации

| Решение | Ответственный | Требуемый результат |
|---|---|---|
| Кто публикует: физлицо, ИП или компания; страна регистрации | Владелец продукта | Подходящий аккаунт, доступы и подтверждающие документы |
| Бесплатная загрузка, платное скачивание или покупки внутри игры | Владелец продукта | Явно утверждённая модель первого релиза |
| Публичное название, package name и владелец ключа | Владелец + Android-разработчик | Постоянная идентичность приложения; отсутствие конфликта с dev/player |
| Поддерживаемые устройства, версии Android/WebView и ориентации | Android-разработчик + QA | Матрица совместимости и измеримые показатели производительности |
| Какие главы, миссии и функции входят в релиз | Владелец + QA | Ссылка на утверждённый продуктовый объём; без изменения баланса этим планом |
| Какие данные и SDK реально используются | Разработчик + ответственный за документы | Карта потоков данных, декларации, политика и юридическая проверка |

**Упрощённая техническая ветка:** бесплатная загрузка без покупок и рекламы, гостевое прохождение, локальная мета. Это предложение для уменьшения зависимостей, не решение о коммерческой модели. При необходимости продаж с первого дня этап RUS-M становится обязательным.

Регистрация доступна физлицам и бизнесу; подключение монетизации RuStore предусмотрено для ИП и юридических лиц. Для зарубежного издателя применима отдельная процедура проверки и договора [R1, R2]. Нельзя определять статус издателя по месту проживания участника команды.

## 3. Карта официальных требований

| Область | Краткая опора для реализации | Источник |
|---|---|---|
| Самостоятельность | WebView допустим для законченного продукта, а не перенаправления на сайт | [R3] |
| Поставка | APK либо AAB; предел файла 5 ГБ | [R4] |
| Идентичность | Контролируемая подпись и совместимость обновлений | [R5] |
| Карточка | Название до 30, краткое описание до 80, полное до 4000 символов; минимум три скриншота для соответствующего типа устройства | [R4] |
| Данные | Декларирование собираемых данных и обоснование чувствительных разрешений | [R6] |
| Тестирование | Закрытая альфа — для бесплатных мобильных приложений; бета открытая | [R7, R8] |
| Выкладка | Долевое распространение доступно обновлениям, не первой публикации | [R9] |
| Покупки | Актуальное руководство ориентирует интеграцию на Pay SDK | [R10] |

Предрелизный реестр должен содержать для каждого требования источник, дату проверки, реализацию, проверяющий сценарий и доказательство прохождения. Перед отправкой повторно сверить ограничения консоли, особенно версии Android/SDK и правила оформления. Численный обязательный `targetSdkVersion` в рамках исследования не подтверждён: не переносить автоматически требования другого магазина.

## 4. Архитектура релизного канала

```text
Общее ядро + продуктовые модули Sector Zero
                  │
        самостоятельная HTML-сборка и её ресурсы
                  │
        существующий контракт GamePlatform
                  │
        Android/RuStore-адаптер нужных возможностей
                  │
        отдельная Capacitor release-конфигурация
                  │
        подписанный APK + протокол проверок
                  │
        тестирование → модерация → публикация
```

Не добавлять в `shared-core` зависимости RuStore. Не включать корпорации, сетевую регистрацию, FFA и другие ненужные продукту модули только потому, что они есть в монорепозитории. Для ограничения состава использовать граф импортов и чистую упаковочную директорию, а не только размер файла.

Разделить: идентичность установки, игровой профиль, идентичность покупки и возможный облачный профиль. Платёжный аккаунт сам по себе не является облачным сохранением. Недоступная возможность должна корректно отражаться в `capabilities`, а не оставлять неработающую кнопку.

## 5. Этапы и критерии завершения

### RUS-0. Паспорт релиза и реестр требований

**Приоритет:** P0. **Зависимости:** нет. **Ответственные:** владелец, Android-разработчик, QA.

Завести паспорт из раздела 2, выбрать владельцев доступов, проверить условия аккаунта и поддержки, собрать реестр требований. Не ставить календарную дату публичного запуска до подтверждения технической совместимости и маршрута тестирования.

**Готово:** все решения либо утверждены, либо имеют явный блокирующий статус; команда знает, какой именно продукт и на каких устройствах выпускает.

### RUS-1. Самостоятельная Android-упаковка Sector Zero

**Приоритет:** P0. **Зависимости:** выбран продукт и package name. **Ответственный:** Android/клиентский разработчик.

Добавить профиль в упаковщик; собирать `sector-zero.html` и полный комплект его локальных ресурсов. Очищать staging перед упаковкой. Не повреждать прежние dev/player-команды. Согласовать название, иконку и стартовый экран. Добавить проверку отсутствия запрещённых для продукта импортов и случайно оставшихся dev-экранов.

**Готово:** из чистого checkout получается отдельное приложение; оно открывает Sector Zero, содержит нужные изображения/комиксы/звук и не предлагает вход в основную сетевую игру. Артефакт привязан к исходному commit.

### RUS-2. Производственная подпись и воспроизводимый выпуск

**Приоритет:** P0. **Зависимости:** RUS-1. **Ответственные:** Android-разработчик + ответственный за CI.

Создать отдельную release-конфигурацию, исключающую debug-signing patch. Хранить закрытый ключ и его резервную копию вне репозитория, с ограничением доступа. Зафиксировать отпечаток сертификата, package name, растущий счётчик `versionCode` и понятный `versionName`.

Сверить реальные версии Capacitor, JDK, Gradle и Android SDK с lockfile и сборкой. Выпускать магазинный артефакт по защищённому тегу или ручному запуску workflow, а не автоматически из каждого merge. Не передавать production-секреты в проверки недоверенных PR.

**Готово:** CI отклоняет debug-артефакт, неверный сертификат, отсутствие ключа, неверный package name и нерастущую версию. Две последовательно собранные release-версии успешно обновляются одна поверх другой без очистки данных. Сохраняются SHA-256 APK, commit, версии toolchain, отчёт подписи и результаты тестов.

### RUS-3. Обновления, жизненный цикл и сохранения

**Приоритет:** P0. **Зависимости:** RUS-1; итоговые проверки после RUS-2. **Ответственные:** клиентский и Android-разработчик.

Для магазинной сборки убрать проверку GitHub alpha/player и переходы к сторонним APK. Реализовать канал уведомления и обновления через RuStore; SDK обновлений рассмотреть как основной вариант [R11]. Сбой проверки обновлений не должен блокировать игру. Предлагать установку после сохранения, не во время критического игрового действия.

Проверить ограничение схем и адресов нативного моста. Обработать системную кнопку «Назад», сворачивание, блокировку экрана, смену ориентации, восстановление Activity и завершение процесса. Добавить явные состояния загрузки/ошибки вместо пустого экрана и бесконечного перезапуска.

Стабилизировать область хранения и версию формата меты. Проверить запись наград, защиту от повторной выдачи после перезапуска, восстановление предыдущего корректного состояния и миграцию сейвов между релизами. Не обещать автоматический перенос прогресса из отдельного debug-приложения: для него нужен самостоятельный механизм миграции.

**Готово:** регрессионная матрица сохранений пройдена на release-APK; подтверждены отсутствие потери меты и корректная деградация при отсутствии сети/магазина. Обычное обновление не обнуляет прогресс.

### RUS-4. Документы, контент и карточка

**Приоритет:** P0. **Зависимости:** начинается параллельно RUS-1; финал после фиксации функций. **Ответственные:** владелец, дизайнер/редактор, ответственный за данные.

Подготовить контакт поддержки, документы о данных, соответствующие реальным SDK, и пользовательские условия по необходимости. Проверить итоговый merged Manifest, а не только исходный файл. Для каждой передачи данных указать назначение, получателя, срок хранения и обоснование. Юридические обязанности издателя определить с учётом его статуса и фактической обработки.

Провести аудит комиксов, сцен войны, текстов и символики; выбрать возрастную категорию по финальному содержимому, а не предположению. Составить реестр происхождения арта, музыки, шрифтов и сторонних компонентов; проверить условия коммерческого использования.

Подготовить русское описание без спойлеров, реальные скриншоты release-сборки, иконку и инструкции модератору. Рекомендуемый комплект: карта, орбитальный бой, развитие/подготовка, выбор главы и фрагмент сюжетной подачи. Это композиционный план, не доказательство готовности каждого экрана.

**Готово:** документы и карточка проверены на соответствие APK; каждый рекламируемый сценарий воспроизводится; нет ссылок на чужие магазины и материалов, права на которые не подтверждены.

### RUS-M. Монетизация — только при утверждённой необходимости

**Приоритет:** P0 для платного релиза; иначе не блокирует бесплатный выпуск. **Зависимости:** RUS-0, RUS-1, RUS-2. **Ответственные:** владелец + интеграционный/backend-разработчик + QA.

Отдельно различать продажу приложения и покупки внутри него. Для внутриигровых покупок выбрать поддерживаемую версию Pay SDK, проверить её требования и изолировать интеграцию нативным адаптером. Утвердить товары и пользовательские условия, не меняя баланс этим документом.

Спроектировать идентичность владельца покупки и восстановление прав. Проверять подтверждённый платёж, выдавать ценность идемпотентно, восстанавливать незавершённые операции, обрабатывать отмену, потерю сети, повторный callback и возврат. Серверные платёжные секреты не помещать в APK. Подтверждение двухстадийного платежа и необязательный признак выдачи — разные механизмы [R10].

**Готово:** договор и товары готовы; тестовые сценарии не допускают списание без восстановления положенного товара и повторного начисления. Переустановка/другое устройство обрабатываются согласно явно заявленной модели. Не обещать облачный сейв на основании наличия платёжного SDK.

### RUS-5. Проверка качества и предрелизное тестирование

**Приоритет:** P0. **Зависимости:** RUS-1–4; RUS-M при необходимости. **Ответственный:** QA с разработчиками.

Сначала пройти матрицу раздела 6 и основные проверки репозитория (`pnpm run check`, сборка продукта, профильные browser smoke). Затем проверить именно подписанный Android-артефакт, а не только браузерную версию.

Для бесплатного мобильного приложения использовать закрытую альфу RuStore [R7]. Начать с предлагаемой группы 20–30 тестеров, распределённых по матрице устройств; это наш рабочий ориентир, не обязательный минимум магазина. Альфа также проходит модерацию. Участникам заранее объяснить статус тестовых сохранений и проверить маршрут перехода в production, не гарантируя его бесшовность.

Для платного скачивания сначала подтвердить доступный предрелизный маршрут у RuStore: закрытую альфу нельзя считать доступной по умолчанию. Не подменять это молчаливой сменой коммерческой модели.

**Готово:** весь заявленный релизный объём проверен; нет открытых P0/P1; для каждой поддерживаемой конфигурации приложено доказательство прохождения критических сценариев. Отзывы тестеров разобраны, исправления повторно проверены.

### RUS-6. Модерация и первая публикация

**Приоритет:** P0. **Зависимости:** RUS-5 и комплект документов. **Ответственные:** владелец/релиз-менеджер + QA.

Зафиксировать release candidate, загрузить его и согласованную карточку. Выбрать ручное управление первой публикацией. В комментарии модератору дать краткий маршрут проверки и тестовый доступ, если в выбранной модели есть ограничения. Каждое замечание связывать с конкретной исправленной версией.

После одобрения вручную опубликовать выбранный артефакт, затем установить приложение именно из RuStore на чистое устройство и проверить критический пользовательский путь. Зафиксировать опубликованные идентификаторы и артефакт. Масштабное продвижение начинать после этой проверки.

**Готово:** приложение доступно пользователям, установка с витрины проверена, версия и сертификат совпадают с паспортом, поддержка готова принимать обращения, подготовлен процесс срочного исправления.

### RUS-7. Поддержка и следующие версии

**Приоритет:** P1; аварийные процедуры подготовить до RUS-6. **Ответственные:** QA, релиз-менеджер, разработчики.

Собирать достаточную для диагностики информацию о версии, устройстве и сбое без лишних персональных данных. Различать нативные падения, JavaScript-ошибки, зависания и потерю прогресса; один показатель crash-free не заменяет остальные проверки.

Для последующих обновлений применять предлагаемый порядок 5% → 25% → 100%, расширяя распространение только после анализа результата. Это наша политика, не установленная RuStore последовательность. Магазин позволяет остановить проблемную выкладку, но уже установленная версия у пользователя остаётся; поэтому заранее готовить hotfix с большим `versionCode` [R9].

**Готово:** есть ответственный за отзывы, журнал инцидентов, условия остановки выкладки и проверенный способ выпустить исправление без потери сейвов.

## 6. Приёмочная матрица

| Группа | Обязательные для нашего релиза проверки | Доказательство |
|---|---|---|
| Первый запуск | Чистая установка; отсутствие мигания, белого экрана и reload-loop; полный комплект ресурсов | Запись экрана и лог release-версии |
| Обучение и кампания | Новичок проходит обучение; все заявленные главы/миссии завершаются; победа и поражение корректно выдают награды | Чек-лист прохождения с идентификаторами сборки |
| Мета и сейвы | Сворачивание, блокировка, process kill, перезапуск, повреждённая/старая запись, миграция | Автотесты и сравнительный снимок прогресса |
| Обновления | Версия N → N+1; сохранение ресурсов/героев/глав; отсутствие внешнего APK-канала | Отчёт установки двух подписанных версий |
| Телефонный интерфейс | Карта, масштаб, тап/drag, панели, текст, «Назад», экранные вырезы, заявленные ориентации | Матрица реальных устройств |
| Производительность | Самая тяжёлая карта/битва; память, частота кадров, нагрев и длительная сессия | Измерения относительно порогов из RUS-0 |
| Зависимости | Нет сети, сеть пропала, RuStore недоступен, нет Google-сервисов | Протокол поведения без блокировки обещанных функций |
| Безопасность | Подпись, Manifest, экспортируемые компоненты, bridge/deep links, отсутствие секретов | Отчёт проверки финального артефакта |
| Покупки, если есть | Успех, отмена, прерванная операция, повторная выдача, восстановление, возврат | Сопоставленные тестовые транзакции и права игрока |
| Карточка и поддержка | Название/иконка совпадают, функции доступны, контакт работает | Подписанный чек-лист редактора и QA |

**P0:** невозможность запуска/прохождения ключевого пути, потеря меты, серьёзная уязвимость, ошибка денег или прав покупки.  
**P1:** воспроизводимая серьёзная ошибка основного управления или заявленной функции.  
Эти определения и критерий «нет открытых P0/P1» — внутренняя политика предлагаемого релиза, не отдельная норма RuStore.

## 8. Контрольное определение «релиз готов»

Релиз готов не тогда, когда появился APK, а когда проверенная версия устанавливается из RuStore, соответствует карточке, сохраняет прогресс при обычном обновлении и имеет подготовленный путь срочного исправления. Все обязательные этапы должны иметь ссылку на доказательство; отсутствие доказательства не отмечается как выполненная задача.

**Ближайшая инженерная задача:** RUS-1 — самостоятельный Android-профиль Sector Zero. Параллельно владелец закрывает решения RUS-0 и начинает подготовку карточки/документов RUS-4.
