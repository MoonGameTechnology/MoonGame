## Как читать документ

**Факт по коду** означает поведение, найденное в указанных исходниках на проверенном коммите. **Принятое направление** — решение из действующего профильного документа. **Предложение** — рекомендуемое изменение с причиной, ограничениями и условием готовности. **Требует проверки** — риск, который нужно подтвердить экспериментом, а не выдавать за воспроизведённый дефект.

Это целевая сверка границ, точек запуска, сохранения, времени и упаковки, а не полный аудит всех файлов, безопасности или работающего сервера. Конфигурация в GitHub не доказывает конфигурацию развёрнутой машины. Наличие тестов не означает успешный прогон на этом SHA. Большой `docs/state.md` не удалось получить используемым инструментом; поэтому из него не заимствуются ни счётчики, ни статусы готовности.

Документ заменяет устаревшие утверждения прежней редакции: Redis/BullMQ как обязательный текущий стек; React Native как действующий клиент; JSONB как отмену миграций; отсутствие уже реализованной фильтрации видимости; гарантии восстановления, не подтверждённые рабочим путём. Исторические версии остаются в Git. Продуктовый канон, баланс и статусы кирпичей здесь не дублируются.

## 1. Обзор проекта

### Главный вывод

Архитектуру не требуется придумывать заново. Уже есть детерминированное игровое ядро, серверный слой, контракт сообщений, хранилища и разделение платформенных возможностей. Основная проблема следующего этапа — **свести фактические пути выполнения к единым гарантиям**, а не добавить больше технологий.

Текущее серверное приложение разумно описывать как **модульный монолит**: сервер работает одним процессом, но внутри разделён по обязанностям. Бой, движение и экономика — модули, а не независимые сетевые сервисы. Один процесс способен вести несколько отдельных матчей; это не один общий мир. Такая классификация — вывод по устройству рабочего хоста, а не заявление о числе процессов на действующей машине. [S1], [S2]

### Два продукта, один фундамент

```text
Основная стратегия                    Sector Zero
Сетевые матчи, корпорации,             PvE, главы, миссии,
дипломатия, своя метаигра               свой прогресс и сборка
                \                     /
                 Общий фундамент
       Симуляция, движение, бой, экономика,
     технологии, эффекты, видимость, контракты
```

**Принятое направление.** Sector Zero использует технологию основной игры, но не зависит от её приложения. Это не форк репозитория и не только урезанный режим. У продукта могут быть собственные механики. Общее решение переносится в фундамент, а конкретная сюжетная миссия остаётся продуктовой. Ненужные механики основной игры должны отсутствовать в продуктовой сборке, а не просто прятаться за кнопками. [S8]

**Почему так.** Копия ядра дала бы два расходящихся расчёта боя и две цепочки исправлений. Зависимость кампании от всего приложения основной игры принесла бы ненужные экраны, аккаунты и сетевые отказы. Общий фундамент убирает первое, самостоятельная композиция продукта — второе. Цена решения: нужно поддерживать явные границы импорта и проверять каждую поставляемую сборку.

Общий исходный код **не означает** общие аккаунты, смешанные сохранения, один сервер или одинаковый набор возможностей. В сетевом матче итог определяет сервер. В автономной кампании симуляция может выполняться локально; такой локальный прогресс нельзя автоматически считать доверенным основанием для награды в конкурентной серверной экономике.

### Что уже есть и что ещё нельзя обещать

| Область | Подтверждённая основа | Ограничение вывода |
| --- | --- | --- |
| Сервер | Рабочий хост собирается в контейнер, использует общие серверные компоненты | Второй вход пакета не является Docker-входом |
| Действия | Подключаемый `ActionGate`, авторитетная комната и квитанции | Проверка запроса не заменяет игровые правила и атомарную запись |
| Хранение | PostgreSQL при `DATABASE_URL`, иначе Memory-хранилища | Нельзя обещать долговечность только по наличию флага `PROD` |
| Время | Общий драйвер часов, восстановление сохранённого времени | Простой процесса сейчас не догоняется |
| Клиенты | Играбельный `prototype/`, развивающийся `packages/client`, общие `decisions/` | Это ещё не единый полностью мигрированный интерфейс |
| Android | Capacitor и упаковщик `dev`/`player` | В проверенном упаковщике нет отдельного профиля Sector Zero |

Основания: [S1], [S2], [S5], [S9], [S10].

## 2. Философия ядра: Data-Driven

**Данные описывают объекты в пределах уже реализованных правил.** Новый корабль с существующими характеристиками обычно добавляется через контент. Новое поведение оружия может потребовать модуль, схему данных и тесты. JSON сам по себе не исполняет неизвестную механику.

| Изменение | Правильный владелец | Почему |
| --- | --- | --- |
| Характеристики корабля, стоимость здания | `data/` и валидируемые схемы | Не нужна копия расчёта под каждый объект |
| Новое правило попадания или ремонта | Модуль `packages/shared-core` | Один результат в локальной и серверной симуляции |
| «Спасти учёного», условие открытия главы | Продуктовая миссия/сценарий Sector Zero | Это не обязательное правило каждого сетевого матча |
| Доступность кнопки, маршрут после отказа | Общее чистое решение в `decisions/` | Оба клиента должны одинаково интерпретировать действие |
| Отрисовка окна боя, жесты конкретного экрана | Владелец интерфейса и общие решения там, где они уже выделены | DOM и рисование не относятся к симуляции |
| Текст кнопки или комикса | `/localization` и продуктовый контент | Не размножать пользовательские строки в коде |
| Магазинная покупка или облачный сейв | Платформенный контракт и адаптер | SDK площадки не должен менять законы мира |

Это применение действующих границ, а не требование перенести все файлы за один PR. Правила чистых решений и локализации уже закреплены в репозитории. [S3], [S9]

**Важная поправка о балансе.** Правка JSON не означает, что её безопасно незаметно применить к текущему матчу. Требуются версия данных, проверенная совместимость и понятная политика обновления. «Без правки кода» и «без выпуска/миграции» — разные свойства. Политика версий имеет собственный дом: [versioning.md](versioning.md).

## 3. Технологический стек

### Реальная раскладка ответственности

| Слой | Где искать | Ответственность и граница |
| --- | --- | --- |
| Игровые правила | `packages/shared-core` | Состояние мира, действия, события и воспроизводимая симуляция; без БД, SDK и UI |
| Контракт сети | `packages/protocol` | Общие типы/форматы сообщений; клиент не должен импортировать сервер ради типов |
| Проверка действий | `packages/action-layer` | Конверт, payload, сессия, последовательность и повторные запросы |
| Серверные компоненты | `packages/server` | Комнаты, сеть, сервисы, хранилища, драйвер часов |
| Поставляемый серверный вход | `prototype/netserver.ts` | Собирает действующий хост из компонентов и игрового сценария |
| Основной играбельный UI | `prototype/` | Карта, панели, ввод и сборка клиента |
| Развивающийся клиент | `packages/client` | Транспорт, модели и UI; уже есть вход/выбор матча, не только пустая оболочка |
| Общие решения клиента | `decisions/` | Чистые решения без DOM, сети и таймеров; не правила мира |
| Тексты и контент | `localization/`, `data/` | Общая локализация и игровые данные |
| Площадки / Android | `prototype/src/platform/`, `mobile/` | Адаптеры возможностей и нативная упаковка |
| Развёртывание | `Dockerfile`, `deploy/` | Поставляемый образ, Compose, TLS и эксплуатационный контур |

Основания: карта кода, правила проекта и реальные точки сборки. [S1], [S2], [S3], [S4], [S9], [S10]

### Что именно запускается

`Dockerfile` выполняет `prototype/bundle-netserver.mjs`, а затем запускает **`packages/server/dist/proto-server.mjs`**. Этот бандл происходит из **`prototype/netserver.ts`**. `packages/server/src/main.ts` — другой вход. Исправление только второго файла не гарантирует изменение контейнерного сервера. [S1], [S4]

При этом уже общие вещи нельзя объявлять отсутствующими: в частности, оба хоста используют общий `startClockDriver`. Задача — убрать оставшиеся расходящиеся настройки и сборку компонентов, а не написать ещё один планировщик. [S2]

### Выбранный стек и отложенные варианты

Принятое решение — TypeScript, общее ядро, Node.js, `ws` с HTTP-слоем рядом, PostgreSQL/JSONB, веб-клиент и Capacitor. В текущем пути используются внутрипроцессные пробуждения комнат. **pg-boss — направление дальнейшего развития; Redis/BullMQ не являются установленным обязательным звеном этой схемы.** [S2], [S5], [S6]

Общее ядро на клиенте полезно для локальной игры и предпросмотра своего намерения. Оно **не даёт клиенту права назначать результат сетевого матча**. Предпросмотр ограничен доступными сведениями: неизвестный состав противника нельзя превращать в «точный прогноз».

**Почему не микросервисы сейчас.** Разделение боя, экономики и движения по сети добавит промежуточные отказы и согласование общего состояния. Пока задача — надёжно вести отдельные матчи, дешевле удерживать одну последовательность изменений внутри комнаты. Отдельный сервис оправдан только самостоятельной ответственностью и измеренной потребностью, а не длиной исходного файла. Это предложение соответствует направлению ADR по стеку. [S6]

## 4. Архитектура ядра

### 4.1 Модель времени — event-based

Контракт ядра: `applyAction(state, action, ctx)` применяет намерение, `advanceTo(state, ctx)` продвигает симуляцию к переданному времени. События расписания имеют воспроизводимый порядок; течение времени передаётся логике явно. Способ получить реальное время и разбудить комнату — обязанность хоста, не игрового модуля. [S3]

Нужно различать три ситуации:

| Ситуация | Что следует из текущего пути |
| --- | --- |
| Игрок закрыл браузер | Процесс сервера и драйвер событий могут продолжать работу; это не остановка мира |
| Процесс сервера выключился | Нет исполняющего процесса; события в этот период не обрабатываются |
| Процесс поднялся из снимка | Рабочий хост продолжает от сохранённого `state.time`, **не догоняя простой** |

Последний пункт прямо зафиксирован в реализации рабочего хоста. Также базовый Compose задаёт `TIME_SCALE=24` по умолчанию для плейтеста; `1` — другой, явно выбираемый темп. Это конфигурация, а не универсальная скорость всех продуктов. [S2], [S7]

**Вывод.** Заявление «мир идёт круглосуточно» требует отдельно согласовать поведение при аварии. Возможность `advanceTo` рассчитать время не доказывает, что конкретный хост действительно использует её для восстановления после простоя.

### 4.2 Детерминизм

Инварианты проекта: одинаковые входы и версии дают воспроизводимый результат; случайность идёт через seeded RNG; время передаётся контекстом; `applyAction` не изменяет входной объект; состояние сериализуемо. Модули взаимодействуют через события, hooks и capabilities, а не импортируют соседние модули. Порядок модулей — часть контракта. [S3]

**Цена и польза.** Ограничения делают код менее произвольным, зато позволяют повторить проблему на тех же входах. Но одно наличие детерминированного ядра ещё не создаёт полноценный replay: для него нужны исходное состояние, входные действия, переходы времени и соответствующие версии данных/правил. Снимок состояния и квитанции запросов сами по себе не равны полному журналу событий.

### 4.3 Структура состояния

Проверенная PostgreSQL-модель уже сочетает обычные столбцы для `id`, версии, `seq`, статуса и JSONB для состояния. Код содержит создание и изменение схемы таблиц. Поэтому формулировка «JSONB — без миграций» неверна: он облегчает хранение структурированного состояния, но не отменяет совместимость старых сохранений, индексы, ограничения и преобразование значений. [S5]

Раздельными обязанностями остаются контент, состояние конкретного матча и межматчевый профиль. Даже если они хранятся в одном PostgreSQL, у них разные правила владения, срок жизни и основания для изменения. Не нужно превращать их в один неограниченный blob.

### 4.4 Версионирование данных

**Предложение.** Проверять совместимость набора: версия схемы сохранения, данных, правил/манифеста, протокола и продукта. Конкретное представление набора следует согласовать с действующей политикой версий, не вводя параллельную систему. [versioning.md](versioning.md)

Номер версии имеет смысл только вместе с доступным способом прочитать и исполнить её. Для долгого матча нужно либо сохранять совместимый код/контент, либо явно мигрировать, либо безопасно отказать в загрузке с понятной диагностикой. Молча подставлять текущие правила вместо неизвестной версии нельзя.

**Почему.** Иначе обновление может изменить уже оплаченный приказ, сломать длительную стройку или трактовать старый флот по новым правилам. Цена — хранение совместимых артефактов и тестовых старых сохранений. Это дешевле ручного исправления пользовательского прогресса после релиза.

## 5. Безопасность: античит

### Путь одного приказа

```text
Кнопка / жест
    → общий строитель намерения
    → сообщение по контракту
    → проверка соединения, сессии и ActionGate
    → последовательная обработка в комнате матча
    → advanceTo / применение правил ядра
    → попытка сохранения
    → принятие результата комнатой
    → разрешённое игроку представление / обновление UI
```

Это карта обязанностей, а не утверждение, что каждый микрошаг всех путей уже одинаково реализован. Рабочий хост подключает `ActionGate`, квитанции, `MatchRoom`, фильтр дополнительных полей `hostFog` и callback сохранения. **Текущая граница сохранения подробно разобрана в §7: два `await` не являются одной транзакцией.** [S2]

Проверка личности отвечает «кто отправил запрос». Проверка схемы — «можно ли разобрать payload». Игровое правило — «может ли этот игрок сейчас выполнить приказ». Нужно всё вместе: корректно подписанный запрос всё ещё может требовать потратить чужие ресурсы.

### Скрытое не должно уходить клиенту

Фильтрация видимости — уже существующая часть архитектуры, не новая идея. Рабочий хост дополнительно ограничивает продуктовые поля через `hostFog`; в индексе есть завершённые задачи по фильтрации событий и строительства. Но это не доказательство отсутствия утечек во всех каналах. [S1], [S2], [S14]

**Предложение.** Для каждого нового типа сущности проверять снапшот, дельту, события, отчёт боя, сообщения об ошибках и диагностические поля. Прятать объект только на canvas недостаточно. Проверка должна сопоставлять ответы двум игрокам с разной видимостью, включая потерю обзора и реконнект.

### Платформенное доверие и локальная кампания

Отказ SDK или недоступная реклама могут переводить игру в доступный гостевой сценарий. Неопределённый результат покупки не должен превращаться в успешную выдачу товара. Локальный сейв не становится серверным доказательством владения предметом только потому, что он создан нашим UI.

Так разделяются **мягкая деградация необязательной возможности** и **безопасный отказ операции с правами или ценностью**. Это не повод заставлять гостя Sector Zero входить в аккаунт основной игры: такая зависимость противоречит принятому продуктовому разделению. [S8], [S11]

Этот раздел не является сертификатом соответствия и не заменяет [модель угроз](security-a06.md), [целостность игры](game-integrity-roadmap.md) и [безопасный цикл разработки](secure-sdlc-roadmap.md). Наличие архитектурного документа само по себе не «закрывает» категорию угроз.

Для нашей архитектуры практически важны проверка прав на каждое намерение, закрытые административные поверхности, валидация сообщений, отказ без утечки деталей, защита сохранений и выпускаемых артефактов. Проверять нужно работающий путь и отрицательные сценарии, а не число подключённых сканеров.

Для WebSocket ориентиром служат WSS, явная проверка Origin, действительность сессии, авторизация сообщений, ограничения размера/частоты и безопасное логирование. Origin — не замена токену: небраузерный клиент может сформировать заголовок сам. Требования следует связывать с конкретными маршрутами и тестами. [E3]

**Вывод.** Надёжность, античит и безопасность здесь пересекаются: повторное начисление из-за сбоя записи — одновременно дефект восстановления и нарушение честности. Поэтому граница транзакции и порядок обработки важнее общего обещания «сервер авторитетный».

## 7. Отказоустойчивость

### 7.1 Подтверждённая граница сохранения

В рабочем хосте callback содержит:

```ts
persist: async (snapshot, receipt) => {
  await matchStore.save(snapshot);
  await receiptStore.save(id, receipt);
}
```

Это выдержка текущего кода, **не рекомендуемый пример атомарной записи**. Сохранение снимка в `PostgresMatchStore` использует отдельный `pool.query`; общей транзакции вокруг пары в данном пути нет. Ожидание обоих вызовов до публикации защищает от преждевременного успешного ответа, но не гарантирует «оба изменения или ни одного» в базе. [S2], [S5]

**Риск, требующий проверки.** Первый вызов мог записать новое состояние, а второй — завершиться ошибкой или не успеть выполниться из-за остановки процесса. База тогда уже отличается от предположения «всё откатилось». Последующий retry и восстановление нужно проверить на этой конкретной границе. Здесь не утверждается, что двойное списание уже воспроизведено.

PostgreSQL даёт атомарность группе команд внутри транзакции; без явной группы отдельные команды фиксируются самостоятельно. В node-postgres транзакционные команды должны идти через один выделенный client, а не отдельные вызовы `pool.query`. [E1], [E2]

### 7.2 Последовательность действий — не распределённая блокировка

Текущий upsert снимка защищён условием `matches.seq <= EXCLUDED.seq`. Это полезная защита от записи заведомо старого `seq`, но она разрешает равенство и не является проверкой ожидаемой предыдущей ревизии. Метод не сообщает вызывающему коду число изменённых строк. [S5]

**Вывод.** Нельзя использовать этот фильтр как доказательство безопасного параллельного ведения одного матча двумя процессами. Нужно отдельно проверить различение снимков с одинаковым `seq`, временных обновлений и конфликтующего владельца матча. Это ограничение гарантии, а не заявление о найденной эксплуатации.

### 7.3 Разные изменения — разные окна потери

Для изменений, вызванных временем, в хосте есть отложенное сохранение; для запросов используется callback перед публикацией. Они не дают автоматически одинаковую гарантию. Восстановление должно учитывать запланированные события, изменения от ИИ, награды и последние подтверждённые запросы. [S2]

Хороший уже существующий пример — `PostgresCommanderStore.creditMatch`: маркер начисления и само начисление выполняются внутри явной транзакции. Следовательно, защита наград не «отсутствует вообще»; подобный подход стоит последовательно применить к нужным границам фиксации матча. [S5]

## 8. Сетевая инфраструктура и безопасность

### Конфигурация публичного запуска, а не снимок действующего хоста

```text
Браузер / Android
        │ HTTPS / WSS
        ▼
Caddy — публичный TLS-вход
        │ сеть Compose
        ▼
Node.js — игровой хост
        │
        ▼
PostgreSQL — постоянное состояние
```

В репозитории есть базовый Compose с сервером/PostgreSQL и TLS-оверлей с Caddy. PostgreSQL публикуется на loopback хоста; приложение обращается к нему по внутренней сети. Для пути через прокси документация оверлея требует `SERVER_BIND=127.0.0.1`. **Само добавление TLS-оверлея не следует считать доказательством, что прямой игровой порт закрыт:** итоговую объединённую конфигурацию и фактическую достижимость нужно проверить. [S7], [S12]

`TRUST_PROXY=1` — доверие к данным прокси, не самостоятельное доказательство защищённого транспорта. При доступном в обход прокси порте клиент способен подставить заголовки. Caddy и ограничения портов — разные, дополняющие друг друга меры. [S2], [S12]

В этой сверке не проверялись публичный IP, DNS, firewall, сертификат, текущий image digest, резервные копии и доступность БД пользователя. Cloudflare, несколько регионов и управляемые облачные сервисы не объявляются уже развёрнутыми.

### Отдельный риск: публичный режим без долговечного хранилища

В проверенном хосте отсутствие `DATABASE_URL` выбирает Memory-хранилища. Проверка `PROD` требует ряд защитных флагов и проверяет известный дефолтный пароль БД, но не требует самого непустого `DATABASE_URL`. **По прочитанной конфигурационной логике** это оставляет путь к запуску без постоянного хранилища вне штатного Compose, если остальные условия выполнены. Прогон такого запуска здесь не выполнялся. [S2]

Штатный базовый Compose передаёт URL PostgreSQL, поэтому этот вывод **не означает**, что его обычный путь всегда теряет данные. Рекомендация — закрепить требование долговечного режима в самом приложении, а не полагаться только на один способ запуска. [S7]

## 9. Оптимизация: влияние безопасности

Не следует обещать, что проверки «почти ничего не стоят», или назначать универсальные проценты CPU без замеров. Сохранение, фильтрация состояния, сериализация, хеширование и проверка прав имеют стоимость; её надо измерять в наших сценариях.

**Предлагаемый порядок:** сначала корректность и наблюдаемость, затем устранение измеренного узкого места, потом изменение инфраструктуры. Снять проверку прав ради быстрого запроса — не оптимизация. Иногда уменьшить разрешённую дельту выгоднее, чем менять язык сервера; иногда время уходит в запись БД, а не в ядро. Это устанавливается профилем, не внешним видом схемы.

Минимальный набор замеров: время обработки намерения и durable commit, ожидание очереди комнаты, лаг ближайшего события, число отказов/конфликтов, объём разрешённых дельт, RSS и задержка event loop. Значения p95/p99 и бюджеты следует назначить после воспроизводимого базового замера для выбранного профиля. Владельцы темы: [metrics-roadmap.md](metrics-roadmap.md), [infra-sizing-roadmap.md](infra-sizing-roadmap.md).

## 10. Подробные предложения и почему именно так

Приоритеты ниже — **рекомендация порядка**, а не новые заведённые кирпичи. Перед реализацией нужно найти существующую задачу через `bricks-index.md`, сверить её тело и фактический код. Назначенные исполнители, сроки и статусы завершения здесь не выдумываются.

### А. Общая сборка серверных компонентов — P0

**Проблема.** Два входа позволяют исправить проверку или хранилище не на том пути, который получает игрок. При этом часть компонентов уже общая. [S1], [S2]

**Предлагается.** Выделять единую сборку хоста с явными зависимостями: конфигурация, сторы, политика авторизации, создание комнат, наблюдение, запуск/остановка. Разные сценарии и dev-инструменты могут оставаться отдельными входами. Переносить по одной связной ответственности; сначала зафиксировать текущий контракт тестами.

**Почему не просто переключить Docker CMD.** Другой вход может не содержать нужной продуктовой композиции. Красивое имя файла не доказывает равенство поведения. Почему не копировать исправления вечно: копии постепенно расходятся, даже если конкретный баг сейчас закрыт в обеих.

**Цена и риск.** Ошибка выделения способна изменить порядок запуска или конфигурацию. Поэтому не совмещать эту работу с новым балансом, миграцией UI или сменой схемы сохранений.

**Готово, когда:** проверены регистрация/вход, создание и восстановление матча, гейт, видимость, ошибки БД и shutdown на **собранном контейнерном входе**; одинаковые политики не поддерживаются двумя рукописными копиями. Общий драйвер часов переиспользован, а не заменён третьим.

### Б. Атомарная фиксация действия — P0

**Проблема.** Снимок и квитанция в текущем callback записываются последовательно, но не атомарно. [S2], [S5]

**Предлагается.** Ввести одну операцию фиксации результата: новый снимок, квитанция, ожидаемая ревизия. PostgreSQL-реализация получает client, открывает транзакцию, проверяет конфликт, сохраняет согласованные данные и фиксирует их вместе. Обновление памяти комнаты и успешный ответ следуют за подтверждённой записью. Контракт не должен протаскивать SQL в ядро. [E1], [E2]

Ключ квитанции необходимо связать с субъектом и запросом; повтор одного идентификатора с другим содержимым не должен применить второе действие. При неизвестном исходе commit после обрыва связи сначала выясняется durable-результат по идентификатору, а не слепо повторяется эффект.

**Почему.** Пара отдельных интерфейсов удобна для чтения, но не выражает совместную гарантию записи. Один `await Promise.all(...)` её тоже не создаст. Транзакция защищает одну согласованную операцию, а не обещает «доставка по сети ровно один раз».

**Цена и риск.** Меняется контракт хранилища; потребуются миграция/совместимость квитанций и тесты ошибок. Нельзя держать транзакцию открытой на время рекламы, отправки сообщений или тяжёлого расчёта ядра.

**Готово, когда:** остановка до commit не оставляет половину операции; после commit и до ответа повтор возвращает тот же результат; конфликт версии отклонён; эффект не дублируется после рестарта. Тесты выполняются с настоящим PostgreSQL, не только с Memory-store.

### В. Явная готовность долговечного публичного сервера — P0

**Предлагается.** Публичный режим требует явно выбранного долговечного хранилища и подтверждённой доступности обязательной БД. Memory-вариант остаётся удобным, но только как осознанный dev/тестовый профиль. Readiness отражает способность обслуживать обязательные операции, а liveness — жизнеспособность процесса.

**Почему.** Сейчас долговечность зависит от наличия URL в окружении, а не только от заявленного публичного режима. При недоступности БД нельзя тихо перейти на память и продолжить выдавать успешные ответы. [S2], [S7]

**Цена.** Строже стартовая конфигурация, понятные диагностические ошибки и тесты профилей запуска. Это намеренная цена вместо незаметной потери матчей.

**Готово, когда:** публичный профиль без БД не принимает игру; явно локальный профиль работает; временный отказ БД не превращается в ложный успех; секреты отсутствуют в ответах и диагностике. Не исправлять ситуацию автоматическим выключением `PROD` или `GATE`.

### Г. Политика времени при простое — P0 перед обещанием длительных партий

**Предлагается.** Раздельно определить политику для сетевого мира, автономной кампании, плейтеста и технического обслуживания. Сохранённый якорь времени и масштаб относятся к матчу; решение «пауза» либо «догонять» должно быть явным и совместимым с ожиданиями игрока.

**Почему.** Текущее восстановление пропускает простой. Молчаливая смена на догоняние может неожиданно разрешить много боёв после аварии и изменить результат кампании. Ни одна политика не должна включаться случайно вместе с рефакторингом. [S2]

**При выборе догоняния:** ограничивать работу порциями, сохранять проверяемый прогресс, обрабатывать просроченные события в воспроизводимом порядке, не принимать действия в полувосстановленный мир. Предусмотреть скачки часов и повторный сбой на середине восстановления.

**Цена.** Дополнительная модель восстановления и решения по UX/эксплуатации. **Готово, когда:** сценарии остановки до прибытия флота, внутри боя и до завершения стройки дают заранее утверждённый результат; масштаб времени не меняется незаметно после перезапуска.

### Д. Ревизии, совместимость и восстановление — P1

**Предлагается.** Проверить, что ревизия различает все публикуемые изменения, включая изменения от времени и внутренних приказов. Если нынешний `seq` этого не обеспечивает, ввести отдельную ревизию состояния и проверку ожидаемой предыдущей версии. Не переопределять смысл `seq` без проверки протокола и сохранений.

**Почему.** Условие `stored.seq <= incoming.seq` само по себе не разрешает конфликт равных номеров и не защищает владение матчем. Отдельно нужна политика сохранений и доступности старых правил (§4.4). [S5]

**Цена.** Миграции, фикстуры старых сейвов, совместимые обновления. **Готово, когда:** устаревшая запись не заменяет более новое состояние; старый поддерживаемый сейв загружается предсказуемо; неподдерживаемый не интерпретируется молча; проверен реальный restore из резервной копии, а не только её создание.

### Е. Общие решения клиента, а не большой переписанный UI — P1

**Предлагается.** Продолжать существующий путь `decisions/`: чистое решение и тест общие, отрисовка остаётся у экрана, тексты — в `localization/`. Переносить цепочку целиком, когда она нужна обоим клиентам: намерение, строитель сообщения, трактовка отказа, взаимодействие с UI. [S9]

**Почему.** Извлечение функции из большого `main.ts` внутрь того же прототипа уменьшает файл, но не обязательно приближает переиспользование. Второй рукописный payload может расходиться с протоколом. Новый фреймворк или массовое переименование `prototype/` эту проблему не решат.

**Цена.** Нужно определить владельца решения и не занести в чистый слой браузерные зависимости. **Готово, когда:** оба нужных клиента используют одну функцию; тесты переехали вместе с ней; нет импорта прототипа из общего решения; пользовательский сценарий сохранён в собранном UI.

### Ж. Самостоятельные артефакты Sector Zero — P1, блокер отдельного магазинного релиза

**Проблема.** Проверенный Android-упаковщик допускает только `dev`/`player`. Это не доказательство полного отсутствия других мобильных работ, но этот конкретный путь ещё не выражает самостоятельную сборку Sector Zero. [S10]

**Предлагается.** Отделить конфигурацию продукта от адаптера площадки и окружения сборки. Для Android добавить явный путь упаковки нужного продукта; не подменять его основным клиентом с визуально скрытой регистрацией. Проверять фактический артефакт на ненужные экраны, сетевые обращения и зависимости.

**Почему.** Один общий движок не обязывает кампанию требовать сервер основной игры. Сбой входа или SDK не должен блокировать доступный гостевой PvE. Аккаунт магазина, идентичность профиля и облачное сохранение — разные контракты. Подключение оплаты не создаёт перенос прогресса автоматически. [S8], [S11]

**Цена.** Матрица продукт × площадка × окружение; её следует ограничить реально поддерживаемыми сочетаниями. **Готово, когда:** релизный артефакт стартует, сохраняет и восстанавливает кампанию, переживает закрытие приложения, корректно обрабатывает недоступный SDK и не требует чужой регистрации. Покупки и восстановление оплаченного проверяются отдельно, если включены. Актуальные требования магазина сверяются в задаче релиза, а не считаются доказанными этим документом.

### З. Проверки видимости и авторитета по всем каналам — P1

**Предлагается.** Расширять существующие тесты адресно, не создавать туман войны заново. Для новых механик проверять чужого владельца, устаревшее состояние, повтор, потерю обзора, реконнект и скрытые поля в событиях/ошибках. Отдельно проверять доверенные внутренние приказы: «внутренний» не означает право нарушать правила мира. [S2], [S14]

**Почему.** Добавленная модификация флота или отчёт боя способны обойти прежнюю фильтрацию даже при корректной основной карте. **Цена:** больше отрицательных и межслойных тестов. **Готово, когда:** запрещённый приказ не меняет мир, недоступная информация не появляется ни в одном проверяемом сетевом канале, разрешённый союзный обзор сохраняет нужные данные.

### И. Эксплуатационные доказательства и релизный гейт — P1

**Предлагается.** Связать метрики из §9 с действиями оператора: commit не проходит — новые успехи не подтверждаются; событие застряло — есть диагностика; резервная копия — регулярно проверяется восстановлением. Токены, пароли и полные чувствительные payload не логируются.

В прочитанном CI общий гейт запускается с PostgreSQL, но browser smoke, platform archive smoke и perf помечены **non-blocking**. Поэтому зелёный итог сам по себе не доказывает успех каждого из этих шагов. [S13]

**Почему.** Тест исходной библиотеки не поймает все ошибки упаковки. Предложение — сделать надёжно воспроизводимые проверки целевого релиза обязательными именно для соответствующего артефакта. Не менять все informational-проверки на блокирующие одним движением: сначала исключить проблемы среды и зафиксировать ожидаемое поведение.

**Цена.** Нужны стабильные браузерные/мобильные прогоны и обслуживание тестовых данных. **Готово, когда:** видны результат каждой обязательной проверки и точный SHA/артефакт; restore и отказ БД реально испытаны; заявленные RPO/RTO основаны на измерении, а не на наличии Docker restart policy.

### К. Масштабирование только после модели владельца матча — P2

**Предлагается.** При реальной необходимости нескольких процессов сначала определить, кто единственный имеет право менять конкретный матч. Потребуются маршрутизация, ревизии и механизм fencing: старый владелец после потери полномочия больше не может записать результат. Затем выбирать механизм распределённых пробуждений и доставки событий.

**Почему.** Очередь «разбудить матч» не заменяет правила владения его состоянием. pg-boss может стать способом пробуждения в PostgreSQL; Redis — дополнительным инструментом при доказанной потребности. Ни один из них сам не создаёт атомарность игрового приказа. Текущий ADR оставляет такое усложнение дальнейшему этапу. [S6]

**Цена.** Сетевые разделения, повторная доставка и смена владельца требуют отдельных тестов. **Готово, когда:** два процесса не фиксируют конфликтующие изменения одного матча; повторное пробуждение безопасно; недоступность владельца обнаруживается; измерения действительно показывают выигрыш. До этого несколько реплик — не гарантированная отказоустойчивость.

## 12. Проверяемые критерии готовности

Матрица ниже — **задание для проверки/дополнения покрытия**, а не список тестов, которые якобы уже успешно выполнены этой сверкой.

| Сценарий | Что должно быть доказано | Где проверять |
| --- | --- | --- |
| Два одинаковых запроса | Одна фиксация эффекта и тот же подтверждённый результат | Комната + PostgreSQL |
| Один ID, разное содержимое | Второй эффект не применяется | Гейт / хранилище квитанций |
| Сбой между снимком и квитанцией | Нет половинчатой операции после восстановления | Интеграционный тест с внедрением сбоя |
| Commit прошёл, ответ потерян | Retry восстанавливает результат без повторного эффекта | Сеть + рестарт + БД |
| Два конкурентных изменения мира | Порядок согласован, устаревшая ревизия отклонена | Комната / стор |
| Публичный профиль без БД | Нет старта с ложной долговечностью | Реальный серверный вход |
| Перезапуск во время движения/боя/стройки | Выполняется утверждённая политика времени | Хост + сохраняемое состояние |
| Старый сейв после обновления | Совместимая загрузка/миграция либо безопасный отказ | Фикстуры версий + сборка |
| Игрок потерял обзор | Нет утечек через дельты, события, ошибки, диагностику | Два клиента с разной видимостью |
| Собранный контейнер | Исполняет те же проверенные политики, что ожидаются от хоста | Docker-артефакт |
| Sector Zero без сервера основной игры | Доступный гостевой PvE не блокируется чужим логином | Целевая продуктовая сборка |
| Android закрыт и открыт заново | Прогресс корректно восстанавливается | Установленный целевой артефакт |
| SDK отказал / исход покупки неизвестен | Нет краша гостевой игры и ложной выдачи ценности | Адаптер + продуктовый сценарий |
| Восстановление резервной копии | Проверены данные и измерено время возврата | Изолированный restore-стенд |

### Что проверено при подготовке этой редакции

Прочитаны выбранные исходники/конфигурации и документы из §13 на указанном SHA. Сопоставлены точки запуска, выбор хранилища, callback записи, политика времени, упаковщик Android и границы продуктов. Выводы о рисках не выдаются за результаты fault-injection.

**Полный `pnpm run check` и репозиторный `docs-check` локально не выполнены:** клонирование рабочей копии заблокировано DNS среды (`Could not resolve host: github.com`), а зависимостей проекта в ней нет. Чтение и публикация через GitHub-коннектор доступны. Статус CI определяется отдельно в PR; этот текст не объявляет его зелёным заранее.

Обновляется существующий `docs/architecture.md`, на который уже ведут живые документы. H1 и первая содержательная строка сохранены для неизменности метаданных `docs/index.md`; формальные кирпичи и их статусы не добавляются, генераторы/индексы вручную не правятся. `docs/state.md` и счётчики тестов не меняются: это документационная работа без изменения поведения.

## Сводка ключевых принципов

Сохраняем общее ядро и самостоятельность продуктов. Укрепляем фактический серверный путь, атомарность сохранения, политику времени и совместимость версий. Используем уже существующие общие решения вместо новых копий. Проверяем поставляемые артефакты и восстановление, а не объявляем готовность по схеме. Усложняем инфраструктуру только там, где необходимость подтверждена измерением.
