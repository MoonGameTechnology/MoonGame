# Журнал безопасности и расследование на одном VPS

Локальный этап [security operations](../../docs/security-operations-roadmap.md).
[Исследование и решения](../../docs/research/2026-10-30-security-logging.md)
объясняют выбор; независимое хранилище и SIEM остаются следующим этапом.
Новых публичных портов, игровых полномочий и внешних получателей уведомлений нет.

## Что сохраняется

`PROD=1/true` или `SECURITY_AUDIT=1` включает `SecurityAudit` в обоих хостах.
HTTP-отказы 400/401/403/404/409/413/429/5xx, успешные auth/mutation, WS admission,
нарушения границы команд и lifecycle пишутся в постоянный игровой JSONL-том.
Успешные health/ready и частые telemetry/activity pulse не засоряют этот поток.
Обычные отказы игровых правил не считаются нарушениями безопасности.

Запись v2 содержит `at`, `service`, `version`, `run` UUID, `sequence`, событие,
результат `E_*`, шаблон маршрута и разрешённую корреляцию. HTTP получает новый
серверный `X-Request-Id`; входящий клиентский ID не считается доверенным.
`actor` привязывается после проверки аккаунта; `target` — HMAC нормализованного
введённого логина, `source` — меняющийся по UTC-дням HMAC сетевого адреса.
Ключ — существующий защищённый `ANALYTICS_SALT` длиной от 32 символов.
Без постоянного ключа эти идентификаторы не сохраняются и появляется сигнал
`correlation-missing`. Матч также представлен HMAC. Пароли, JWT, email, исходные
accountId/IP/ники, URL/query, заголовки, payload и stack traces не входят в схему.
Псевдонимы остаются данными ограниченного доступа, а не доказанно анонимными.

Caddy сохраняет отдельный поток: время, HTTP status, размер/длительность и фиксированные
классы метода/маршрута. Весь `request`, response headers, URI, IP и произвольная ошибка
удаляются до записи. Отказ на `/metrics` виден даже без обращения к Game.
Edge-поток не позволяет восстановить IP, исходный URL или конкретного посетителя.
`edge_up` проверяет наличие/чтение файлов, не полноту всех сетевых обращений.

## Установка после подписанной доставки

Для штатного VPS с `/var/lib/moongame`, локальным rootful Docker и уже установленным
host observer выполнить от root:

```bash
node /var/lib/moongame/current/deploy/security/install.mjs
systemctl status moongame-security-monitor.timer --no-pager
moongame security status
```

Installer работает под deployment/erasure lock. Он сверяет revision пары Game/Caddy,
проверяет конфигурацию Caddy, добавляет import из подписанного Caddy image, проверяет
public health/ready и закрытый `/metrics`. При сбое edge-проверки возвращает прежний
Caddyfile. Остальные host-шаги повторяемы; при ошибке проверять результат, а не считать
активный timer доказательством полной установки. Секреты не выводятся.

Создаются root0600 `/etc/moongame/security-monitor.env` с несекретными путями,
root0700 `/var/lib/moongame-security` и service/timer. Код observer открывается его
прежнему UID через read-only bind из signed release; права `/var/lib/moongame` не
расширяются. Будущая успешная автодоставка обновляет привязку observer.
Worker каждый раз запускает код из `current`; unit/config меняются отдельной установкой.

Сборщик запускается через 15 секунд после окончания предыдущего запуска: максимум
96MiB RAM, 15% CPU, 32 tasks, 20 секунд, Node heap 48MiB. Network/Docker/DB/response API
не используются. Это доверенное root-задание control plane: systemd ограничения
уменьшают область случайной ошибки, но не создают независимость от root игрового хоста.
Прогоны, deployment, offline erasure и операторский поиск сериализованы общим `flock`;
при занятом lock сбор пропускается, долгое отсутствие свежести видно отдельно.

## Лимиты хранения и потери

| Поток | Бюджет | Срок |
| --- | --- | --- |
| `security-*.jsonl`, события | 4MiB/UTC-день | 14 UTC-дат, включая текущую |
| `security-auth-*.jsonl`, успешные auth/lifecycle/локальные alerts | 1MiB/день | 14 UTC-дат |
| `security-status-*.jsonl`, heartbeat раз в минуту | 2MiB/день | 14 UTC-дат |
| `security-incidents-*.jsonl` | 1MiB/день | 14 UTC-дат |
| Caddy `access.log` | 1MiB + 4 rolled files, без gzip | Ротация каждые 24h/по размеру, до 336h |
| Операторские `access-*.jsonl` | около 1MiB/день | 14 UTC-дат |

Суммарный верхний порядок — около 140MiB без прежних игровых/клиентских журналов.
Это лимиты приложения, не filesystem quota. Очистка происходит при очередной записи/
сборе/поиске, а не отдельным таймером выключенного хоста. Файлы 0600, каталоги 0700.
У каждого producer stream очередь 1024/512KiB; контекстные события ограничены 64/sec.
Heartbeat и приоритетный auth имеют отдельные файловые бюджеты, но не гарантию доставки
при переполнении общей частоты. `sampled/failed/dropped` отражают неполноту.
`datasync` выполняется для принятых batches; аварийный хвост до flush может потеряться.
Запись аудита **не атомарна с бизнес-транзакцией**.

Detector читает bounded строки/файлы, до 16384 событий и 4096 групп за окно 10min;
сохраняет не больше 128 обычных новых кандидатов за сбор плюс служебные случаи.
Обрезанный/повреждённый поток, повторный `run/sequence` с другим содержимым,
переполнение и отсутствие producer heartbeat дают отдельные сигналы.
Приёмка на отдельном fixture из 15000 событий (~4MiB): 3.482s, CPU527ms,
peak33.4MiB в настоящем systemd96MiB/15%CPU. Это не длительный production SLO.

## Правила и панель

| Правило | Начальный порог/смысл |
| --- | --- |
| `auth-burst`, `auth-slow` | Один source: 20 отказов/min либо 15/10min |
| `success-after-failures` | Успешный вход после ≥5 отказов того же source/target за 10min |
| `input-probes` | 30 HTTP-отказов/source/min |
| `mixed-script-probes` | 3 разных target с Latin+Cyrillic при регистрации/source/5min |
| `action-boundary`, `rate-limit`, `server-errors` | 5 нарушений команд/source/min,10 rate-limit/source/min,5 HTTP5xx/min |
| `edge-probes` | 5 отказов на operator routes/min; без атрибуции посетителя |
| `restart-burst` | 4 разных run одной версии/10min; разные версии релизов разделены |
| `audit-loss`, `audit-stale`, `correlation-missing` | Потери/семплирование; heartbeat старше 180s; нет постоянного ключа |
| `detector-capacity`, `maintenance-stuck` | Неполный вход/лимиты; erasure barrier и последний успех старше 5min |

Это подозрения, а не доказанные атаки. NAT, повторные ошибки пользователя,
разрешённый пентест и плановое обслуживание могут давать похожие последовательности.
Incidents содержат evidence references и время обнаружения `observedAt`.
Повторный сбор не дублирует сохранённый case ID; count — значение при обнаружении,
не непрерывно обновляемый счётчик всех попыток. История и активные случаи разделены.
Автоматических банов, рестартов и финансовых действий нет.

`security.prom` содержит только числа и фиксированные rule labels. Host observer
проецирует процессные счётчики из закрытого `/metrics`; identities не становятся labels.
Grafana экран `moongame-security` связан с обзором, Prometheus загружает 8 rules из Git.
Отсутствие данных и устаревание имеют отдельные проверки. Внешних receivers нет:
текущий канал — панель мониторинга. Правила проверяются реальным promtool в CI.

Installer не запускает полный Grafana/Prometheus/Loki/Alloy stack. Его запуск — по
[существующему runbook](../observability/README.md), только при ≥12GiB free,
активном guard и достаточной RAM. Резерв не снижать. При нехватке ресурсов сохраняются
локальный журнал/CLI/worker, тяжёлый поиск и отдельная площадка остаются в роадмапе.
На одном VPS недоступность всего хоста не может быть обнаружена его собственным экраном.

## Расследование

```bash
moongame security status
moongame security incidents --limit 50
moongame security events --request 11111111-2222-4333-8444-555555555555 --limit 100
moongame security incidents --rule auth-slow --from 2026-10-30T00:00:00Z --to 2026-10-30T01:00:00Z
journalctl -u moongame-security-monitor.service --since '30 minutes ago' --no-pager
```

UUID/период заменить на время и ID события. Доступны также `--actor`16hex,
`--target`24hex, `--source`UTC-day:24hex. По умолчанию последние 24h, максимум 14дней,
`--limit`1–1000. Вывод — повторно проверенная проекция, не сырые строки.
`matched/truncated/invalidRecords` не позволяют принять ограниченную выборку за полную.
Root-чтения сначала аудируются: UID, имена фильтров и число строк, без их значений.
Общий UID0 не даёт персональной атрибуции сотрудников; прямой root доступ к файлам
этим CLI не контролируется.

Сначала проверить свежесть и потери, затем связать source/target/request/actor,
сверить временное окно с релизами, обслуживанием и разрешёнными тестами. HMAC source
не равен человеку; по нему нельзя восстановить исходный IP. HTTP outcome не доказывает
commit/откат бизнес-операции: для этого нужны доменные receipts/состояние.
Доказательства дольше TTL требуют отдельного закрытого дела с основанием, ответственным
и сроком. Живые логи не прикладываются к публичному PR.

Инциденты лежат в том же приватном JSONL inventory, что и producer. Offline erasure
удаляет строки по actor и HMAC target с учётом истории ключей. Это предотвращает
забытые производные копии, но Game/root могут изменить локальную историю.
Защита при захвате хоста, персональные права, независимый append-only sink,
транзакционный audit/outbox и долгие расследования требуют следующих SE-8 этапов.
