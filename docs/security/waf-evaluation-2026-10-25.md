# Coraza WAF: проверка перед включением, 2026-10-25

## Решение и область проверки

Coraza подходит как дополнительный HTTP-фильтр перед игровым API. В рабочем Caddy
WAF **ещё не включён**. Этот PR сохраняет исследование, тестовый патч и изолированный
стенд; production Dockerfile, compose, Caddyfile и автодеплой не меняются.

Проверены публичные advisories Coraza (14), coraza-caddy (0 опубликованных), OWASP CRS
(7), история исправлений CRS и проблемы интеграции Caddy. Это перечень опубликованных
проблем на дату проверки, **не обещание найти неизвестные обходы и не свидетельство
реальных взломов нашего сервера**. Нулевое число advisories соединителя не означает,
что у него нет ошибок: две интеграционные ошибки воспроизведены ниже.

Исходники и выпуски: [Coraza 3.8.1](https://github.com/corazawaf/coraza/releases/tag/v3.8.1),
[соединитель 2.6.2](https://github.com/corazawaf/coraza-caddy/releases/tag/v2.6.2),
[CRS 4.30.0 / LTS 4.25.2](https://coreruleset.org/20261002/crs-versions-4.30.0-and-4.25.2-lts-released/).
Стенд: Caddy 2.11.7, Go 1.27.3, Coraza 3.8.1, соединитель 2.6.2 с локальным патчем,
**внешний CRS 4.30.0**. У соединителя 2.6.2 встроен CRS **4.25.0**: один лишь свежий
номер соединителя не закрывает свежие обходы правил; `load_owasp_crs` здесь не используется.
Go-модули x/net 0.60.0 и chi 5.4.0 сохранены на уровне нашей рабочей сборки.

## Найдено непосредственно при интеграции

1. **Утечка чувствительных параметров в журнал.** Штатный `newErrorCb` вызывает
   `MatchedRule.ErrorLog()`: query, matched data и свободный текст попадают в `msg`,
   даже при `SecAuditEngine Off`. Фильтр Caddy, удаляющий `uri`, это не очищает.
   Синтетический token появился в исходном журнале. Патч оставляет постоянное `waf.rule`,
   rule ID, severity, generated transaction ID и признак disruptive; из второй записи
   отказа убраны URI/hostname. Canary после исправления отсутствует. `tx_id_req_header`
   не задаётся: клиент не выбирает ID. Это исправление тестовой сборки, не поставленный
   upstream-патч и не разрешение включить debug/audit с сырыми данными.
2. **Превышение размера тела давало 500 вместо 413.** `request_body max_size` стоит до WAF,
   но соединитель терял `http.MaxBytesError`, форматируя его через `%s`. `%w` сохраняет
   тип ошибки; `errors.As` выбирает 413, наружу выходит общий `E_WAF_REQUEST`.
   Запрос 1 MiB + 1 не доходит до backend. У других ошибок остаётся отказ 500.
3. **Reload включённого файла не гарантирует новые правила.** Ключ общего пула WAF
   содержит текст директив/пути Include, но не содержимое файлов. Изменение Include
   с прежней inline revision оставило старое разрешающее поведение (200). Изменение
   `SecComponentSignature` дало ожидаемый 403. Поддерживаемый путь: неизменяемые правила
   внутри версии образа и пересоздание процесса; для reload — изменение inline revision
   и обязательный контрольный запрос. Одного `reload --force` недостаточно.
4. **PL1 пропускает короткую команду в пути.** Пример с `;id` проходит PL1, отвергается
   на PL3 правилом 932350. Это подтверждённая разница покрытия, не доказательство RCE
   в нашей игре. Более высокий PL требует проверки ложных срабатываний.

Патч и стенд находятся в [deploy/caddy/waf-evaluation](../../deploy/caddy/waf-evaluation/README.md).
Исходный production Dockerfile в этом PR не использует патч.

## Предлагаемая схема и правила

```text
Браузер / Android
  → HTTPS (HTTP/1.1, HTTP/2, HTTP/3) :443
  → Caddy: размеры, таймауты, затем Coraza + внешний CRS
  → HTTPS с проверкой CA и имени сервера
  → API / проверка аккаунта / проверка команд
  → PostgreSQL по TLS с проверкой сертификата

WSS: фильтр проверяет handshake → после 101 игровые сообщения проверяет приложение
```

WAF видит расшифрованный HTTP внутри Caddy; повторное шифрование до сервиса остаётся.
Новых публичных портов WAF не требует. Порт 2019 не публикуется. Публичный 80 остаётся
для действующей HTTPS/ACME-схемы. Сетевые правила должны по-прежнему исключать обход
прокси прямым доступом к API/БД. Внутренние сервисные вызовы, не проходящие Caddy,
этим WAF не проверяются.

Предлагаемый старт: **DetectionOnly**, PL1, inbound anomaly threshold 5; после
наблюдения легитимного трафика — `On`. DetectionOnly **не блокирует атаки**, что отдельно
проверено. Жёсткий внешний лимит тела 1 MiB, заголовки 16 KiB, read_header 5 s,
read_body 10 s, idle 30 s; внутренние endpoint limits остаются строже. JSON depth 32,
аргументы 1000 плюс отказ по флагам recommended config. Значения — начальная политика,
а не доказанная ёмкость сервиса.

Инвентаризация текущего API: GET/HEAD/POST/OPTIONS; PUT/PATCH/DELETE сейчас не используются
и отвергаются. Multipart/XML игре не нужны: при активации стоит закрыть их типы целиком
для JSON-only API, сохранив только явно нужные маршруты. В тестовом общем профиле они
разбираются, чтобы проверить классы старых обходов. Ответы не сканируются. Исключения
допустимы адресно (маршрут + поле + правило), после воспроизведения ложного срабатывания;
глобального исключения `Authorization`, password или всех JSON-полей здесь не добавлено.

## Что остаётся открытым

- Содержимое WebSocket/WSS после upgrade: и SQLi/XSS-похожая строка дошла до echo-fixture.
  В игре нужны schema validation, auth/authz, origin check, payload/rate limits,
  последовательность и идемпотентность команд. См.
  [OWASP WebSocket Security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html).
- Ошибки владения объектами, игровых прав, экономики, наград, повторных запросов;
  валидный по форме запрос может нарушать права. WAF этого не доказывает.
- Компрометация SSH/пользователя VPS, ядра, контейнера, GitHub/CI, ключей и зависимостей;
  прямой внутренний доступ, outbound SSRF и утечки через легитимные ответы.
- Кража действительной сессии, подбор паролей, credential stuffing: нужны отдельные
  ограничения входа, отзыв сессий и защита аккаунтов. CRS не является rate limiter.
- Объёмный DDoS на канал/TLS/QUIC/HTTP-parser до WAF. Сам WAF расходует CPU и память,
  поэтому внешняя фильтрация и ресурсные бюджеты остаются нужны.
- Неизвестные обходы, разница нормализации с приложением и сигнатуры более высоких PL;
  false positives возможны и на PL1. В audit нет сырых тел: анализировать такие случаи
  нужно по безопасному synthetic reproducer и ID правила.

## Результат обязательных тестов

Первые сетевые проверки исходной сборки выявили утечку token и 500 на превышение тела;
отдельно воспроизведены пропуск короткой команды на PL1 и устаревшая политика после
file-only reload. После локального патча и повторной подготовки стенда прошли **54 сетевые проверки**; проверки границ сознательно
подтверждают пропуск, не изображают его блокировкой. Точные статусы, достижение backend
и измерения сохранены в [очищенном результате](../../deploy/caddy/waf-evaluation/results-2026-10-25.json).

Браузер на копии текущего production game image прошёл **10 проверок**: загрузку, регистрацию,
парольный вход и отказ неверного пароля, получение регистрационной награды,
аутентифицированный WSS join, настоящий приказ исследования после 12 s ожидания,
повторный вход после перезагрузки страницы. Ошибок JavaScript не было. Тестовая БД —
память, настоящие пользователи/пароли/сохранения/база не затрагивались.

Upstream `go test ./...` соединителя с патчем прошёл. У движка прошли bodyprocessors,
transformations, corazawaf, auditlog. Два permission-теста auditlog сначала упали,
потому что root мог создать `/unexisting.log`; на read-only rootfs их ожидаемая
ошибка воспроизвелась и весь набор прошёл. Один upstream тест соединителя ожидал
сырой URI в журнале: он обновлён под новый контракт отсутствия URI, с canary-проверкой.
Ни один из этих тестов не отключён.

Нагрузка ограничена 200 маленькими запросами, concurrency 4, edge 0.5 CPU / 512 MiB.
Измеренные p50/p95 находятся в JSON; это короткая совместимость под ограничением CPU,
а не нагрузочная ёмкость production или доказательство защиты от DDoS. OOM и рестартов
в завершённых сетевых прогонах не было. Серия из нескольких reload не заменяет soak.

## Обязательные условия перед production activation

1. Включить модуль/правила в отдельно сканируемый и подписываемый образ; повторить
   приёмку на его точном digest. Текущий PR этого не делает.
2. Защитить rollback: предыдущий production Caddy ещё не знает `coraza_waf`. Нельзя
   оставить новый общий Caddyfile и откатить бинарь без модуля. Сначала подготовить
   совместимую пару образов либо атомарный откат конфигурации вместе с образом.
3. Прогнать текущую игру и Android/WebView, загрузки и все JSON endpoint classes через
   итоговый конфиг; интегрировать повторяемые probes в image CI. Настоящий Android,
   PostgreSQL-поток, облачные сохранения и все механики игры этим аудитом не покрыты.
4. Начать DetectionOnly, проверить реальные ложные срабатывания и расход ресурсов,
   обновление правил и rollback. Только потом включать блокировку и повторять probes.
5. Подписаться на обновления Coraza/соединителя/CRS; обновлять все три, а не один модуль.
   Уязвимости WAF не становятся исправленными только из-за его установки.
