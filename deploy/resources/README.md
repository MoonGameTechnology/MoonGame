# Ограничения ресурсов VPS

Профиль рассчитан на существующий Compose `deploy` и необязательный bot stage.
Основной сервер и PostgreSQL получают по 1 CPU, Caddy — 0.5 CPU; stage сохраняет
0.75/0.5 CPU. Worker удаления аккаунтов ограничен 0.5 CPU. Пределы памяти и процессов
остаются в Compose. Это потолки отдельных контейнеров, а не выделенные физические ядра.

## Логи

`DailyJsonl` ограничивает очередь 4 MiB и дневной файл 16 MiB на каждый префикс.
Сохраняются только полные JSONL-записи; превышение учитывается в `stats().dropped`.
Размер существующего файла проверяется перед каждым append, поэтому перезапуск
не обнуляет бюджет. Старые большие файлы не обрезаются. Запись через symlink,
hardlink или специальный файл отклоняется.

Времена вне текущего окна хранения не создают новые файлы. При штатном удалении
старых файлов два журнала `match`/`client` занимают не больше 992 MiB
(31 UTC-день × 16 MiB × 2). Исторические файлы других форматов в этот расчёт не входят.
Docker stderr/stdout уже ротируются отдельно; journald получает предел 1 GiB,
резерв 6 GiB и срок хранения 14 дней.

## Диск и остановка при переполнении

`guard.py` опрашивает локальный Docker, считает занятые блоки томов через `du -sx`
и свободные байты/inode через `statvfs`. Он не читает содержимое игровых данных,
не следует symlink внутри томов и не удаляет данные.

| Том                            | Аварийный предел | Останавливаются               |
| ------------------------------ | ---------------- | ----------------------------- |
| `deploy_void-pgdata`           | 8 GiB            | основной сервер, затем его БД |
| `deploy_void-logs`             | 1.25 GiB         | основной сервер               |
| `moongame-bots-stage-postgres` | 2 GiB            | stage, затем его БД           |
| `deploy_caddy-data`            | 3 GiB            | Caddy                         |
| `deploy_caddy-config`          | 256 MiB          | Caddy                         |

В `caddy-data` также лежат APK: два канала по восемь версий, до 128 MiB на APK.
Их штатную ротацию выполняет publisher; отдельный маленький лимит только под
сертификаты к этому тому неприменим.

80% бюджета даёт предупреждение. Свободное место ≤6 GiB или ≤100000 inode,
а также ошибка измерения требуют остановки известных игровых, тестовых и
monitoring-контейнеров. Сначала завершаются приложения, затем БД; таймаут Docker
на остановку — 60 секунд. Неизвестные контейнеры и SSH не затрагиваются.

Таймер срабатывает через 30 секунд после предыдущей проверки. Он разделяет lock
с автодеплоем и пропускает проверку, пока тот занят. **Это аварийная защита с интервалом
реакции, не жёсткая файловая квота.** Запись другим процессом или быстрый рост между
проверками могут превысить порог. На ext4 без project quota установка не меняет
файловую систему и не переносит данные.

Перед остановкой атомарно сохраняется `/var/lib/moongame/resource-pressure.json`.
Маркер блокирует production preflight и запускающие команды stage wrapper; systemd
дополнительно проверяет состояние перед Game, автодеплоем, erasure и мониторингом.
Автодеплой с установленным `resource-guard.version` отклоняет старые контроллеры без
`deploy/resources/version=1` до изменения работающего стека. Исчезновение нагрузки
не снимает блокировку автоматически. Никакой автоматической очистки БД или журналов нет.

## Установка на существующий хост

Нужны root, Python 3, GNU `du`, systemd и локальный Docker socket. Исходники и их
родительские каталоги должны принадлежать root и не разрешать запись группе/остальным.
Перед установкой проверьте бюджеты в `guard.py` относительно размера диска и данных.

```bash
sudo bash deploy/resources/install.sh
sudo systemctl status moongame-resource-guard.timer
sudo cat /var/lib/moongame-resource-guard/status.json
```

Установщик проверяет диск до включения защиты, атомарно копирует root-контроллер,
ставит timer/drop-ins и ограничение journald. Игра, Docker и PostgreSQL не перезапускаются;
перезапускается только journald. CPU из Compose применяется при следующем штатном
создании контейнеров. На работающем хосте можно применить те же значения без рестарта:

```bash
sudo docker update --cpus 1 deploy-server-1 deploy-postgres-1
sudo docker update --cpus 0.5 deploy-caddy-1
```

Если используется защищённый `COMPOSE_EXTRA_FILE`, сохраните те же `cpus` в нём,
пока новый подписанный образ с этими настройками не прошёл штатный автодеплой.
Установку guard следует совмещать с контроллером, уже проверяющим его version marker;
старый установленный `autoupdate.sh` нужно обновить до включения marker.

## Восстановление

Прочитайте marker/status и `journalctl -u moongame-resource-guard.service`.
Устраните причину роста или расширьте диск; исторические данные удаляются только
по принятой оператором политике. Для снятия блокировки требуется уровень 0:
не менее 8 GiB свободно, не менее 200000 inode и каждый том ниже 80% бюджета.

```bash
sudo python3 /opt/moongame-ops/deploy/resources/guard.py resume
```

`resume` не запускает контейнеры. После снятия marker обычный production autodeploy
снова может поднять игру; stage запускается своим операторским wrapper.
Остановленный мониторинг guard сам не включает. Отключение таймера не снимает marker.
Проверяющий режим `guard.py check` не меняет ни файлы, ни контейнеры.
