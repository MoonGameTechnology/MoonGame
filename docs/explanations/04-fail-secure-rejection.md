# 04. Fail-secure: ошибки → rejection, не silent pass

**Дата:** 2026-08-18
**Статус:** accepted

## Контекст

Void Dominion — real-time MMO с server-authority. Клиент отправляет намерение;
сервер валидирует и применяет. Ошибки неизбежны: невалидный payload, недостаточно
ресурсов, нет прав, цель не существует, действие заблокировано гейтом.

**Проблема:** если при ошибке ядро «молча проходит» (возвращает `ok: true` без
изменений или игнорирует), клиент не знает, что действие не применилось. Игрок
думает, что приказ ушёл — а он тихо исчез. Хуже: злоумышленник может
перебирать варианты и по ответу (применилось/нет) выводить скрытое состояние
(пример: `E_NO_TARGET` vs `E_NOT_HOSTILE` позволял подтверждать существование
флота — `docs/security-a06.md`).

**Альтернативы:**

- **A.** Любая ошибка → rejection `{ ok: false, code }` со стабильным кодом.
  Никаких internal details (стек, имена полей) — только код. Unexpected throw →
  `E_INTERNAL`.
- **B.** Молча игнорировать невалидные действия — проще, но игрок не понимает,
  что произошло, и security-утечки.
- **C.** Возвращать full error message — информативно, но утекает внутренности
  (имена таблиц, структура состояния) — помогает злоумышленнику.

## Решение

**Альтернатива A.** Fail-secure (OWASP A10):

- `applyAction` возвращает `{ ok: true, state, events }` или `{ ok: false, code }`.
- `code` — стабильный `E_*` (например, `E_BAD_PAYLOAD`, `E_FORBIDDEN`,
  `E_NO_PLANET`, `E_NOT_HOSTILE`, `E_INTERNAL`). Полный список —
  `packages/action-layer/src/errors.ts`.
- `h.reject(code)` — intended path в обработчиках модулей.
- Unexpected throw → `E_INTERNAL` (перехват в kernel, логируется на сервере,
  клиенту — только код).
- Internal details (стек, имена полей, структура) — только в серверных логах,
  не в ответе клиенту.
- Гейт (`@void/action-layer`) добавляет свои коды: envelope validation →
  payload schema → auth → idempotency → sequence — каждый этап со своими `E_*`.

**Ключевое:** коды стабильны — клиент может локализовать (`t('err.no-capacity')`)
и показать игроку, но не может вывести внутреннее состояние по коду.

## Последствия

**Плюсы:**
- Игрок всегда знает, что действие не применилось (не «тихо исчезло»).
- Security: коды не утекают внутренности (A10). Перебор вариантов не даёт
  информации, кроме «да/нет» — и то через стабильный код, не через разницу
  сообщений.
- Локализуемость: код → ключ → текст в `/localization`.
- Отладка: серверные логи содержат full details, клиенту — код.

**Цена:**
- Коды должны быть стабильными — смена кода ломает клиентскую логику/локализацию.
- Нужно вести реестр кодов (`errors.ts`) и не дублировать.
- Unexpected throw → `E_INTERNAL` — игрок видит «внутренняя ошибка», что хуже
  UX, чем конкретное сообщение. Но это safety net, не норма.

**Совместимость:** server-authority (инвариант #5 — гейт возвращает коды),
детерминизм (инвариант #1 — rejection детерминирован), локализация (коды →
ключи → текст).
