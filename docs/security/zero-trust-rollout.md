# Внедрение базовых мер Zero Trust

Этот документ описывает доступные механизмы и порядок их включения. Проверка исходников
и локальное учение не подтверждают конфигурацию работающего сервера.

## Что даёт эта версия

| Граница доверия | Механизм | Ограничение |
| --- | --- | --- |
| Игра → PostgreSQL | `DB_AUTO_MIGRATE=0`, `DB_REQUIRE_LEAST_PRIVILEGE=1`; DML вместо владельца схемы | На существующей установке нужно отдельно перенести права |
| Мигратор → схема | Отдельный `database-admin.mjs`, `SET LOCAL ROLE vd_schema`, одна транзакция и advisory lock | Миграции ещё не подключены к агенту автодеплоя |
| Выпуск → БД | Проверка отпечатка SQL-схемы перед запуском | При откате нужно выполнить мигратор соответствующего образа |
| Старые JWT → новый ключ | Прежний ключ принимается только для проверки до абсолютного срока | До 7 суток; экстренный отзыв требует убрать старый ключ |
| Клиенты → журнал | Структурные HTTP/WS/action/rate события, псевдоним матча | Это отдельный security-поток; прежние игровые логи не стали автоматически очищенными |
| Поток отказов → детект | Алерт при 20 отказах категории за 60 секунд | Локальный JSONL, без внешнего получателя и центрального хранилища |

Секрет-стор, OIDC/service identity, RLS, проверяемый TLS к БД, WAF и управление
SSH/firewall остаются отдельными задачами. Полный Zero Trust этим PR не закрывается.

## Роли БД и безопасный перенос

Поддерживается выделенная игровая БД. `provision` откажется работать, если в `public`
есть посторонние таблицы/представления. Перед первым переносом нужны проверенный
зашифрованный бэкап, окно обслуживания и выключенный `AUTODEPLOY=0`.

- `vd_schema`: постоянный владелец, `NOLOGIN`, без superuser/CREATEDB/CREATEROLE.
- `vd_runtime`: `NOLOGIN`, DML только на 29 игровых таблицах и доступ к их
  последовательностям; только SELECT на служебный отпечаток `vd_schema_revision`.
- `vd_app_<имя>`: сменяемая LOGIN-роль приложения, член только `vd_runtime`.
- `vd_migrate_<имя>`: отдельная LOGIN-роль мигратора, член `vd_schema`.

`CONNECT` выдаётся конкретным LOGIN-ролям; общие группы его не получают. Приложению
запрещены DDL, TRUNCATE, TEMP, владение таблицами и любые посторонние наследуемые роли,
включая `pg_read_server_files`. Пароли — 32 случайных байта в hex; SQL получает SCRAM
verifier. Verifier тоже чувствителен: не включайте логирование административных SQL.

Административные значения держите в файлах режима 0600 вне Git и образа. Для первого
шага файл `database-provision.env` содержит `DB_ADMIN_URL`, `DB_RUNTIME_USER`,
`DB_RUNTIME_PASSWORD`, `DB_MIGRATION_USER`, `DB_MIGRATION_PASSWORD`. Имена должны иметь
соответствующий префикс `vd_app_`/`vd_migrate_`, затем 1–40 строчных ASCII букв, цифр
или подчёркиваний. Для последующих миграций отдельный `migration.env` содержит только
`DB_MIGRATION_URL`. URL включает выбранную роль и её пароль.

Используйте **проверенный подписанный дайджест нового образа** (`VOID_IMAGE`), который
уже содержит эту реализацию. На действующем Compose-стеке PostgreSQL должен быть
доступен в `deploy_default`; на другой топологии задайте её сеть и адрес БД.

```bash
bash deploy/verify-image.sh "$VOID_IMAGE"
docker run --rm --read-only --cap-drop ALL --security-opt no-new-privileges \
  --memory 512m --pids-limit 64 --network deploy_default \
  --env-file /secure/database-provision.env "$VOID_IMAGE" \
  packages/server/dist/database-admin.mjs provision
```

`provision` атомарно создаёт/проверяет роли, переносит существующие игровые таблицы
постоянному владельцу, запускает схему и выдаёт права. Существующие данные сохраняются.
Для переноса суперпользователя `void` на DML нужен перезапуск игрового процесса; это
не обещание бесшовной первой миграции. После успеха в **runtime** `server.env` задайте:

```dotenv
DB_RUNTIME_USER=vd_app_v1
DB_RUNTIME_PASSWORD=<32 случайных байта в hex>
DB_AUTO_MIGRATE=0
DB_REQUIRE_LEAST_PRIVILEGE=1
```

Пароли/имена здесь должны совпадать с фактически созданными. Для запуска без Compose
аналогичные flags дополняют `DATABASE_URL` с DML-ролью. `POSTGRES_PASSWORD` остаётся
паролем первоначального администратора; его замена в env не меняет пароль в томе.
Административный файл **не** передаётся игровому контейнеру. `DB_ADMIN_URL` и
`DB_MIGRATION_URL` отсутствуют в его Compose environment.

Перед **каждым** последующим выпуском выполните мигратор целевого подписанного образа:

```bash
docker run --rm --read-only --cap-drop ALL --security-opt no-new-privileges \
  --memory 512m --pids-limit 64 --network deploy_default \
  --env-file /secure/migration.env "$VOID_IMAGE" \
  packages/server/dist/database-admin.mjs migrate
```

Только после успеха запускайте сервер этого образа и проверяйте `/health`, вход,
получение матчей и запись данных. Агент `autoupdate.sh` пока **не запускает** этот шаг:
не включайте unattended-обновления hardened-стека до интеграции миграционного job.
Несовпадающий отпечаток/права дают `E_DB_BOOT`, а не работу с неподготовленной схемой.
Откат: мигратор прежнего подписанного образа → прежний сервер → health и запись;
совместимость изменения схемы с откатом проверяется отдельно. Не откатывайте образы,
которые вообще не знают `DB_AUTO_MIGRATE=0` и DML-режим.

## Ротация БД без преждевременного отзыва

1. Создайте `vd_app_v2` с новым паролем через `provision`; роль мигратора и её пароль
   остаются прежними. Обе app-роли действуют параллельно.
2. Переключите runtime env на v2, перезапустите сервер, проверьте health и запись.
   Откат в этом окне — возврат v1, пока она ещё действует.
3. После окна отката отзовите v1 командой `retire`: отдельный файл содержит
   `DB_ADMIN_URL` и `DB_RETIRE_USER=vd_app_v1`; запуск аналогичен `provision` выше.
   Команда запрещает LOGIN и отзывает `vd_runtime`, поэтому даже уже открытые старые
   соединения теряют доступ к данным. Она не останавливает новый процесс.

Административные команды пишут `security.admin` с названием операции и результатом,
без URL, паролей и SQL-ошибок. Это журнал операций, а не аудит доступа к secret-store.

Restore использует существующие `deploy/backup.sh` / `restore.sh`. Дамп не сохраняет
владельцев/GRANT. После restore под администратором повторите `provision`, чтобы вернуть
владельца и DML-права, затем проверьте hardened-запуск. Runtime-роль не подходит для
restore. Офлайн-ключ `age` хранится отдельно от хоста.

## Ротация JWT

Для плановой смены одновременно задайте новый `AUTH_JWT_SECRET`, прежний
`AUTH_JWT_PREVIOUS_SECRET` и `AUTH_JWT_PREVIOUS_UNTIL` — **Unix-время в секундах**.
Прежний ключ должен иметь ≥32 символа и отличаться от текущего. Срок — не больше
7 суток вперёд от момента запуска; для join/reset обычно достаточно 15 минут,
для сессий по умолчанию нужны 7 суток. При `SESSION_TTL_SEC` больше 7 суток часть
прежних сессий потребует повторного входа. Отсутствующий/некорректный срок блокирует
конфигурацию с `E_AUTH_ROTATION_CONFIG`.

Все новые токены подписываются новым ключом. `alg`, issuer, audience, typ и exp
проверяются и при прежнем ключе. По достижении срока старые токены перестают работать
без перезапуска; после этого удалите прежний секрет из env. Для инцидента уберите его
сразу и перезапустите процесс. Уже открытые WebSocket не перепроверяют JWT каждый кадр;
экстренное прекращение их работы требует закрыть соединения/перезапустить сервер.
Процессный ключ не перечитывается из env на лету. Хранение и аудит чтений секретов
через KMS/SOPS этим механизмом не реализованы.

## Журнал и алерты

Под `PROD=1/true` аудит включён; для LAN/stage есть `SECURITY_AUDIT=1`.
Compose передаёт этот flag по умолчанию. Поток идёт в stderr и попадает в существующий
Docker `json-file` с ротацией `10m × 3`. Отдельного бесконечного security-файла нет.

События: успешные login/register/reset, HTTP 401/403/429, WS-отказы 401/403,
игровые ошибки/отказы и raw-flood. Метаданные ограничены типом, временем, кодом и
псевдонимом матча; нет login/IP/JWT/URL/тела запроса. Псевдоним меняется при перезапуске.
HTTP и WS отказы авторизации суммируются. По категориям auth/actions/rate — один
sample в секунду и один `security.alert` при 20 событиях в минутном окне; счётчик
учитывает и пропущенные samples. Пороги сигнализируют о необходимости расследования,
а не доказывают чит/атаку. Смена корпоративных прав и обычный игровой JSONL пока не
охвачены этим security-контуром.

Для внешней доставки настройте сборщик этого потока и получателя `security.alert`;
адрес/канал владельцем ещё не заданы. Отправка в Slack/email/webhook в учении не
выполнялась. Проверка: 20 отказов дают alert, collector его принимает, оператор
получает уведомление; журнал имеет согласованные сроки хранения и доступ.

## Проверка эффективной конфигурации хоста

```bash
node deploy/posture.mjs /var/lib/moongame/server.env
```

Коллектор только читает локальный Docker socket и metadata прав файла. Он не читает
содержимое env-файла, не выводит `docker inspect`, не подключается к внешним адресам,
не меняет настройки и не запускает код игровых контейнеров. Проверяет эффективные
env-flags, порты, контейнерные ограничения, digest pin, health и ротацию логов.
Код 1 означает high/critical находку либо незавершённую проверку. Medium-находки могут
оставаться и при коде 0: читайте весь JSON. Конфигурация guard не заменяет фактическую
проверку GRANT, digest pin не заменяет cosign, наличие TLS-env не проверяет сертификат.

SSH/firewall, валидность сертификата, подпись образа, права БД, свежесть зашифрованных
бэкапов, restore и доставка внешних алертов всегда отмечаются как `unverified` до
отдельной проверки. Для полного read-only аудита применяется репозиторный
`.claude/skills/infra-audit/SKILL.md` на конкретном хосте владельца.
