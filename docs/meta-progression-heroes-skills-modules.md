# Void Dominion — Hero, Skill & Module Meta Progression

> **Статус:** Draft / design concept. Документ фиксирует согласованное направление метапрогрессии, но не утверждает конкретные шансы, количества дубликатов, цены, редкости, количество звёзд или числовой баланс.

## Цель

Метапрогрессия должна создавать долгосрочное коллекционирование, разнообразие сборок, спрос на игровые ресурсы и естественную связь с аукционом, не превращая все предметы в одинаковые вертикальные шкалы характеристик.

Разные категории развиваются по-разному:

```text
Hero
  rarity → потенциальное количество skill slots
  stars  → открытие этих slots

Skill
  stars → развитие самого навыка
  upgrade → риск успеха/неудачи

Modules
  rarity → сила/уникальность механики
  crafting/drop → способ получения
  NO STARS
```

Главный принцип: **герои, навыки и модули должны создавать новые стратегические решения, а не только увеличивать числа.**

# 1. Прокачка героев

## 1.1. Редкость героя

Каждый герой имеет редкость.

Редкость определяет **максимальный потенциал сборки героя** — прежде всего максимальное количество доступных слотов под навыки.

Концептуальный пример (не финальный баланс):

| Редкость | Потенциальный максимум skill slots |
| --- | ---: |
| Common | 2 |
| Rare | 3 |
| Epic | 4 |
| Legendary | 5 |

Высокая редкость не обязана автоматически означать, что герой лучше во всех ситуациях. Низкая редкость может иметь сильную узкую специализацию, тогда как Legendary в первую очередь получает большую гибкость и более сложный build ceiling.

Иными словами, желаемое направление:

> **Rarity = potential / versatility ceiling.**

а не обязательное:

> `Legendary = всегда больше всех характеристик`.

## 1.2. Звёздность героя

Звёздность героя **не повышает его базовые характеристики**.

Она делает только одно:

> **открывает дополнительные слоты под навыки в пределах максимума, заданного редкостью героя.**

Пример для Legendary с максимумом 5 slots:

```text
★      → 1/5 slots
★★     → 2/5 slots
★★★    → 3/5 slots
★★★★   → 4/5 slots
★★★★★  → 5/5 slots
```

Конкретное число звёзд и соответствие slots определяется балансом позднее.

### Инвариант

Hero Stars **не должны** давать прямые бонусы вида:

- +HP;
- +damage;
- +economy;
- +speed;
- другие скрытые/явные статовые усиления только за сам факт повышения ★.

Ценность звёздности — **ширина и сложность сборки**.

## 1.3. Дубликаты героя

Для повышения звёздности требуется `N` дубликатов/фрагментов соответствующего героя.

Рабочая модель:

```text
получение героя
      ↓
повторное получение героя
      ↓
Hero Fragments / duplicate progress
      ↓
накопление N
      ↓
+★ Hero
      ↓
новый skill slot
```

Точные значения `N`, правила конвертации duplicate и наличие universal fragments определяются отдельным economy balancing.

## 1.4. Почему duplicate остаётся ценным

После первого получения героя повторное выпадение не превращается в бесполезный предмет. Duplicate является прямым прогрессом к следующему skill slot.

При этом желательно сохранить гарантированный игровой путь прогресса помимо чистого RNG (например universal fragments, mastery/event rewards или другие механики), чтобы случайность ускоряла развитие, но не была единственным способом раскрыть героя.

# 2. Прокачка навыков (Skills)

## 2.1. Skill — отдельный объект метапрогрессии

Получить навык один раз недостаточно для раскрытия его полного потенциала.

Навык имеет собственную звёздность и развивается независимо от звёздности героя.

Разделение:

```text
Hero Stars → сколько skills можно экипировать одновременно.
Skill Stars → насколько развит каждый конкретный skill.
```

## 2.2. Что даёт повышение Skill Stars

Повышение может:

- усиливать существующий эффект;
- улучшать параметры способности;
- открывать дополнительное свойство;
- добавлять новую синергию;
- менять способ применения способности.

Предпочтительно, чтобы часть уровней давала **качественное развитие**, а не только линейные проценты.

Концептуальный паттерн:

```text
★      → базовая способность
★★     → усиление
★★★    → дополнительное свойство
★★★★   → усиление / новая синергия
★★★★★  → развитая версия / дополнительная возможность
```

Это пример структуры, не утверждённая сетка.

## 2.3. Рискованное улучшение Skill

Попытка повысить звёздность навыка может быть **неудачной**.

Перед попыткой игрок тратит необходимые предметы/материалы.

### Успех

```text
Skill ★★
+ upgrade materials
      ↓ SUCCESS
Skill ★★★
```

### Неудача

```text
Skill ★★
+ upgrade materials
      ↓ FAILURE
Skill остаётся ★★
materials consumed
+ compensation resource
```

Ключевой принцип:

> **Failure may destroy resources. Failure must never destroy achieved progress.**

То есть при провале:

- навык не исчезает;
- звёздность не снижается;
- уже открытые свойства не теряются;
- расходные материалы могут сгореть;
- игрок получает компенсационный ресурс.

## 2.4. Компенсационный ресурс

Рабочее имя: `Residual Data` (название не утверждено).

Он выдаётся при неудачной прокачке навыка и превращает failure в частичный прогресс.

Потенциальные применения:

- компонент редкого крафта модулей;
- обмен на отдельные progression resources;
- накопление для deterministic/pity механик;
- специальные рецепты.

Важно: если ресурс является компенсацией конкретному unlucky-player, имеет смысл рассмотреть `account-bound` модель, чтобы он не превращался просто в ещё один свободно покупаемый товар.

## 2.5. Прозрачность RNG

Перед подтверждением попытки интерфейс должен ясно показывать:

- вероятность успеха;
- что будет потрачено;
- что произойдёт при failure;
- что skill не откатится;
- размер/правило компенсации, если оно детерминировано.

Не использовать deceptive presentation вроде визуального «почти успеха», если исход уже определён RNG.

## 2.6. Pity / guaranteed progression

Точная механика не утверждена, но система должна иметь защиту от экстремально плохой удачи.

Возможные варианты для дальнейшего рассмотрения:

- накопление compensation resource до гарантированного результата;
- upgrade stabilizer;
- рост шанса после серии failures;
- universal skill fragments.

RNG должен создавать эмоциональный момент, но не позволять одному игроку потерять месяцы прогресса исключительно из-за хвоста распределения случайности.

# 3. Модули — общая философия

## 3.1. У модулей НЕТ звёздности

Это принципиальное отличие от героев и skills.

Модуль после получения/крафта существует как законченный предмет своего типа и редкости.

Не вводить:

```text
Module ★ → ★★ → ★★★ → ...
```

без отдельного будущего пересмотра этого решения.

Причины:

- уменьшить количество параллельных progression axes;
- не увеличивать разрыв аккаунтов ещё одной вертикальной системой;
- упростить баланс огромного количества комбинаций;
- сохранить эмоциональную ценность самого получения редкого модуля;
- сделать разные категории меты действительно разными.

## 3.2. Редкость модуля

Редкость отражает силу, сложность и/или уникальность механики.

Предпочтительное направление:

```text
Common    → простые специализации / параметры
Rare      → условные эффекты / комбинации
Epic      → заметно меняет роль юнита/корабля
Legendary → может добавлять новую игровую механику
```

Legendary не должен означать только `+40% stat`.

Лучший ориентир:

> **Legendary module makes the player ask: “So I can do that?”**

## 3.3. Counterplay

Особенно сильные модули должны по возможности создавать читаемый counterplay.

Пример:

**Repair Drone Swarm** — выпускает ремонтных дронов во время космического боя, которые восстанавливают корпус союзных кораблей.

Сильная сторона: sustain в бою.

Counterplay: дроны можно уничтожить подходящими средствами (fighters/interceptors/AA или другим определённым counter).

Таким образом редкий модуль создаёт новую задачу для противника, а не безусловный бонус.

# 4. Модули юнитов / флота (Fleet & Unit Modules)

Обычные модули меняют возможности кораблей/юнитов и являются одним из основных инструментов построения build.

Примеры направления:

- оружейная специализация;
- броня/защита;
- сенсоры;
- логистика;
- planetary assault support;
- специальные tactical effects;
- deployable systems;
- repair/support mechanics.

### Примеры Legendary

**Regenerative Cargo Bay / Mobile Field Hospital**

Позволяет постепенно лечить/восстанавливать перевозимую в трюме наземную армию. Это позволяет экспедиционному флоту проводить серию операций без полного возвращения на базу.

**Repair Drone Swarm**

Создаёт во время боя рой ремонтных дронов, восстанавливающих корпус. Дроны являются уязвимой частью механики и могут быть контрены.

Это рабочие примеры, а не утверждённые финальные предметы.

# 5. Модули корабля героя (Hero Ship Modules)

## 5.1. Отдельная категория

Hero Ship Modules устанавливаются на уникальный флагман героя и не должны смешиваться с обычными fleet modules.

Их задача — менять **специальные возможности флагмана** и поддерживать стратегическую идентичность героя.

Ограниченность Hero Ship slots позволяет делать эти модули более необычными, не распространяя их эффект бесконтрольно на весь флот.

## 5.2. Примеры направления

- улучшенная координация десантных челноков;
- восстановление наземных войск внутри флагмана;
- специальные command effects;
- производство ограниченных tactical assets;
- ремонтные дроны;
- особые разведывательные/маскировочные возможности;
- поддержка planetary assault.

Hero Ship Modules:

- имеют rarity;
- не имеют stars;
- могут выпадать или крафтиться в зависимости от предмета;
- самые редкие могут быть craft-only.

# 6. Модули корпораций (Corporation Modules)

## 6.1. Корпоративный модуль — актив организации

Corporation Module принадлежит не конкретному игроку как личный permanent item, а является **капиталом корпорации**.

Типовой цикл:

```text
обычные игроки добывают resources
          ↓
auction / corporate acquisition
          ↓
corporation treasury / inventory
          ↓
craft / production
          ↓
Corporation Module
          ↓
выдача выбранному командиру
          ↓
Corporate War
          ↓
wear / repair / eventual replacement
          ↓
новый спрос на resources
```

Это одна из причин использовать термин **Corporation**, а не просто Alliance: организация владеет активами, производит имущество, инвестирует в участников и несёт экономические потери.

## 6.2. Роль в доступности Corporate Wars

Корпоративные модули позволяют развитой организации снабжать менее прокачанного, но сильного игрока конкурентоспособным оборудованием.

Это снижает зависимость участия в endgame от возраста аккаунта:

> **Economy provides the weapons. Players win the war.**

Корпорация получает причину рекрутировать игроков за skill и грамотно распределять дорогое оборудование.

## 6.3. Износ

В отличие от личных модулей, Corporation Modules могут иметь wear/repair lifecycle.

Цель — создать постоянный economic sink и не допустить состояния, когда корпорация однажды изготовила максимальный комплект и навсегда перестала нуждаться в экономике.

Точные правила износа, ремонта и уничтожения требуют отдельного документа.

# 7. Получение и крафт модулей

## 7.1. Не все модули должны получаться одинаково

Возможные источники:

- PvE rewards;
- PvP/meta rewards;
- drops;
- events;
- blueprints;
- crafting;
- специальные сюжетные источники;
- corporate production.

Некоторые Epic/Legendary modules могут быть **только craftable**.

## 7.2. Рискованный крафт

Крафт редкого модуля может завершиться неудачей.

```text
Blueprint
+ crafting materials
+ special resources
      ↓
CRAFT ATTEMPT
   ↙       ↘
SUCCESS   FAILURE
module    materials consumed
          module not created
          stability/pity progress
```

При failure уже существующие предметы/прогресс игрока не уничтожаются — теряются только ресурсы, добровольно вложенные в конкретную попытку.

## 7.3. Blueprint Stability / crafting pity

Чтобы исключить экстремальные серии неудач, предлагается рассмотреть progression конкретного blueprint.

Пример механики:

```text
Base success chance: X%
Failure → Blueprint Stability +Y
Next attempt → higher chance
...
Eventually → guaranteed success
```

Конкретные проценты не фиксируются этим документом.

### Для Corporation Crafting

Корпоративная неудача психологически сильнее, потому что может уничтожить результат работы десятков игроков. Поэтому corporate crafting может использовать более мягкий risk model.

Возможная модель для рассмотрения:

- Standard Production — дешевле / ниже шанс;
- Reinforced Production — дороже / выше шанс;
- Guaranteed Production — очень дорого / 100%.

Это превращает RNG в управленческое решение о риске, а не только бросок кубика.

# 8. Связь с компенсацией за Skill Upgrade Failure

Компенсационный ресурс от неудачных skill upgrades может стать одним из компонентов особого crafting.

Пример:

```text
Skill upgrade failure
       ↓
Residual Data
       ↓
+ gameplay crafting resources
+ blueprint
       ↓
Epic / Legendary Module craft attempt
```

Это даёт failure дополнительный смысл: неудачная прокачка навыка может приблизить игрока к созданию редкого предмета.

При этом `Residual Data` не обязан быть единственным pity-механизмом и не обязан быть свободно торгуемым.

# 9. Аукцион как связующая система

Метапрогрессия создаёт постоянный спрос на ресурсы аукциона.

Игроку могут понадобиться материалы для:

- skill upgrades;
- fleet module crafting;
- Hero Ship Module crafting;
- других progression recipes.

Корпорациям нужны ресурсы для:

- Corporation Modules;
- зданий;
- ремонта;
- замены изношенного оборудования;
- Corporate Wars.

Таким образом один рынок обслуживает одновременно **личную и корпоративную экономику**.

Типовой economic loop:

```text
matches / PvE / activities
          ↓
resources created
          ↓
auction
          ↓
personal progression OR corporation production
          ↓
upgrade/crafting/building/wear
          ↓
resources destroyed
          ↓
new demand
          ↓
players return to activities
```

Неудачные upgrades и crafting attempts являются частью resource sinks, но failure rates нельзя искусственно ухудшать только ради уничтожения ресурсов
