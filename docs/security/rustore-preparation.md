# Подготовка сетевой игры к RuStore

Обновлено: 2026-10-18. Это подготовка существующего player-клиента Void Dominion;
отдельный продукт Sector Zero описан в `../../mobile/rustore-sector-zero-release-roadmap.md`.
Оператор, контакт для обращений, география хранения, финальный package ID и ключ
подписи ещё не определены. Публикация и приём реальных запросов удаления пока выключены.

## Что реализовано

- `POST /auth/delete-account`: живая сессия, повторный ввод текущего пароля,
  явное подтверждение, лимит запросов; транзакционная очередь и отзыв сессий.
  Ответ 202 означает принятие запроса, а не уничтожение всех копий.
- В player-клиенте: «Ещё → Удалить аккаунт», предупреждение, пароль с показом
  символов, отдельное подтверждение. Ошибка сервера не выдаётся за успех.
- Обработчик `packages/server/account-erasure.mjs`: обе БД, профиль, инвентарь,
  социальные связи, push, метаэкономика, места и JSONB матчей. Другой участник
  сохраняет свой баланс и прогресс. Общее состояние обезличивается; место
  удалённого аккаунта нельзя занять повторной регистрацией прежнего ника.
  Хеш прежнего позывного резервирует его на срок существования реестра и старых
  копий: повторное удаление не должно затронуть нового владельца того же имени.
  Это защищённые ПДн, а не анонимные сведения. Снимать резерв допускается только
  вместе с соответствующей записью реестра после уничтожения старых копий.
- JSONL: связанные actor, установка и место; события другого вошедшего игрока
  на общем устройстве сохраняются без связи с прежними install/session.
  Список солей должен покрывать **всю** историю сохраняемых журналов.
  Чат `MatchRoom.chatHistory` находится в памяти процесса: остановка обоих
  сервисов очищает его. Произвольный текст, самостоятельно опубликованный
  в названиях корпораций/сообщениях других людей, требует отдельного обращения.
- Защищённый реестр удалений записывается с fsync **до** изменения данных и
  сохраняется независимо от дампов. Он содержит идентификатор, старый ник и
  при наличии email: это тоже ПДн, а не анонимный журнал. Доступ только
  обслуживанию; хранение — до гарантированного уничтожения всех старых копий,
  которые могут вернуть эти сведения. Удалять записи раньше нельзя. Для реестра
  и завершённых строк `account_deletions` оператор утверждает сроки и процедуру
  очистки; они не предназначены для бессрочного накопления.
- После `deploy/restore.sh` сервер отказывается запускаться, пока обработчик
  не повторит удаления по внешнему реестру (`--replay`) на обеих БД.
- Отдельный `rustore.yml`: только ручной запуск на main, environment `rustore`,
  release APK, отдельный package ID и закрытый ключ, TLS, запрет Android backup,
  проверка финального manifest/разрешений/сертификата. GitHub APK-updater выключен
  в этом канале. Никакой автоматической отправки в магазин.
- Русская политика доступна из welcome и «Ещё», запакована офлайн как инертный
  документ; её содержимое и SHA-256 должны совпадать с утверждённым публичным
  `text/plain` документом на сервере. Карточке магазина даётся публичная ссылка.

## Включение обработки удалений

Выполнять на стенде с синтетическими аккаунтами, затем на проде после утверждения
политики. Не включать `ACCOUNT_DELETION_ENABLED=1` до успешного учения.

1. Развернуть миграцию обеих БД штатным механизмом. Подготовить отдельный
   закреплённый checkout с зависимостями Node 22 / pnpm. Он должен соответствовать
   схеме работающего сервера. Не использовать checkout, изменяемый во время задачи.
2. Создать `/etc/moongame/account-erasure.env`, владелец root, режим 0600.
   Файл совместим с systemd EnvironmentFile и bash; значения брать в одинарные
   кавычки. Задать `ERASURE_CHECKOUT`, `STATE_DIR`, `ERASURE_GAME_DATABASE_URL`,
   `ERASURE_CORP_DATABASE_URL`, `ERASURE_LEDGER`, `ERASURE_LOG_DIR`,
   `ERASURE_ANALYTICS_SALTS` (JSON-массив текущей и исторических солей),
   `ERASURE_STOP_HOOK`, `ERASURE_START_HOOK`. Учётки обслуживания не передавать
   игровому процессу. Не помещать файл в GitHub или чат.
3. Реестр первоначально содержит `[]`, режим 0600, родительский каталог 0700.
   Создавать его **только при первом вводе**: отсутствующий после аварии реестр
   восстанавливается из независимой защищённой копии, а не заменяется пустым.
   Организовать его резервирование в РФ и контроль срока хранения. `ERASURE_LOG_DIR`
   содержит все текущие JSONL, режим каталога 0700, файлов 0600. Неизвестные файлы,
   архивы, вложенные каталоги и повреждённые строки блокируют обработку.
4. Hooks — абсолютные root-owned исполняемые файлы без записи группы/остальных.
   Stop переводит сайт в обслуживание и останавливает **оба** runtime, включая
   все экземпляры и воркеры, а также клиентов БД из мониторинга и резервного
   копирования, но оставляет PostgreSQL. Проверка не допускает даже idle-пулы. Start запускает штатный
   проверенный стек и снимает обслуживание. Не использовать `eval` и не
   передавать credentials аргументами. Работа держит тот же `autoupdate.lock`.
5. Установить service/timer из `deploy/`, поправив `ExecStart` под checkout.
   Таймер ежедневно в 04:30 UTC; политика должна отражать выбранный срок и окно
   обслуживания. Запустить вручную и проверить журнал. При ошибке сервисы
   остаются остановлены; `account-erasure.pending` блокирует автодеплой.
6. Провести учение: удаление из приложения → вход отозван → обе БД/журналы
   очищены → данные второго игрока сохранены → восстановление старых дампов
   при выключенных runtime → обычный старт отвергнут → `--replay` → повторная
   проверка отсутствия данных → запуск. Не править guard вручную для обхода.
7. Зафиксировать отчёт и его SHA-256. В server.env включить
   `ACCOUNT_DELETION_ENABLED=1`; для публичного выпуска задать
   `ERASURE_READINESS_CHECK=/путь/deploy/account-erasure-readiness.sh` вместе с
   `PUBLIC_RELEASE=1` и privacy/backup evidence из `rf-personal-data-readiness.md`.
   Проверка требует активный таймер и успешный запуск менее 48 часов назад.

После сбоя: устранить причину, повторить обработку под тем же lock. Если запрос
уже выполнен, но marker остался, проверить обе БД и реестр через `--replay`, затем
снять marker и запустить hooks. Не стирать marker, чтобы просто вернуть сайт.
При восстановлении из бэкапа сначала миграция, затем replay актуального внешнего
реестра на обеих БД; только после этого запуск. Immutable backups уничтожаются
по утверждённому сроку и до этого защищены и исключены из обычного обслуживания.

## Ключ и выпуск APK

[Полный шаблон политики](privacy-policy-template.md) содержит обязательные места
для подтверждённых сведений. Он не готов к публикации до заполнения и проверки.

1. Определить операторские сведения, сервер/бэкапы в РФ, возрастную категорию,
   бесплатность/покупки/рекламу и необходимые договоры/уведомления по RF-реестру.
   Сверить фактические SDK и разрешения с декларацией магазина.
2. Утвердить окончательный `appId`: он отличается от debug player/prototype.
   Создать **новый приватный** Android release keystore, например интерактивно
   через `keytool -genkeypair -keystore rustore-release.p12 -storetype PKCS12
   -alias rustore -keyalg RSA -keysize 4096 -validity 10000`. Пароли вводятся
   интерактивно; файл и резервную копию хранить защищённо. Публичный
   `mobile/debug.keystore` для магазина не подходит. Сохранить SHA-256 сертификата.
3. В GitHub создать environment `rustore`, разрешить только main, включить
   required reviewer и запрет обхода, если доступно в тарифе организации.
   Secrets: `RUSTORE_KEYSTORE_BASE64`, `RUSTORE_KEYSTORE_PASSWORD`,
   `RUSTORE_KEY_PASSWORD`, `RUSTORE_KEY_ALIAS`, `RUSTORE_RELEASE_CONFIG`.
   Последний — заполненный JSON по `mobile/rustore-release.example.json`.
   `previousVersionCode` брать из последнего опубликованного APK/консоли,
   новый строго больше. Один сертификат сохраняется для будущих обновлений.
4. `privacyEvidenceSha256` — SHA-256 утверждённого privacy manifest;
   `erasureRestoreDrillSha256` — SHA-256 реального отчёта об учении.
   Проверка формата этих полей не удостоверяет содержание доказательств:
   reviewer обязан сверить их до разрешения job. `policySha256` — хеш точных
   UTF-8 байтов публичной политики. Сведения пересматриваются не реже 30 дней.
5. Добавить `https://localhost` (origin нового Capacitor-профиля) в
   `ALLOWED_ORIGINS` сервера, сохранив нужные web/playtest origins. Проверить
   CORS и WSS с реального APK. Actions → **RuStore release candidate** → Run workflow. Получить только APK
   и `.verification.json`; приватный ключ в artifacts не попадает. Проверка
   разрешает INTERNET/ACCESS_NETWORK_STATE; новое разрешение требует отдельного
   обоснования и изменения проверки. Не расширять allowlist ради зелёной сборки.
6. Проверить на физических Android-устройствах: первый запуск, офлайн-соло,
   регистрация/вход/восстановление, удаление, политика, поворот, слабая сеть,
   установка обновления поверх предыдущего release тем же ключом. Проверить
   отсутствие debug-меню, внешнего APK-updater и запросов лишних разрешений.
7. Подготовить реальные скриншоты, описание и возрастную анкету; загрузить в
   тестовый канал RuStore, пройти проверки, затем отправить на модерацию.

## Основания и пределы проверки

Официальные [правила RuStore](https://www.rustore.ru/help/developers/publishing-and-verifying-apps/requirement-apps),
сверены 2026-10-18: разделы 5.1–5.4 (политика, обработка, минимальные разрешения,
удаление из приложения), 2.14 (техническая безопасность), 6.3 (разрешения).
Прохождение CI и наличие подписанного APK не подтверждают юридическое соответствие
или одобрение магазина. Не определять требования РФ одной кнопкой согласия:
основания обработки и обязанности оператора проверяются отдельно.

Проверки: `pnpm run check` с отдельным PostgreSQL, `pnpm run prototype`,
`node prototype/accountdeletiontest.mjs` (Chromium; форма на экране 390×844).
Локальные тесты используют отдельные синтетические БД, проверяют очередь, отказ
по паролю/сессии/хранилищу, повторное удаление, чужие данные и shared-device события.
Реальные operator facts, release key, Android device QA и production restore drill
остаются условиями выпуска. Playtest и новый магазинный канал не объявлены релизом.
