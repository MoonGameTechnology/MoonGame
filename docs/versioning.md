# Версионирование и обновления игры

Сетевой матч сохраняет правила своего запуска. Обновление хоста, интерфейса,
аутентификации и мета-сервисов не заменяет его движок и баланс. Новые матчи получают
текущий пакет. Операционные команды — в [runbook капсул](../deploy/RULESETS.md).

## 1. Что закрепляется

`packages/server/src/rulesets/` выбирает самодостаточный ESM-пакет по SHA-256 его байтов.
Внутри — исходный kernel и RNG, набор/порядок модулей, родной `GameData`, разрешение
конфига, автоматические приказы и расчёт видимости. Пакет собирает
`packages/server/build-ruleset.mjs`; исходная точка — `scripts/ruleset-entry.ts`.
Даже изменение логики без изменения номеров data/manifest даёт другой ID пакета.

В `MatchSnapshot.ruleset` / `matches.ruleset` записаны:

- ID пакета и исходная версия/хэш данных;
- конфиг, разрешённый исходным движком до первого действия;
- HMAC, связывающий эти значения с конкретным `matchId`;
- для доказанного старого запуска — исходный заголовок и свидетельство выкатки.

`state.version.manifest` содержит `ruleset:<sha256>`. Версия данных и её хэш остаются
исходными. Геометрия карты, `pricing`, RNG, очередь работ и прогресс остаются в мире;
реальная скорость и якоря времени — в сохранённом `MatchClock`.
Пин не заменяется при последующих сохранениях: адаптеры и триггер
`protect_match_ruleset` проверяют его неизменность и соответствие заголовку мира.

## 2. Как продолжается старая партия

Оба сетевых входа выбирают пакет до комнаты, квитанций и запуска часов. `MatchRoom`
получает выбранные kernel/data/проекцию и уже закреплённый конфиг; текущий движок не
разрешает его заново. Несколько пакетов загружаются в один процесс хоста, каждый мир
остаётся отдельным состоянием. Счётчик действий, квитанции и скорость переживают рестарт.

Номер текущего выпуска служит значением по умолчанию только для новых матчей.
Если нужный пакет отсутствует, повреждён или не поддерживает контракт хоста, комната
изолируется с `E_MATCH_RULES_MISMATCH` и причиной `E_RULESET_*`. Снимок и номер матча
сохраняются; остальные комнаты работают. Непустой стор не засевается заново из-за
пустого списка совместимых комнат.

Старые снимки без капсулы требуют проверенного происхождения. Операторский CLI
проверяет commit фактического запуска, интервал выкатки, родные data/hash, манифест и
конфиг. Он делает старый движок явным, сохраняя мир, seq, часы и первоначальный заголовок
в свидетельстве. Совпадения одного номера каталога недостаточно. Автоматическая
подмена заголовка на текущую версию в сетевых входах отсутствует.

## 3. Граница с современным интерфейсом и метой

В `welcome.ruleset` передаются публичные каталог, конфиг, доступные действия и данные
для отображения. Ключ, HMAC и исполняемый пакет в клиент не передаются. Интерфейс
использует каталог активной партии, затем восстанавливает текущий при выходе в хаб
или кампанию. Локальный новый reducer не блокирует команды старых правил;
окончательное решение принимает выбранный серверный движок.

Аккаунты, права доступа, ограничения запросов, журналирование и протокол обслуживает
текущий хост. Мета-сервисы сохраняют собственные версии и идемпотентные расчёты.
Обновление права собственности на предмет не добавляет его определение в старый каталог.
Сохранённые наградные политики/свидетельства матча сохраняются вместе со снимком.

Сетевой контракт не заменяет [миграции одиночных сохранений](../decisions/soloSaveMigration.ts).
Sector Zero продолжает пользоваться отдельной цепочкой проверенных пар версий.

## 4. Хранение, доверие и восстановление

Подписанный image содержит текущий пакет. После проверки подписи deploy-agent
архивирует его `.mjs` и дескриптор в `$STATE_DIR/rulesets`. Каталог принадлежит root;
приложение получает mount только для чтения. PostgreSQL выбирает digest, а не путь или
исполняемые байты. Реестр проверяет целостность и допустимый формат до исполнения.
Веб-API для загрузки кода отсутствует.

Отдельный ключ HMAC создаётся атомарно в постоянном томе `void-ruleset-keys`, доступном
пользователю контейнера. При наличии закреплённых матчей утраченный ключ не генерируется
заново. Пакеты, ключ и SQL-снимок входят в комплект восстановления: одной копии БД
недостаточно. Ключ не ротируется вместе с JWT или выпуском игры.

Пакет нельзя удалять, пока на него ссылаются живой матч, архив или сохраняемый комплект
расследования/восстановления. Автоматического удаления капсул сейчас нет.

## 5. Порядок доставки

1. CI собирает новый пакет вместе с хостом и клиентом, проверяет код и подписывает image.
2. Deploy-agent проверяет подпись, архивирует пакет, выполняет административную миграцию.
3. Хост восстанавливает каждый матч на его пакете и конфиге; новые матчи берут новый пакет.
4. Клиент переподключается к прежнему номеру матча и получает его каталог.

Текущий Compose выполняет обновление с корректным завершением процесса и повторным
подключением клиентов. Rolling/blue-green не является гарантией этого VPS.
Откат на хост с поддержкой того же формата капсул сохраняет выбор движков; более ранний
хост со строгим числовым manifest откажет в загрузке таких снимков. Пины для обхода этого
отказа не переписывают.

## 6. Следующие этапы и границы VPS

Следующие пункты — roadmap, их нельзя считать реализованными:

- матрица CI с точными историческими пакетами, обезличенными мирами и проверками клиента;
- версионные read-model/adapters для сложных производных чисел и будущих изменений
  wire/schema; перед удалением старого формата нужен такой адаптер;
- worker-изоляция по версии с отдельными бюджетами CPU/памяти и управлением жизненным циклом;
- единый автоматизированный зашифрованный комплект БД/ключа/капсул, доставка вне VPS
  и регулярное учение восстановления;
- сборка мусора по ссылкам живых матчей, архивов, реплеев и резервных копий;
- отзыв небезопасного пакета и отдельные проверенные совместимые исправления старых правил;
- полный replay-интерфейс оператора и закрепление runtime для офлайн-кампании.

На VPS остаются лёгкий кэш пакетов и исполнение активных миров. Тяжёлые матрицы,
нагрузочные испытания и дополнительные окружения следует выполнять вне игрового хоста.
`minSupportedClientVersion`/форс-гейт протокола — отдельное будущее изменение; получение
каталога матча само по себе такой гейт не вводит.

## APK вне магазина

Player/dev APK получают версии и скачивание с нашего HTTPS VPS, один source для
приложения и кнопки «Скачать APK» в шапке хаба (на ПК с мышью — и QR по наведению). Android versionCode растёт, appId и signing
key сохраняются; установка требует подтверждения пользователя и не очищает данные.
Откат remote manifest или ошибка сети не должны принуждать обновление или блокировать
игру. Публикация проверяет реальные APK metadata и атомарно переключает JSON+APK.
Манифест подписан в CI; приложение ставит только файл с подписанным SHA-256.
[Контракт, pipeline и проверки](../deploy/apk/README.md); RuStore обновляется отдельно.
