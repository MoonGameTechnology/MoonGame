# Синхронизация живых доков

`docs/state.md` — «живой якорь контекста»: снапшот того, что готово и как оно работает.
Его читают следующие сессии Claude и напарники, чтобы не перечитывать репозиторий целиком.
Якорь работает ровно до тех пор, пока **каждое** утверждение в нём актуально: одна
устаревшая строка дороже десяти отсутствующих, потому что по ней начинают писать код.

Три правила из `CLAUDE.md` («Working agreements») — ниже с обоснованием, потом практика.

## 1. Код первый, доки после

Сначала изменение → зелёный `pnpm run check` → **потом** текст. Не наоборот.

Почему: доки описывают то, что *реально легло*, а не то, что задумывалось. План по дороге
меняется (имя функции, код отказа, число тестов), и док, написанный вперёд кода, фиксирует
намерение — то есть врёт с первой минуты. `CONTRIBUTING.md` §«Тесты и документация»
формулирует это же: «После изменения поведения обнови `docs/state.md`».

Обновление доков едет **в том же PR**, что код (`docs/backlog.md`, «Как взять кирпичик»,
п. 5; чек-лист в `.github/pull_request_template.md`). Разъехавшись по двум PR, якорь врёт
в промежутке — а промежуток может длиться дни.

## 2. Реконсилируй, не дописывай

Найди утверждение, которое твоё изменение **отменяет**, и перепиши или удали его. Новый
абзац рядом со старой правдой — худший из вариантов: читатель видит две живые версии
одного факта и не может определить, какая свежая.

Практически это значит:

- Ищи по ключевому слову (имя модуля, действия, файла) **по всему** `docs/`, а не только
  в том абзаце, куда собрался писать: `rg 'fleet\.launch' docs/`.
- Исправление баг-репорта в §9 оформляют как зачёркивание с пометкой — там уже есть образец:
  `✅ ~~старое утверждение~~ — **исправлено**: …`. Так виден и факт, и его история.
- Не бей новую секцию `## 12`, если факт принадлежит существующей. Шапка §«Быстрый старт
  сессии» прямо декларирует: «факты живут в секциях и не дублируются здесь».

## 3. Сверяй с реальностью, не пиши по памяти

Каждое имя, число и сигнатура — из исходника или из вывода команды. Читай файл, который
описываешь; гоняй гейт; считай элементы, а не вспоминай их. Если утверждение нечем
подтвердить — его не пишут вовсе. Короткий точный док лучше длинного правдоподобного.

## Куда класть факт: карта секций `state.md`

Сначала найди владельца факта, потом пиши.

| Секция | Что владеет |
| --- | --- |
| §1 Что это | назначение проекта + роль каждого пакета монорепо |
| §2 Архитектура ядра | `createKernel`/`applyAction`/`advanceTo`, инварианты |
| §3 Карта файлов | дерево путей — правь при появлении/переезде файла |
| §4 Модель состояния | поля `GameState` |
| §5 Модули ядра | по подсекции `###` на модуль: действия, коды отказа, хуки |
| §6 Данные | `data/*.json`: ресурсы, юниты, здания, версия данных |
| §7 Прототип | `prototype/` — играбельный клиент, сборка, UI |
| §8 Метаигра | north-star: корпорации, AvA, мета-слой |
| §9 Статус | статус этапов + «⚠️ Известные стопгапы/долги» |
| §10 Команды и качество | команды гейта, property/fuzz-слой |
| §11 Как возобновить работу | вход для новой сессии |

## Счётчик тестов в шапке

Шапка `state.md` несёт строку вида
`**Тесты: N зелёных** (M skip, K файла)`. Число берут **из вывода гейта**, а не
приблизительно: `pnpm run check` (или `pnpm test`) печатает в конце две строки вида

```
 Test Files  <K> passed (<K>)
      Tests  <N> passed | <M> skipped (<всего>)
```

Отображение: `N` ← `Tests … passed`, `M` ← `skipped`, `K` ← `Test Files … passed`.
Здесь намеренно стоят плейсхолдеры, а не пример с цифрами: любой конкретный пример
устареет к следующему PR, а списать число из скилла вместо вывода гейта — ровно та
ошибка, которую этот скилл предотвращает. Смотри свой прогон.
Счётчик — единственный числовой якорь «сколько кода реально проверено», поэтому он
живёт в ОДНОМ месте: `docs/backlog.md` намеренно пишет «Тесты зелёные (актуальный
счётчик — в шапке `state.md`)» вместо своей копии числа. Не заводи вторую копию.

## Соседние доки — проверь на устаревший дубль

Один факт часто отражён в нескольких местах. После правки `state.md` пройди:

- **`docs/backlog.md`** — статус кирпича (`✅ готово` · `⏳ можно брать` · `🔒 ждёт
  зависимость`) и строка «что реально сделано». Кирпич, закрытый в коде, но висящий `⏳`,
  утащит следующую сессию делать сделанное.
- **`docs/roadmap.md`, §«Статус реализации»** — трогай, только если закрыт **этап**;
  секция сама ссылается на `state.md` за подробностями, дублировать детали туда не нужно.
- **Парный роадмап темы** (`docs/server-roadmap.md`, `docs/metrics-roadmap.md`,
  `docs/playtest-hardening-roadmap.md`, …) — если кирпич пришёл оттуда, там его строка статуса.
- **`docs/reviews/**` не трогай.** Это ДАТИРОВАННЫЕ исторические снапшоты: они верны на
  свою дату, и «актуализация» их уничтожает. `scripts/docs-check.mjs` исключает их из
  проверки ссылок ровно по этой причине.

## Гейт знает про доки

`pnpm run check` включает `docs-check` (`scripts/docs-check.mjs`) — исполняемая часть
правила «сверяй доки с реальностью». Он проверяет:

1. markdown-ссылки `[текст](путь.md)` и backtick-упоминания `` `имя.md` `` — цель должна
   существовать. Переименовал/удалил док — гейт краснеет во всех файлах, которые на него
   ссылались, и ты чинишь граф знаний, а не оставляешь висячие ссылки.
2. теги зон в `docs/backlog.md` (`[core]` `[act]` `[srv]` `[cli]` `[proto]` `[data]`
   `[docs]` `[sec]` `[ops]`) — против словаря `ZONES` в самом скрипте. Новая зона
   добавляется в **оба** места.

Осознанная ссылка на ещё не созданный файл — это запись в `ALLOW` внутри скрипта
**с причиной и датой** (конвенция `.trivyignore`), а не молчаливое удаление ссылки.

## Чек-лист

- [ ] Изменение уже в коде, `pnpm run check` зелёный — доки пишутся после.
- [ ] Каждое число/имя в новом тексте сверено с исходником или выводом команды.
- [ ] Найдена и **переписана** устаревшая формулировка (не добавлен абзац рядом).
- [ ] Факт лежит в секции-владельце `state.md`, новая секция не заведена.
- [ ] Счётчик тестов в шапке = реальный вывод vitest (если менялся набор тестов).
- [ ] `docs/backlog.md`: статус кирпича и «что сделано» — актуальны.
- [ ] `docs/roadmap.md` §«Статус реализации» — только если закрыт этап.
- [ ] `docs/reviews/**` не редактировался.
- [ ] `pnpm run check` прогнан ещё раз — `docs-check` видит правки доков.
