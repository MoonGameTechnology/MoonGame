# Анализ баланса контента

Баланс здесь меряется, а не обсуждается: ядро детерминировано, поэтому один и тот же
seed воспроизводит матч байт-в-байт, а сотня матчей считается за секунды. Спор «мне
кажется, red слабее» заменяется прогоном и диффом двух отчётов.

## 0. Сначала — какой контент ты меряешь

В репозитории **два** набора контента, и это первое, что надо развести:

- **`prototype/src/game.ts`** — инлайновый `parseGameData({ ... })` (начало ~строка 112).
  Секции: `technologies` (~119), `units` (~428), `modules` (~578), `factions` (~633),
  `buildings` (~655), `sectors` (~884), `sectorKinds` (~896), `planetTypes` (~920),
  `heroes` (~997). **Именно его гоняют все харнесы** (`selfplay.mjs`, `econplaytest.mjs`,
  `netserver.ts`) и играбельный клиент `prototype/dist/void-dominion.html` (артефакт
  сборки — в git его нет, собирается `pnpm run prototype`). Дома здесь —
  `blue/red/amber/violet` с чистыми пассивками.
- **`data/*.json`** — shipped-бандл (`data/manifest.json` + фрагменты, собираются
  `packages/shared-core/src/data/loadGameData.ts`). Его читают `packages/server/src/scenario.ts`,
  `packages/client/src/gameData.ts` и тесты `shared-core`. Фракции здесь другие —
  `vanguard` / `swarm`.

Правь то, что меряешь. Цифра, покрученная в `data/units.json`, **не изменит вывод
`pnpm run selfplay`** — харнес её просто не видит. Если вывод обязан измениться, а не
изменился, ты почти наверняка правишь не тот файл.

## 1. Прогон батча self-play

```bash
pnpm run selfplay            # 20 матчей, база сидов "sp"
pnpm run selfplay 200        # 200 матчей
pnpm run selfplay 200 tag7   # 200 матчей, другая семья сидов
```

`prototype/selfplay.mjs`: два AI-места на **реальном ядре**, headless, без сервера и DOM.
Цикл повторяет драйвер netserver — `kernel.advanceTo` + `aiOrders` каждые 2 игровых часа.
Фэйрнесс встроена: старты меняются на `i % 2`, фракции на `(i >> 1) % 2`, так что «по слоту»,
«по фракции» и «по старту» разделяются чисто. Конфиг матча: `scoreLimit = SCORE_LIMIT` (1100,
константа в `game.ts` — это код, не контент), `endsAt = 60` игровых дней, страховочный кап
харнеса — 90 дней.

Бери **200–400 матчей** для решения и меньше 20 — только чтобы убедиться, что харнес жив:
на 6 матчах «100% по старту» — это шум, на 300 — находка. Сохраняй базовую линию в файл
(`pnpm run selfplay 300 base > /tmp/before.txt`), иначе сравнивать будет не с чем.

## 2. Что читать в отчёте

Строки вывода и что каждая значит:

- **`win by slot`** — цель ~50/50. Перекос = первоходовое/позиционное преимущество, а не
  контент; сначала чини его, иначе он загрязнит все остальные строки.
- **`win by faction`** — главный балансный сигнал. Отклонение сильно за 50/50 (в
  `docs/metrics-roadmap.md` зафиксирована историческая находка «экономика бьёт урон ~73/27»)
  указывает на пассивку дома.
- **`win by start`** — если одна стартовая клетка выигрывает почти всё, дело в карте, а не
  в юнитах. Карта уже симметризована по обеим осям, так что перекос здесь — эмерджентный.
- **`длина` (avg/min/max) + `исходы`** — `score` значит, что кто-то добрал `SCORE_LIMIT`;
  `timeout` — что матч упёрся в `endsAt`. Сдвиг средней длины после правки — самый
  чувствительный индикатор того, что ты задел темп экономики.
- **`1-й бой` + `боёв всего`** — ноль боёв = матчи выродились в гонку очков; такой батч
  ничего не говорит о боевом балансе.
- **`snowball`** — доля матчей, где лидер середины выиграл. Высокий % = камбэков нет.
- **`usage` + `мёртвый контент`** — что ИИ реально построил и что не построил ни разу.
- **`SELFPLAY_JSON …`** — машинная строка (`n`, `decided`, `draws`, `errors`, `winsBySlot`,
  `winsByFaction`, `winsByStart`, `avgLengthDays`, `snowball`) для диффа двух прогонов.

Отдельно: `errors` ≠ 0 — это не баланс, это баг ядра (`advanceTo` вернул `{ ok: false }`).
Останавливайся и разбирайся с ним первым.

## 3. Экономика: кривые ресурсов

```bash
node prototype/econplaytest.mjs            # 40 игровых дней, 4 места, сиды sp-0..2, поза expand
node prototype/econplaytest.mjs 60 6 5     # 60 дней, 6 мест, 5 сидов
node prototype/econplaytest.mjs 40 4 3 defend  # мирные строители (поза aiOrders)
```

`prototype/econplaytest.mjs` тем же драйвером снимает почасовой `economySnapshot` и печатает:
запас на конец матча (median/mean/peak по игрокам), **стоки** (сколько ушло в постройки,
юниты, рынок), **arrears-часы** (сколько часов игрок жил в долгах — прокси brownout'а) и
**кривую запаса по дням**. «Пилит вверх» на кривой = ресурс копится и его не на что тратить.
Победа по очкам здесь намеренно отодвинута (`scoreLimit = 100_000_000`), чтобы мерить
steady-state, а не гонку. Побочно пишет `prototype/econ-playtest-result.json` (в `.gitignore`).

## 4. Живой матч, а не боты

`pnpm run metrics [файл]` (`prototype/report.mjs`) читает JSONL плейтеста из `playtest-logs/`
(пишет `prototype/netserver.ts`; без аргумента берётся свежайший `.jsonl`). Даёт микс действий
по типам/игрокам, реджекты по кодам, **контроль во времени** (таймлайн `planet.captured`),
desync'и и латентности. Это про поведение живых игроков и здоровье сервера — используй, когда
надо проверить, повторяют ли люди то, что показали боты. `pnpm run perf` — это про CPU кадра,
к балансу отношения не имеет.

## 5. Трассировка выброса до числа

Выброс полезен только тогда, когда доведён до конкретного поля:

- перекос **по фракции** → `factions.*.passives` (`productionBonus`, `combatDamageBonus`,
  `fleetSpeedBonus`) в `prototype/src/game.ts` (~633) / `data/factions.json`;
- **юнит доминирует** → `units.*.stats` (attack/defense/hp/shield/speed), `cost`, `upkeep`;
  смотри отношение боевой ценности к цене, а не абсолютные числа;
- **постройка мертва или обязательна** → `buildings.*`: `cost`, `buildTimeHours`, `produces`,
  `upkeep`, `scoreValue`, лестница `upgrades`;
- **матчи слишком короткие/длинные** → `scoreValue` построек и `SCORE_LIMIT`, потом уже
  темп добычи (`produces`);
- **технология обязательна** → `technologies.*.effects` + `researchTimeHours` / `cost`.

Важная ловушка: **«мёртвый контент» чаще означает, что его не строит ИИ**, а не что он плохой.
Прежде чем нерфить/бафать, проверь `aiOrders` в `prototype/src/game.ts` (~5040) — умеет ли бот
вообще заказывать эту сущность. Если не умеет, правильный вывод — «харнес не покрывает», а не
«контент сломан».

## 6. Дисциплина: одна переменная за раз

1. Зафиксируй базовую линию: `pnpm run selfplay 300 base > /tmp/before.txt`.
2. Измени **ровно одно** число в контенте. Две правки в одном прогоне делают эффект
   неатрибутируемым — отчёт не скажет, какая из них сдвинула win rate.
3. Прогони **ту же семью сидов и то же N**: `pnpm run selfplay 300 base > /tmp/after.txt`.
   Сиды — единственное, что делает два прогона сравнимыми.
4. Подтверди на **другой** семье сидов (`pnpm run selfplay 300 alt`), иначе ты подогнал
   контент под один конкретный набор матчей.
5. Подозрительный матч не обсуждают, а воспроизводят: детерминизм ядра (инвариант №1 в
   `CLAUDE.md` — никаких `Math.random`/`Date.now`, только seeded `Rng` и `ctx.now`) означает,
   что `sp-17` разыграется точно так же. Можно добавить временный лог в копию харнеса и
   прогнать один сид, вместо того чтобы спорить.

Историческая заметка в `docs/metrics-roadmap.md` (§M4) показывает, зачем шаг 4: усиление
урона red до +15% сделало **хуже** — 100% побед blue. Интуиция про «просто добавь урона»
здесь ломается регулярно.

## 7. Зона, гейт, оформление

Балансная правка — это изменение контента, зона **`[data]`** по словарю `docs/backlog.md`
(`data/*.json`; правка инлайнового каталога прототипа — зона `[proto]`). Контентные зоны почти
не пересекаются с кодом, поэтому такой PR редко конфликтует с чужой работой — но зона всё равно
одна на кирпичик.

Перед PR обязательно `pnpm run check` (lint + typecheck + test + docs-check). Тесты **пиннят
конкретные числа контента**, и это by design — например `packages/shared-core/src/data/schemas.test.ts`
проверяет `data.units.cruiser?.upkeep.credits === 8` и `data.buildings.orbital_aa?.aaDamage === 14`,
`packages/shared-core/src/data/factions.test.ts` — что фракций ровно две, а
`prototype/src/factions.test.ts` — что домов ровно четыре и что +12% экономики blue реально
двигает казну. Красный тест после балансной правки — это не «сломанный тест», а вопрос:
изменение намеренное (тогда обнови пин в том же PR) или ты задел то, чего не собирался.

Итог оформляй как измерение, а не мнение: команда, N матчей, семья сидов, до/после по строкам
отчёта, и какое поле контента изменено. Найденное, но не исправленное — отдельным кирпичиком в
`docs/backlog.md`; изменившееся поведение — правкой (не дописыванием) в `docs/state.md`.
