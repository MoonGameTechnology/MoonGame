# Единое правило: почему PR не вливается

Собрано по итогам суток, за которые PR висели по пяти разным причинам подряд. Документ
отвечает на один вопрос — **«почему этот PR не поехал»** — и заменяет собой гадание по
цвету галочек.

Разбор конкретного PR читай **не здесь, а в нём самом**: авто-мерж пишет в PR
sticky-комментарий «🚦 Почему этот PR не вливается» и называет виновника поимённо. Этот
документ объясняет, как устроено правило целиком и что делать с каждым ответом.

---

## Правило

> **PR вливается сам тогда и только тогда, когда выполнены все пять условий.
> Если PR висит — не выполнено ровно одно из них.**

| # | Условие | Кто проверяет |
| --- | --- | --- |
| 1 | PR открыт, не черновик, не из форка, база — `main` | `automerge.yml`, отсечка в `if` |
| 2 | Все **обязательные** чеки на ГОЛОВНОМ коммите зелёные — и ни один не **отменён** | ruleset ветки |
| 3 | GitHub досчитал `mergeStateStatus` до `CLEAN` или `UNSTABLE` | `automerge.yml`, цикл перечитывания |
| 4 | У базовой ветки есть merge queue | `automerge.yml`, чтение `repository.mergeQueue` |
| 5 | Ревью собрано, если ruleset его требует | ruleset ветки |

Дальше PR ставится в очередь автоматически, очередь пересобирает его на «свежий `main` +
PR», перепроверяет обязательные чеки **там** и вливает. Руками жать ничего не нужно.

`UNSTABLE` в условии 3 — не опечатка. Это «обязательные зелёные, необязательный красный»,
а информационные сканеры краснеют штатно: в `caddy`/`gosu` живут HIGH-CVE, которые чинятся
только апстримом. Требуй мы строго `CLEAN` — один чужой CVE остановил бы вообще все PR.

## Таблица причин

Каждая строка — реально случившийся случай, а не гипотеза.

| Что видно | Причина | Что делать |
| --- | --- | --- |
| Все чеки зелёные, PR стоит, в комментарии `BLOCKED` после 6 попыток | Обязательный чек **отменён** (`cancelled`) — чаще всего столкновение в concurrency-группе | Перезапустить отменённый прогон. Отменённый required-чек GitHub считает провалом навсегда |
| В комментарии класс **сканер** | Блокирующий сканер (SEC-1) нашёл проблему **или** сам не отработал | Смотри сводку сканеров: «⚠️ НЕ подтверждён» = сломался скан, иначе = настоящая находка |
| В комментарии класс **код** | Упал `pnpm run check` — lint / typecheck / тесты | Чинится кодом. Это не сканер |
| В комментарии класс **скрипт** / **инфраструктура** | Упал конкретный шаг джобы либо раннер/сеть | Открыть указанный шаг; инфраструктурное — перезапустить |
| Красное есть, но в разделе «мержу НЕ мешает» | Информационный сканер | Ничего. Мерж это не держит |
| «Обязательных чеков нет ВООБЩЕ» | Воркфлоу, который даёт чек, не подписан на нужное событие | Добавить ему `pull_request` / `merge_group` **и** дописать в `workflows:` у `automerge.yml` |
| «У базовой ветки нет merge queue» | Стековый PR: база — не `main` | Ничего. База станет `main`, когда вольётся нижний PR |
| Нужно ревью | Ruleset требует одобрений | Ждёт человека, автоматикой не лечится |
| Ничего красного, а состояние `BLOCKED` | Мешает правило ветки, а не проверка | Settings → Rules: требование ревью, «Require deployments to succeed», запрет мержа автором |

## Три грабли, на которые мы уже наступили

**1. `mergeStateStatus` считается асинхронно.** Сразу после того, как позеленел последний
чек, GitHub ещё какое-то время отдаёт `BLOCKED`. Авто-мерж будит именно завершение
прогона, поэтому одно чтение попадало прямо в окно пересчёта — и PR вставал навсегда,
потому что будить его больше некому. Закрыто циклом перечитывания (6 попыток по 20 с).
Наблюдалось дважды на одном PR с разницей в 7 часов; при этом REST в те же секунды отдавал
`mergeable_state: clean`.

**2. Перезапуск прогона — не лекарство, а способ воспроизвести проблему.** Перезапуск
возвращает чек в `pending`, то есть сам загоняет состояние в `BLOCKED`, и когда чек
зеленеет, всё повторяется. Хуже: если в этот момент в ту же concurrency-группу приезжает
push (например, «Update branch»), один из прогонов **отменяется** — и получается уже
неустранимый перечитыванием `cancelled`. **Не перезапускай прогон, если по ветке уже
что-то идёт.**

**3. «Ветка отстала от `main`» — это НЕ причина.** Мерж трёхсторонний: отставшая ветка
ничего не откатывает. Проверять это `git diff main branch` (две точки) **нельзя** — такой
diff показывает разницу вершин, то есть выдаёт все ушедшие вперёд коммиты `main` за
«удаления». Правильно смотреть `git diff main...branch` (три точки — от точки ветвления)
либо честно прогнать пробный мерж:

```bash
git checkout -B trial origin/main && git merge --no-commit --no-ff <ветка>
git diff --cached --stat origin/main   # вот это и произойдёт при мерже
```

Автор этого документа успел на этом ошибиться и объявить ложную тревогу — поэтому грабля
записана, а не забыта.

## Что делать, когда PR висит

1. **Открой комментарий «🚦 Почему этот PR не вливается»** в самом PR. Он обновляется на
   каждом прогоне авто-мержа и называет причину. Комментарий пропал — значит PR поехал.
2. Комментария нет вовсе → авто-мерж не запускался. Смотри его прогоны: джоба отсекает
   форки, черновики и прогоны не по `pull_request`.
3. Причина ясна — чини по таблице выше.

**Не диагностируй по цвету галочек.** Зелёный список чеков совместим и с «поедет через
минуту», и с «не поедет никогда» — разницу видно только в состоянии мержа.

## Где это живёт в коде

- `.github/workflows/automerge.yml` — правило целиком: отсечки, цикл перечитывания,
  постановка в очередь.
- `.github/scripts/why-not-merging.mjs` — классификация («сканер» / «код» / «скрипт» /
  «инфраструктура» / «отменён») и sticky-комментарий. Обязательность чека берётся из
  ruleset базовой ветки, а не угадывается.
- `.github/scripts/summarize-security.mjs` — сводка сканеров, по которой отличают
  «настоящая находка» от «скан сломался».
- `CONTRIBUTING.md` — настройка репозитория (ruleset, очередь, required-чеки).
