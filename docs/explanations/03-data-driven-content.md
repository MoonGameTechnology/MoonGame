# 03. Контент в JSON, а не в коде

**Дата:** 2026-08-18
**Статус:** accepted

## Контекст

Void Dominion — 4X-стратегия с большим объёмом игрового контента: юниты, здания,
фракции, технологии, герои, типы планет, сектора, ресурсы, награды, медали,
события, таблицы дропа. Контент постоянно меняется (баланс, новые фракции,
сезоны).

**Проблема:** если контент в коде (TS-константы, классы), каждое изменение
баланса — релиз кода, pull request, CI. Дизайнер не может править контент без
разработчика. Контент и код связаны — нельзя заменить фракцию без правки логики.

**Альтернативы:**

- **A.** Контент — JSON-файлы в `data/`, валидируются zod-схемами в
  `shared-core/src/data/schemas.ts`. Ядро читает контент через `GameData`
  (immutable, валидированный). Баланс — правка JSON, не код.
- **B.** Контент — TS-константы/классы в коде. Типобезопасно из коробки, но
  каждое изменение — релиз кода.
- **C.** Контент — в БД, загружается рантайм. Гибко, но ломает детерминизм
  (контент меняется mid-match) и требует инфраструктуры.

## Решение

**Альтернатива A.** Контент — data-driven JSON:

- `data/*.json` — фрагменты контента (`units.json`, `factions.json`,
  `buildings.json`, …).
- `data/manifest.json` — версия контент-бандла.
- `data/maps/*.json` — карты (`MatchMap`).
- `loadGameData(reader)` — композитор: собирает фрагменты в один `GameData`,
  валидирует через `parseGameData` (zod).
- `safeParseGameData` — безопасный парсинг (A05/A08: весь внешний контент
  валидируется до того, как достигнет ядра).
- Версия контента пинится per match (`version.data`, `version.dataHash`) —
  матч не меняется, если контент обновился после старта (GDD §5.2).

**Ключевое:** ядро знает ничего о конкретных юнитах/фракциях — только строки,
которые резолвятся против `GameData`. Новая фракция = JSON-запись + опц. модуль,
не правка ядра.

## Последствия

**Плюсы:**
- Баланс — правка JSON, не код. Дизайнер может править без разработчика.
- Версионирование: контент пинится per match, реплей воспроизводим.
- Валидация: zod-схемы ловят невалидный контент на загрузке (fail-secure).
- Расширяемость: новая механика = данные + опц. модуль, kernel не трогается.

**Цена:**
- zod-схемы должны поддерживаться в синхрон с JSON — иначе невалидный контент
  валит загрузку.
- Контент — строки, не типы: опечатка в `unit: 'cruiser'` ловится только
  рантайм-валидацией (но `parseGameData` ловит на старте).
- JSON — нет логики: сложные правила (условные бонусы) — через хуки в коде,
  не в данных.

**Совместимость:** детерминизм (инвариант #1 — контент immutable per match),
fail-secure (инвариант #4 — невалидный контент → `E_*` код), модульная шина
(инвариант #3 — хуки читают контент через `h.ctx.data`).
