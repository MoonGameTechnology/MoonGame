# Полный тестовый стенд — проверка 2026-10-10

Стенд поднят, проверки выполнены для Void Dominion и Averion: Sector Zero.
Сохранение данных, границы доступа, TLS, сетевые клиенты и восстановление после
аварий работают в проверенных сценариях. **Готовность к непрерывной эксплуатации
не подтверждена:** обнаружены **2 HIGH и 3 MEDIUM**, а p95 ping превысил цель.
Успешная проверка наблюдения слабости означает, что слабость воспроизведена.

Приоритеты перед тестовым релизом:

1. Восстанавливать часы матча из устойчивого wall-clock якоря: после рестарта время откатывается.
2. Включить восстановление владельцев/прав БД в процедуру восстановления сервиса.
3. Сделать одноразовое погашение reset-токена атомарным.
4. Исправить healthcheck для нативного HTTPS.
5. Подключить доставку писем либо явно закрыть недоступное восстановление пароля.

## Что именно проверялось

Контейнерный сервер собран из `7466e6fc342c71cd565bb12b678226b81d358cbf`, через
проектный multi-stage Dockerfile: Node 26.10.0 в builder; в distroless runtime
**Node 22.23.2 / OpenSSL 3.5.7**, UID 65532, без shell и компилятора. PostgreSQL
16.15 — проектный digest; Caddy 2.11.4 собран через `deploy/caddy/Dockerfile`.
Системный Node для проверок — 22.23.3. age — 1.2.1, QUIC-клиент — aioquic 1.3.0.

После слияния #1567/#1568 ветка обновлена до
`024979918d076c937922e350e1d75da4344fb215`.
Транспорт, auth, PostgreSQL, Dockerfile, backup/restore и игровые часы между двумя
срезами не менялись. Изменились производство/кораблестроение и сборка UI:
оба прототипа пересобраны, Sector Zero/mines проверены повторно, полный гейт
повторён на свежем main: **10826 тестов, 0 skip, 887 файлов**, lint/typecheck/docs-check зелёные. Контейнерные измерения относятся к первой сборке.

Это отдельные контейнеры/сети/тома с синтетическими аккаунтами, случайными ключами
и временной CA. Рабочий порт опубликован на loopback; PostgreSQL находится в
Docker internal network. Второй контейнер из посторонней сети не смог подключиться
к БД. Доступ владельца Docker daemon остаётся административной границей доверия.

**Отличия проверенных профилей от стандартного deploy:**

- Baseline: нативные HTTPS/WSS, PROD=1, GATE=1, SEAT_LOCK=1, Origin allowlist,
  отдельная роль PostgreSQL, DB_AUTO_MIGRATE=0, DB_REQUIRE_LEAST_PRIVILEGE=1.
  В исходном соединении с PostgreSQL `ssl=false`.
- Усиленный стенд: PostgreSQL TLS 1.3, `hostnossl reject`, доверенная CA и
  `sslmode=verify-full&sslrootcert=...` у настоящего приложения. Проверены также
  отказ чужой CA/hostname и TLS 1.2. Этот профиль не включён патчем в shipping Compose.
- Caddy: временный сертификат и проверенный TLS upstream вместо штатного
  `reverse_proxy server:8788` по HTTP. HTTP/2 и HTTP/3 проверены запросами,
  а не выводом о поддержке из конфига. Нативный сервер и Caddy принимают TLS 1.2;
  CBC принят нативным сервером и отвергнут Caddy.
- Только для сборки добавлены CA secret mounts и `NODE_USE_ENV_PROXY=1` для
  Corepack/Node 26; для собственных контейнерных имён расширен NO_PROXY Caddy.
  Проверка сертификатов сетевых инструментов не отключалась.

## Находки

### ST-01 · HIGH · Рестарт откатывает игровой clock

**Подтверждение:** до остановки `welcome.serverTime=2386896`, после запуска —
`11400`, при сохранённом `state.time=3048` и неизменном `seq=3`. Прошло 23.636 с
реального времени. При TIME_SCALE=24 ожидалось ещё 567264 мс игрового времени;
фактически clock пошёл назад на **2375496 мс, около 39.6 игровых минут**.

`MatchRoom` при `initiallyStarted` задаёт `lobbyAccrued=initialState.time` и новый
`lobbyRunningSince=now()`. Shipping host восстанавливает снапшот без устойчивого
wall-clock якоря. Поэтому сохранённое действие не исчезает, но оставшийся срок
исследования/события повторно отсчитывается после запусков. Исследование на 4
игровых часа не завершилось после 689 секунд отсутствия игрока и серии рестартов.
Это не проверка его срока при непрерывном uptime.

**Последствие:** обслуживание/аварии задерживают мир, непрерывность 24/7 не обеспечена.
Долг уже отмечен как [PE-2.2](../persistence-roadmap.md).
**Приёмка:** после 20-секундного простоя время монотонно и включает простой с
учётом TIME_SCALE; due-событие применяется один раз, включая повторный restart.

### ST-02 · HIGH · Данные восстановлены, runtime роль лишилась доступа

**Подтверждение:** настоящий age-бэкап всей БД восстановлен после удаления
users/matches/receipts/seats. Количество и отпечатки строк каждой таблицы совпали.
Но `SELECT ... FROM users` под `vd_app_stack` завершился **SQLSTATE 42501**.
`backup.sh` использует `--no-owner --no-privileges`: таблицы восстановились под
admin, runtime grants не вернулись. Это профиль раздельных ролей из #1566.

**Последствие:** успешный restore данных не означает восстановленный игровой сервис.
Повторный `database-admin.mjs provision` вернул права, readiness и запуск, без
изменения отпечатков данных. Измерены отдельно restore и provision+startup.
**Приёмка:** полная процедура возвращает данные, schema revision, владельцев,
минимальные права и `/ready=200`; сервер работает без admin credentials.

### ST-03 · MEDIUM · Одноразовый reset не атомарен

**Подтверждение:** локальный SMTP-приёмник получил ссылку через тестовый `Mailer`
общего auth API. Последовательное повторное использование даёт 401, старые сессии
после смены пароля теряют доступ. Но два параллельных запроса с одним bearer
оба дали **200**. На shipping HTTPS API с настоящей PostgreSQL повторено **3/3**:
статусы `[200,200]` в каждом раунде. Это тестовые аккаунты и ключ стенда.

`authApi.ts` отдельно читает fingerprint, вычисляет scrypt и вызывает безусловный
`PostgresUserStore.setPassword`. Проверка/смена не образуют compare-and-set.
**Последствие:** один bearer можно погасить дважды, итог зависит от последней записи.
Для эксплуатации уже требуется действующий reset bearer; обхода подписи не найдено.
**Приёмка:** два одновременных запроса дают ровно один успех; новый session жив,
старый и проигравший запрос не меняют пароль.

### ST-04 · MEDIUM · Нативный TLS несовместим с image healthcheck

**Подтверждение:** HTTPS `/health` и WSS работают; контейнер становится `unhealthy`.
В Dockerfile проба всегда вызывает `fetch('http://127.0.0.1:8788/health')`, тогда
как listener обслуживает HTTPS. Этот HTTP-запрос отдельно воспроизведён и отвергнут.
**Последствие:** ложная авария в мониторинге; внешний orchestrator может считать
работающий сервис неисправным. Сам Docker не перезапускает контейнер лишь по `unhealthy`.
**Приёмка:** оба поддержанных TLS-пути дают достоверную health-пробу с проверкой CA.

### ST-05 · MEDIUM · В точке запуска нет доставки recovery-письма

**Подтверждение:** shipping host передаёт в `registerAuthApi` signing/verification
и RESET_BASE_URL, но не `sendMail`. Используется `logMailer`: по умолчанию только
to/subject, без тела. `/auth/recover` отвечает 200, но письмо не доставляется.
`MAILER_LOG_BODY=1` раскрывает bearer в логе и не является почтовым транспортом.
Риск флага уже описан в [аудите шифрования](2026-10-10-encryption-protocols.md).

Реальные SMTP команды и приём сообщения проверены через **тестовый адаптер**;
эта проводка не считается готовой интеграцией production host.
**Приёмка:** сервер доставляет письмо через настроенный transport, сохраняет
uniform response и не раскрывает bearer ни в обычных, ни в debug-логах.

**Нагрузка:** 40 WSS-клиентов, 4 матча, 481.488 с на полной численности, setup
107.027 с. В последней выборке **8200 команд**, 7135 сверок state hash; ноль
десинков, ошибок, отклонений и межматчевых сообщений. Ping измерен по 8280 pong:
**p50=51 мс, p95=312 мс, max=1708 мс**. Команды/хеши приведены по последнему
периодическому sample, ping — по всему завершённому прогону.

Цель p95<150 мс не достигнута. Параллельно работали сборка Caddy, браузерные
smoke и полный гейт; это не отдельный capacity benchmark production VPS.
Контейнер ограничен 1 GiB/512 pids; memory usage между первой/последней выборкой
233.9→250.7 MiB. Короткий прогон не устанавливает отсутствие утечки памяти.

В исходном прогоне после restart время readiness: graceful 2.432 с, SIGKILL+autorestart 5.964 с,
возврат БД 1.675 с. Это локальные измерения, не production SLA/RTO.
`docker kill` через API означает ручную остановку и не проверяет autorestart:
в итоговом сценарии отдельный helper с CAP_KILL сигналил ровно PID игрового
контейнера; сеть helper отключена, RestartCount проверен.

107 исходных записей и 8 уточняющих сценариев в JSON включают положительные/отрицательные проверки,
контрольные перепроверки и наблюдения найденных слабостей. Первоначальные ошибки
харнеса (статус create=200, случайные match IDs, drop вместо disconnect, issuer,
права bind mount и ожидание readiness) исправлены и не выданы за дефекты продукта.
Первые нагрузочные попытки с невалидным `orbit='far'` исключены из измерений:
гейт их отверг, не сжёг seq, а следующий пропущенный номер был отвергнут по порядку.

CSP в обоих browser viewport блокирует `eval` библиотеки zod; pageerror нет.
Для UI automation явно пинован SPKI временного сертификата. Проверки подлинности
CA/hostname выполнены отдельными TLS-клиентами с обязательной проверкой сертификата.

## Уточнение доказательств после автоматического ревью

Повторная сборка контейнера — `f1c700c12046576dcaa5c6be241bb8d8a863b6dd` (между срезами менялся только UI
кораблестроения). Восемь сценариев выполнены повторно на новом отдельном матче:
корректный чужой player/actionId отвергнут именно `E_FORBIDDEN`; чужой match token
проверен на существующем втором матче с успешным положительным контролем;
220 raw frames дали 50 parse errors, соединение осталось открытым.

До рестартов реально выполнен `fleet.split`: отпечаток принадлежащих игроку
флотов изменился и совпал с сохранённой БД. После graceful и SIGKILL совпали
**оба отпечатка и seq=3**. В уточняющем прогоне readiness вернулся за 2.425 и
11.515 секунды соответственно. Это проверка конкретного эффекта, а не
тождественности всех полей мира во всех возможных сценариях.

При остановке БД `/ready` недоступен и транспорт уже закрыт. Попытка разделения
не изменила seq/флоты; после возврата БД нет успешного receipt этой попытки,
отпечаток состояния и seq остались прежними. Путь `E_UNAVAILABLE` на открытом
транспорте этим прогоном отдельно не подтверждён.

Overflow повторно измерен **после входа в `/game/`**: `scrollWidth/innerWidth`
равны 1440/1440 и 390/390; pageerror нет. PNG заменены снимками этого прогона.
Сохранённые нагрузочные счётчики проверены отдельно: последняя выборка содержит
8200 команд, 8200 pong и пустой rejects; весь прогон — 8280 pong. Первоначальный
финальный счётчик отправки не был экспортирован: флаг в JSON теперь назван
`connectionHashPass`, оценка записанной выборки — `recordedTrafficPass`.
Pong подтверждает ping, а не receipt конкретного игрового действия.

Исходники исправлены: shared `test()` задаёт ненулевой exit code при ошибках;
уточняющий сценарий сохраняет результаты после каждого шага и прекращает работу
при провале. Контрольная искусственная ошибка дала exit=1 и сохранённую запись. Для Docker PG после restart используется актуальный IP с проверкой
сертификата по DNS-имени `postgres`; статический IP в первых попытках устаревал.
Ранние варианты сценариев заменены; исходные результаты сохранены с примечаниями
о границах их доказательств. Дополнительные прогоны не изменили пять находок. Полный гейт на этом свежем main:
**10835 тестов, 0 skip, 888 файлов**, lint/typecheck/docs-check зелёные.
Временная umask=0077 мешала упаковочным Debian fixtures; с обычной для сборки
umask=0022 полный прогон прошёл, тесты/продукт для этого не менялись.

в отчёт. Ритуал публикации — только документация и доказательства.

## Что остаётся неподтверждённым

- Реальный сервер: его адрес, DNS/сертификаты, firewall, SSH, cloud IAM и текущая
  конфигурация. Публичный GitHub Pages клиент ранее проверен через прокси среды,
  который перехватывает TLS; это не origin TLS attestation игрового сервера.
- Шифрование host/cloud volumes, snapshot storage, ключи KMS/HSM и физический диск.
  Docker overlay и volume сами по себе этого не доказывают.
- Доставка recovery в реальные inbox, SPF/DKIM/DMARC, cron/retention реального
  backup-хранилища, независимость production restore identity от backup host.
- Физические телефоны/GPU/перегрев; phone viewport не заменяет устройство.
- Многочасовой/многосуточный цикл, 8-часовой downtime, максимальная вместимость,
  два процесса сервера и распределённые гонки. Наш прогон ограничен временем/CPU
  среды и выявленной проблемой clock; автоматические core/driver тесты не заменяют
  подтверждение полноценного 24/7 режима.
- Полная ZTA: mTLS/workload identity на всех hops, service egress policy и отсутствие
  доверия к владельцу Docker daemon здесь не реализованы. Доказана работоспособность
  усиленного тестового профиля, не развёртывание его на вашем хосте.
