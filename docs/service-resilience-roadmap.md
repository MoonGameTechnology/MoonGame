# Отказоустойчивые сервисы — роадмап и фундамент

Продолжение модульной архитектуры ядра на уровне процессов: отказ необязательной
механики отключает её операции, сохраняя остальные возможности игры. Сервисы
выделяем по самостоятельному состоянию, нагрузке и границе отказа; расчёт боя,
движение и сессионная экономика остаются модулями одного детерминированного движка.

Решение владельца: 2026-10-11. Это последовательность работ с критериями приёмки,
а не календарное обещание. Состояние сверено со свежим `main` и исходниками.
[Карта сервисов и сегментов](service-architecture-map.md) ·
[Корпорации: контракт и перенос](corporation-service.md) ·
[Сервер](server-roadmap.md) · [Эксплуатация](operations-roadmap.md) ·
[Экономика и условия запуска торговли](economy-roadmap.md).

## Что реализовано

- Обычные матчи и авторизация живут в Game. Его локальный Meta/Economy объединяет
  инвентарь, материалы, награды, крафт, сезон, кошелёк и Auction одной транзакцией.
- Commerce имеет отдельный entrypoint, собственную БД/runtime-роль, signed entitlement
  и долговечную доставку. Реальные провайдеры отключены; платный запуск не подтверждён.
  [Точный объём v0 и runbook](meta-economy.md).
- Corp имеет самостоятельный entrypoint и опциональную отдельную PostgreSQL.
  Game стартует без него; итог AvA и аудит возврата доставляются после восстановления.
  Код переноса готов, фактическое переключение живого сервера не подтверждено.
- `DependencyGuard` ограничивает нагрузку на удалённую зависимость. Оба игровых
  входа и внутренние корпоративные RPC используют его через `corporateRequest`.
  На один повторно используемый объект endpoint и игровой процесс — максимум
  **16** незавершённых вызовов, без очереди ожидания. После **3** подряд неуспешных
  завершений circuit открывается на **5 секунд**, затем пропускает одну пробу.
  Ошибки транспорта/подписи/разбора и HTTP 5xx считаются отказом; подписанные
  остальные ответы, включая пользовательский rate-limit 429 и бизнес-отказы 4xx,
  подтверждают доступность транспорта. Один ограниченный клиент не открывает
  общий circuit для остальных пользователей: сервис корпораций и сам отвечает на
  клиентские ошибки (битый JSON, размер тела) кодом 4xx, а не 503.
  Старые ответы не закрывают и не открывают новое поколение circuit.
- Транспорт по-прежнему ограничивает вызов **2 секундами**, ответ **1 MiB**,
  запрещает redirect и проверяет подпись ответа. Путь проверяется до guard:
  изменение origin/пути/query при URL-нормализации и fragment отклоняются без
  отправки peer; публичный gateway отвечает `400 E_BAD_REQUEST`. Это защищает
  общий circuit от клиентских запросов к закодированным `..`. Guard не повторяет команды.
  Публичный corporate gateway сводит локальный отказ к `503 E_CORPORATIONS_UNAVAILABLE`.

Guard — локальный предохранитель, не распределённая квота, не лимитер входящей
авторизации и не защита от потери общего хоста. Его состояние не долговечно;
рестарт допускает новую ограниченную серию вызовов. `snapshot()` отдаёт состояние
и число активных вызовов для адаптера наблюдаемости; экспорт метрик ещё не подключён.
Для новой зависимости нужен свой guard и свой ограниченный транспорт. Нельзя
создавать новый endpoint на каждый запрос или объединять независимые домены одним guard.

## Целевые владельцы данных

| Домен | Единственный владелец записи | Что не выносится вместе с ним |
| --- | --- | --- |
| Game / match workers | Снимок боя, места, pinned manifest/data/loadout, квитанции, результат матча и журнал доставки | Корпоративные роли, кошельки и книга лотов |
| Meta / Economy | Личные и корпоративные предметы, provenance/soulbound, материалы, кошельки Варрантов, ledger, награды, крафт, Season Pass, entitlements и лоты Auction | Членство корпораций, платёжные provider secrets/orders и состояние матча |
| Commerce | Каталог платных предложений, заказы, provider transaction IDs, webhooks, refunds/chargebacks и payment receipts | Арсенал, кошельки, игровые лоты и выдача игровых ценностей: только entitlement-команда в Meta/Economy |
| Corp | Членство, роли, влияние, инфраструктура, вызовы/ростеры AvA, корпоративные результаты/аудит | Сам бой и физическое владение предметами |
| Profile / statistics / notifications | Позже: проекции прогресса/рейтинга, доставка уведомлений | Источник результата и выдача предметов/валюты |
| API / Auth / Lobby | Сессии, маршрутизация и вход в матч; пока роль Game | Расчёт боя и прямые записи в чужую БД |
| Staff / Support | Заявки, назначения, evidence references, решения, grants/admission и копии служебного аудита | Игровые санкции/ценности меняет их владелец; SSH/deploy/БД-admin остаются management |
| Backup / log-audit / SIEM / response | Собственные архивы, потоки, incidents и runbook admission; независимые контуры | Первичные данные остаются у игровых доменов; права write/delete/restore/response разделены |

**Meta/Economy остаётся единым транзакционным доменом**: Inventory/Arsenal,
Wallet/Ledger, Rewards/Drops, Crafting, Season Pass, Auction и Entitlements не
разносятся на сетевые микросервисы только ради числа процессов. Покупка лота,
списание покупателя, зачисление продавца, комиссия и передача предмета должны
оставаться одной локальной транзакцией. Влияние Corp не становится торгуемой
валютой. Тип владельца предмета должен быть явным: `account | corporation`,
а не совпадением строковых ID. Сейчас корпоративный склад использует
`accountId = corpId`; перед переносом нужно обнаружить и разрешить
неоднозначности исторических записей.

**Commerce, наоборот, выделяется отдельным trust boundary**: каталог платных
предложений, заказы, payment/rewarded-ad provider adapters, webhooks,
refund/chargeback и секреты провайдеров не должны жить в процессе, который
владеет боевой симуляцией или таблицами арсенала. Commerce не выдаёт игровые
ценности SQL-записью — он отправляет идемпотентную entitlement-команду
Meta/Economy.

Модули ядра остаются чистыми и общаются через шину. Межсервисные вызовы происходят
в адаптерах сервера, вне `applyAction`/`advanceTo`. Состав модулей, версия данных и
снаряжение закрепляются на матч; выключение сервиса не меняет правила уже идущего боя.
Sector Zero использует общий код, но автономный забег не получает обязательной
сетевой зависимости от Meta/Economy/Commerce/Corp. Локальное сохранение не служит
доверенным доказательством серверной награды.

Внутри каждого мета-домена разделяем доменные правила, сценарии приложения и
адаптеры HTTP/БД/межсервисного транспорта. Владельцы данных в таблице не означают,
что это разделение уже выполнено во всех существующих классах. Проверяемые слои —
MSVC-6; сеть и административный доступ — MSVC-7/8; проверки компрометации — MSVC-9.
Отдельный [Staff/Support](staff-case-roadmap.md) и два служебных пульта — OPS-4.3/4.4/4.5:
case-bound полномочия ограничивают злоупотребления сотрудников. Это отдельный
служебный контур, а не обязательная зависимость игрового ядра или готовая реализация.
Backup repository, collector/audit store, SIEM и реагирование развёртываются
независимо от игровых процессов и Staff. [Контракты и матрица отказов](security-operations-roadmap.md)
относятся к SE-3.5/8.1/8.4/8.5/9.2; backup/restore скрипты и локальные security-события
частично реализованы, off-host среда и SIEM/response ещё не подтверждены.

## Контракты, обязательные до следующего выделения

Это общие требования к выделению доменов. Локальный settlement и контракт
Commerce → Meta v0 уже реализованы; корпоративные leases и остальные будущие
контракты не следует считать выполненными вместе с ними.

1. Версия контракта, bounded payload и deadline; синхронные обращения не входят в
   горячий путь боя. Каждый домен владеет runtime-ролью БД, пулом, CPU/RAM/pids и
   лимитами очереди; соседний сервис не читает и не пишет его таблицы напрямую.
2. Изменяющая команда имеет `commandId`, тип, версию, actor, целевого получателя
   и хеш канонического payload. Receipt записывается атомарно с изменением.
   Повтор того же ID/payload возвращает прежний результат; тот же ID с иным
   payload отклоняется. Timeout означает **неизвестный исход**, а не разрешение
   создать новую команду. API статуса позволяет восстановить результат.
3. Game атомарно фиксирует итог и задания доставки в своей БД. Получатель
   дедуплицирует по событию/команде; доставка как минимум один раз, эффект один.
   Версия aggregate защищает от нарушения порядка. Нужны ограниченные batches,
   backoff с jitter, справедливость, контроль возраста backlog и карантин с
   операторским replay. Переполнение не должно терять уже сохранённые результаты:
   новые операции ограничиваются до приёма, существующие данные сохраняются.
4. Авторизация ограничена доменной операцией. Corp выдаёт одноразовое разрешение
   конкретному предмету, получателю, матчу и версии прав; Meta/Economy проверяет его
   при аренде, хранит receipt и reserve/use lease. Смена роли и отмена разрешения
   имеют явную точку отсечения; кэш членства не разрешает новые передачи при отказе.
   Передача предметов при роспуске корпорации — отдельный долговечный workflow.
5. Между хостами HTTPS с проверкой сертификата и приватная сеть; идентичности
   сервисов и credentials раздельны, доступ разрешён конкретным операциям.
   Существующий HMAC Corp не объявляется полной zero trust архитектурой.
   Ротация ключей/отзыв, проверка audience и ограничение capability должны войти
   в контракт следующих сервисов; JWT signing secret не раздаётся потребителям.
6. Readiness проверяет только обязательные локальные ресурсы. Недоступность
   необязательного домена не выключает Game readiness и не запускает каскад
   рестартов. Ошибка наружу — стабильный код; логи не содержат ключей, токенов и PII.

Существующие `ava_result_delivery` и `corp_return_audit` — конкретные долговечные
механизмы, а не уже реализованный универсальный outbox. Не добавляем Kafka, service
mesh или Kubernetes как обязательную основу; начинаем с текущего PostgreSQL и
ограниченных HTTP-адаптеров, измеряем, затем выбираем инфраструктуру.

## Покупки без лишней распределённой транзакции

Решение владельца 2026-10-15 отменяет прежний план физически отделять Auction от
Inventory. **Auction — модуль Meta/Economy, а не самостоятельный сетевой сервис.**

Покупка игрового лота выполняется внутри одной локальной транзакции Meta/Economy:

1. запирается/проверяется лот и право продавца;
2. проверяются provenance/soulbound и доступ покупателя;
3. списываются Варранты покупателя;
4. зачисляется продавцу сумма за вычетом комиссии;
5. комиссия отражается в ledger как sink;
6. предмет/партия материалов меняет владельца;
7. лот закрывается и записывается стабильный receipt.

Так сохраняется сильная сторона текущего `PostgresMetaMarket.buy`: деньги,
комиссия и предмет не расходятся по сетевым saga. Повтор того же `tradeId`
возвращает прежний результат; гонка двух покупателей и отмена против покупки
сериализуются локальной БД.

Распределённый workflow нужен **не между Auction и Inventory, а между Commerce и
Meta/Economy**. Commerce после подтверждения провайдера атомарно фиксирует order/
payment receipt у себя и передаёт entitlement-команду со стабильными
`orderId / providerTransactionId / accountId / productId / payloadHash`.
Meta/Economy применяет её exactly-once в своей локальной транзакции и возвращает
receipt/status.

- Потерянный ответ после применения entitlement означает неизвестный исход:
  Commerce спрашивает status и повторяет **тот же** commandId/payload.
- Refund/chargeback не даёт Commerce прямого SQL-доступа к арсеналу: применяется
  отдельная доменная команда с явной политикой возврата/блокировки entitlement.
- Клиентский callback покупки или rewarded-ad не является доказательством выдачи.
- Недоступность Commerce останавливает новые платные покупки, но не матчи, F2P
  награды, крафт и аукцион.
- Недоступность Meta/Economy не позволяет подтверждать выдачу игрового товара;
  Commerce сохраняет подтверждённый платёж/заказ и повторяет ограниченную доставку.

Публичное включение торговли по-прежнему требует условий Фазы 3 экономического
роадмапа; выделение Commerce само по себе не закрывает EC-0.4/EC-3/EC-6.

## Проверяемая карта отказов

Ниже **целевые** гарантии. Сегодня процессно выделены только Corp; прочие требуют
этапов ниже. Пока Game DB/процесс — общая точка отказа матчей, auth и инвентаря.

| Отключённый блок | Продолжает работать | Ограничение и восстановление |
| --- | --- | --- |
| Corp/API или Corp DB | Обычные матчи, личный инвентарь, уже закреплённый бой AvA | Новые корпоративные изменения/AvA блокируются; итог и аудит догоняют из Game |
| Commerce/API или Commerce DB | Матчи, Corp, F2P-награды, крафт, Season Pass-прогресс и аукцион Meta/Economy | Новые платные заказы/реклама недоступны; уже подтверждённые provider orders доставляются после восстановления по receipt/status |
| Meta/Economy API или DB | Уже начатые матчи с закреплённым loadout, самостоятельные операции Corp, фиксация payment order в Commerce | Арсенал, кошельки, крафт, сезонная выдача, Auction и применение entitlement блокируются; Game/Commerce сохраняют durable намерения до восстановления |
| Один match worker | Другие workers, API, инвентарь и Corp | Его комнаты восстанавливаются из durable снимков; возможен reconnect/временная пауза |
| Profile/statistics/notifications | Матчи и первичные доменные записи | Проекции и доставка запаздывают; новые действия с обязательной проверкой уровня fail-secure |
| Auth/API или его DB | Только уже установленные сеансы workers в пределах установленной политики сессии | Новый вход/присоединение блокируются; политику срока/отзыва нужно реализовать и проверить |
| Staff/Support или его DB | Обычные матчи и обычные доменные операции игроков | Заявки и новые служебные принятия недоступны; уже принятые команды/receipt восстанавливаются без повторного эффекта |
| Collector/SIEM/backup/response | Обычная игра и подтверждённые локальные receipts | Собственные bounded backlog/RPO/incident controls; sensitive actions ограничиваются до принятия при exhaustion, recovery — по отдельному учению |
| Общий хост, общий PG-кластер, сеть или диск | Только компоненты на независимых ресурсах | Процессное разделение не обеспечивает HA; нужны раздельные ресурсы и учение восстановления |

Нельзя при сетевом сбое молча переключаться на Memory или старую копию БД:
это создаст вторую истину. Пока подтверждение домена недоступно, UI не сообщает
успех. Отказ подтверждения не является основанием выдать валюту/предмет повторно.

## Последовательность небольших PR

### MSVC-0 · Фундамент исходящих вызовов `[srv]` ✅

Сделано: общий `DependencyGuard`, интеграция corporate HTTP обоих входов,
проверки лимита, открытия/пробы/восстановления, устаревших завершений и независимых
доменов. Реальный HTTP-тест удерживает 16 корпоративных запросов и проверяет
доступность игрового маршрута. Эта карта и контракты задают следующий этап.

### MSVC-1 · Контракт Meta/Economy и совместимость `[srv]` ⏳

**Частично реализовано:** локальные reward/craft/season/trade/entitlement используют
общую транзакцию, provenance и receipts; Game сохраняет observation/activity до
доставки. Остаются совместимость всех legacy-писателей, явные account/corporation
владельцы и общий контракт аренды/equip.

Продолжение: инвентаризация **всех** писателей
предметов/кошельков/материалов (награды, starter, equip, consume, аренда,
MetaMarket, реализованные крафт/сезон), явные типы владельца и provenance, idempotency
receipts и запрет обхода soulbound/reserve. Внутренние модули получают один
application transaction boundary; HTTP/SQL не протекают в доменные правила.

Отдельно фиксируется контракт Game → Reward Settlement:
`matchId/accountId/result facts` записываются durable до доставки, Meta/Economy
дедуплицирует эффект. Не менять баланс выдачи в PR архитектурного переноса.

**Готово, когда:** найдены все пути записи ценностей; trade/reward/craft/entitlement
имеют однозначную семантику и idempotency; гонки покупки/аренды/equip/replay не
дают двойного эффекта.

### MSVC-2 · Самостоятельный Meta/Economy `[srv]` 🔒(MSVC-1)

При появлении эксплуатационной причины — отдельный entrypoint/БД/runtime-роль для
единого Meta/Economy. Внутри процесса остаются Inventory/Arsenal, Wallet/Ledger,
Rewards/Drops, Crafting, Season Pass, Auction и Entitlements. Game доставляет
награды/износ/возвраты durable-командами; Corp выдаёт scoped разрешения на аренду.

Переход поэтапный: сначала совместимый локальный adapter в нынешнем
`packages/server`, затем переключаемый remote adapter; двух параллельных
источников истины не допускается.

**Готово, когда:** выключение Meta/Economy не останавливает активный бой; после
рестарта награда/износ/trade/entitlement применяются однократно; Game/Corp не
пишут его таблицы напрямую.

### MSVC-3 · Отдельный Commerce service `[srv][sec]` ⏳

**Предыдущий план этого ID — самостоятельный Auction — superseded решением
2026-10-15.** Auction остаётся модулем Meta/Economy ради локальной атомарности.

**Основа v0 реализована:** отдельные entrypoint, схема/роль PostgreSQL, каталог,
orders/provider receipts/outbox, status/retry/refund и HMAC с audience/capability,
ротацией ключей и durable nonce. Контрактные тесты включают настоящую PostgreSQL
и Commerce → Meta HTTP. Реальные provider adapters и эксплуатационное подключение
ещё не выполнены; готовность платежей не заявляется.

Commerce использует отдельный entrypoint, DB credentials и secret namespace.
Владеет каталогом платных offers, orders, payment/rewarded-ad provider adapters,
webhooks, refunds/chargebacks и provider receipts. Он **не** владеет арсеналом,
Варрантами, Season Pass state или игровыми лотами и не имеет SQL-доступа к их БД.

Единственный путь выдачи ценности — versioned/idempotent entitlement-команда в
Meta/Economy. Provider retry, двойной webhook, потерянный ответ после commit,
refund и restart покрываются контрактными тестами.

**Готово, когда:** повтор одного provider transaction не выдаёт предмет дважды;
падение Commerce не останавливает F2P игру/аукцион; падение Meta/Economy не теряет
подтверждённый заказ, но и не позволяет Commerce объявить игровую выдачу успешной
без receipt.

### Изоляция комнат · Существующие SV-4.1 / OPS-2.1 `[srv]`

Это уточнение уже существующих кирпичей, не второй проект шардинга. API/Lobby
и ограниченное число workers; группируем комнаты по допустимому радиусу отказа,
не выделяем микросервис на каждый корабль/бой. Единственный writer матча через
lease **с fencing epoch в атомарном persist/receipt**, а не один lease-таймер.
Старый владелец не пишет и не рассылает после потери lease. Reconnect/drain,
планировщик и pinned версии должны переживать передачу комнаты. Установленный
WSS не должен зависеть от процесса Auth/API: API выдаёт маршрут и join-token,
а отдельный WSS ingress соединяет браузер с worker. Общий ingress остаётся
собственной границей отказа и требует отдельной проверки HA.
**Готово, когда:** SIGKILL/OOM одного worker не останавливает другой; stale writer
отклонён БД; состояние, sequence, квитанции и per-player туман не нарушаются.
БД матчей остаётся отдельной критической зависимостью: это не обещание HA PostgreSQL.

### MSVC-4 · Фоновые потребители по измеренной нагрузке `[srv]` ⏳

Сначала выделить контракт доставки и проекции результатов; один consumer-процесс
может обслуживать рейтинг/статистику/уведомления, пока нет причины разделять их.
Связать с OPS-0.1/0.2/0.3 и MED-1, сохранить принадлежность текущих медалей Corp
до отдельного согласованного переноса. Auth/OIDC не выносить попутно ради схемы.
**Готово, когда:** отказ потребителя не теряет первичный результат и не тормозит
бой; повтор/неправильный порядок событий не удваивает прогресс. Доставка внешних
уведомлений использует idempotency провайдера, если она доступна; без неё возможный
повтор при потере подтверждения описывается явно, а не обещается exactly-once.

### MSVC-5 · Автоматизированное учение отказов `[ops]` ⏳

Начать с существующей пары Game/Corp, затем расширять на каждый реально появившийся
сервис. Синтетические данные и локальные тестовые БД; выключение процесса и его БД,
задержка/обрыв ответа после commit, переполнение bounded очередей, disk-full и OOM
только внутри принадлежащих учению ресурсов. Ни живые аккаунты, ни общий Docker
daemon не являются целью аварийных инъекций.
**Готово, когда:** reproducible CI/stand smoke фиксирует независимую readiness,
доступность соседних API, сохранность данных, latency/error budget, backlog age и
время восстановления; доказан нулевой повторный эффект и нет пропавших команд,
которые сервер подтвердил как успешно записанные. Порог p95 задаётся на измеренном
стенде; текущие 2s/16/3/5s — предохранители, не обещание SLO всей игры.

## Доменные слои, сегментация и проверка доверия

### MSVC-6 · Доменные правила и границы слоёв `[srv]` ⏳

Для Meta/Economy, Commerce и Corp инвентаризировать правила и смешанные
HTTP/SQL-классы. Доменные правила принимают данные и возвращают решение без сети,
SQL, Fastify и чтения env; время и необходимые значения передаются явно. Сценарий
приложения проверяет actor/полномочия, координирует транзакцию и receipts через
порты; адаптеры реализуют хранение, транспорт и сериализацию стабильных `E_*`.
Допустимые зависимости: адаптер → приложение → домен; порты принадлежат приложению,
композиция зависимостей находится во входе сервиса. Пакеты и DI-framework ради схемы
не обязательны. Чистые правила метаэкономики не переносятся в боевой `shared-core`.
**Готово, когда:** есть карта правил/портов каждого домена, чистые тесты бизнес-решений,
контрактные тесты адаптеров и исполняемая проверка запрещённых импортов. Контрпример
с импортом HTTP/pg в домен делает проверку красной; оба игровых входа используют
одни правила. Выполнять по доменам вместе с MSVC-1/2/3, без общего переписывания игры.

### MSVC-7 · Сегменты и разрешённые соединения `[ops][sec]` ⏳

Превратить [целевую матрицу](service-architecture-map.md) в версионируемую политику:
source identity/segment → destination identity/segment → protocol/port → operation,
отдельно ingress и egress. По умолчанию запрещено; разрешён ответ на установленное
соединение, но это не право инициировать обратный запрос. Разделить edge, API, workers, Meta/Economy, Commerce, Corp, data-сегменты каждого
владельца и management.
Начать с имеющихся Game/Corp; новые домены добавлять при их появлении. Один общий
private bridge и отсутствие published port не обеспечивают изоляцию соседей:
нужны отдельные сети/точки маршрутизации и реально исполняемые ACL/firewall.
Конкретный механизм выбрать под стенд; Kubernetes/service mesh не обязательны.
Связать с SE-0.3, SE-1.2/1.3, SE-2.1/2.2, SE-3.1/3.2: раздельные identities,
проверяемый TLS, scoped audience/operations, ротация/отзыв и отсутствие admin-секретов
в runtime. mTLS либо подписанные scoped-токены выбираются в контракте; нахождение
в разрешённой сети не заменяет авторизацию команды. При mTLS scope и права actor
проверяются в API дополнительно к сертификату. DNS, доставка алертов, secret-
store и backup требуют собственных ограниченных разрешений, а не общего egress.
**Готово, когда:** на воспроизводимом стенде разрешённые пути проходят, остальные
недостижимы из каждого сегмента; Commerce не соединяется с Game/Corp/Meta DB
напрямую, Meta/Economy не получает provider secrets, runtime не достигает
управляющих поверхностей management, БД не доступны из интернета.
Политика переживает
restart/redeploy, журналирует отказы и имеет проверенный откат без временного allow-all.
Публичный cutover каждого нового домена требует такой проверки его связей.
Staff получает отдельные ingress/data ACL; owner → Staff authorize/consume/status
разрешается только для служебной admission, вне обычного игрового пути.

### MSVC-8 · Отдельный административный канал `[ops][sec]` ⏳

Выбрать приватный VPN/access gateway либо bastion с сильной аутентификацией;
описать operator → management → конкретный хост/мигратор/restore, сроки доступа,
отзыв и аварийный доступ. Отдельные credentials и журналы; приложение не получает
SSH, Docker socket, права мигратора/restore или возможность читать чужие секреты.
Административные инструменты подключаются к конкретной БД временно и адресно;
backup читает свой домен отдельной ролью, offline restore-key не хранится в runtime.
Это операционное продолжение SE-2/3/5/8/9 и существующего
[runbook ролей и внедрения](security/zero-trust-rollout.md), не новый публичный API.
**Готово, когда:** SSH, панели управления и административный доступ к БД недоступны
напрямую из интернета и игровых сегментов; вход оператора проходит только через
защищённую точку доступа;
проверены вход оператора, отзыв доступа, аудит без секретов и аварийное восстановление.
Закрытие административного канала не отключает игровые соединения и процессы.

### MSVC-9 · Проверки компрометации и ограниченных полномочий `[srv][sec][ops]` ⏳

Начать с доступных Game/Corp, расширять вместе с MSVC-6/7/8 и MSVC-1/2/3.
В принадлежащем тестам стенде имитировать захваченный runtime и украденные его
credentials, не администратора всей инфраструктуры. Проверить запрещённые сетевые
переходы, прямой доступ к чужой БД, подмену service identity/actor/audience,
просроченный/отозванный ключ, replay и команду вне разрешённой области.
Отдельно: Commerce с украденной service identity пытается выдать произвольный
предмет/Варранты без подтверждённого order/provider transaction — Meta/Economy
отказывает. Meta/Economy с украденными credentials не может обращаться к payment
provider или подделать статус оплаты, потому что provider secrets ему не выдаются.
Для Auction внутри Meta/Economy отдельно проверяются гонки двух покупателей,
отмена против покупки, soulbound/provenance и replay одного tradeId; локальная
атомарность не отменяет actor/authz-проверок.
**Готово, когда:** каждый запрещённый сценарий отказан без изменения ценностей,
обхода ролей или чтения чужих данных; разрешённая операция работает; события
отказов попадают в аудит. Тесты обнаруживают намеренное ослабление ACL или scope.
Приёмка нового домена требует этих негативных проверок и MSVC-5; зелёные SAST/DAST
общего сервера не заменяют их и не объявляют живую инфраструктуру проверенной.
Для сотрудников дополнительно проверяются самоповышение через тикет, чужое дело,
отзыв назначения, обход суммарных лимитов и изменение аудита (OPS-4.4/4.5).

## Внедрение и остановка расширения — условия переключения

Каждый следующий сервис вводится отдельно: green contract/failure tests →
подготовленные роли/схема → проверенные зашифрованные backup/restore → freeze всех
писателей → dry run и сверка данных → перенос → canary → контроль receipts/backlog →
открытие записей. До новых записей возможен возврат на старую конфигурацию;
после них нужен обратный перенос. Dual write без восстановления запрещён.

Выпуск сервисов должен поддерживать совместимость N/N-1 API/event schema,
expand/contract миграций и конкретный rollback runbook. Секреты, сеть, TLS,
ресурсы и backup каждого домена проверяются независимо. Общий проверенный образ
разрешён; отдельный deploy не должен принудительно обновлять соседние процессы.

Ближайший порядок: MSVC-1 вместе с доменными слоями MSVC-6 → MSVC-2 → MSVC-3.
MSVC-7/8/9 можно начинать на имеющихся Game/Corp; они являются условиями безопасного
cutover каждого нового домена, а не необязательной работой после публичного запуска.
Учение MSVC-5 можно начинать уже на Corp; изоляцию workers вести через SV-4.1/OPS-2.1
при подтверждённой нагрузке.
MSVC-4 вводить по реальной потребности, без дробления на пустые сервисы.

Разделение достаточно, когда наиболее вероятный отказ отключает одну механическую
область, её данные восстанавливаются, а соседи укладываются в согласованные бюджеты.
Не добавляем новый процесс, если он лишь увеличивает цепь синхронных обращений и
не уменьшает радиус отказа, не даёт независимого масштабирования/выпуска или владения данными.
