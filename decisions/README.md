# `/decisions` — чистые решения, общие для обоих клиентов

Здесь живут **решения**, которые одинаковы для прототипа и для `packages/client`:
«что показать вместо списка», «куда вести игрока после отказа», «какой маршрут у
приказа», «можно ли нажимать кнопку». Чистая функция + типы + тесты рядом. Ни DOM, ни
сети, ни таймеров, ни `Date.now()`.

## Зачем папка вообще появилась

Поток REFM вынес из `prototype/src/main.ts` больше сотни таких решений — и каждое легло
внутрь пакета прототипа. `packages/client` их не видит и пишет свои: `welcomeScreen`,
`matchHud`, `mapRender`, `camera` существуют в обоих местах отдельными реализациями.
Получилось, что рефакторинг улучшает ровно тот клиент, который планируется заменить, а
миграция от него не приближается.

Прецедент общего кода в репозитории уже был и работает без единой строки конфигурации
сборки: `/localization` лежит в корне, оба клиента импортируют его относительным путём,
и вопроса «как перенести переводы» не существует — переносить нечего. Эта папка устроена
так же.

## Что сюда кладут

- Решение, от которого зависит, **что увидит игрок**, но которое не рисует само.
- Всё, что можно проверить тестом без браузера.
- Правила с причинами в шапке файла — почему именно так, а не иначе (стиль соседних
  `browserFallback.ts`, `errorRoute.ts`, `orderRoute.ts`).

## Что сюда НЕ кладут

- **Правила мира** — они в `packages/shared-core`. Здесь только клиентская сторона:
  что показать и куда вести, а не что произошло в игре.
- **Разметку и рисование** — они остаются у хозяина экрана.
- **Текст для игрока** — он живёт в `/localization` по ключу. Отсюда можно ссылаться
  на ключ, но не хранить строку (гейт `prototype/src/i18n.test.ts` сканирует и эту
  папку).

## Как это собирается

Ничего специального. Оба клиента импортируют относительным путём, esbuild и Vite
следуют за импортом сами. Три места, где папка упомянута явно:

- `vitest.config.ts` — `decisions/**/*.test.ts` в `include`;
- `prototype/tsconfig.json` — `../decisions/**/*.ts` в `include`;
- `prototype/src/i18n.test.ts` — папка в списке потребителей `/localization`.

Сам контракт папки держит `shared.test.ts` — он читает КАТАЛОГ (не список имён, который
забыли бы дописать) и проверяет три правила: из `/decisions` не импортируют `prototype/`,
исходники чистые, у каждого решения есть тест рядом. Первое правило и есть смысл папки:
один такой импорт молча возвращает решение в прототип, и «общее для обоих» перестаёт
быть правдой. Запрещён именно ИМПОРТ — тест вправе ЧИТАТЬ файл прототипа как фикстуру
(`netClientReuse.test.ts` так сканирует `main.ts`), это не связь сборки.

## Что переезжает разом, а что по дороге

**По умолчанию — по дороге:** новое кладём сюда, старое переезжает, когда его и так
трогают. 222 модуля `prototype/src` перевозить скопом незачем — стоимость миграции
лучше размазать по обычной работе, чем ставить отдельным проектом.

**Исключение — связная цепочка, которая нужна второму клиенту ПРЯМО СЕЙЧАС.** Правило
«по дороге» писалось, когда на вопрос «зачем везти сейчас» ответа не было. У сетевого
входа он появился: `packages/client` не умеет ни войти, ни выбрать матч, ни занять
место — а решения для всего этого уже написаны и покрыты тестами, просто лежали внутри
прототипа. Возить их «когда тронем» означало бы писать их заново, и REFM-поток именно
это и делал: улучшал тот клиент, который планируется заменить.

Разом везём, когда выполнено всё:

1. модули **чистые** и самодостаточные (`shared.test.ts` это теперь проверяет);
2. у каждого **есть тест**, и он переезжает вместе с модулем;
3. они образуют **одну цепочку**, а не выборку «что попалось»;
4. **гейт зелёный с тем же числом тестов** — перевозка не меняет поведение, и это
   видно по счётчику, а не по обещанию.

Так переехал вход в сетевой матч (17 модулей: адрес сервера → вход → обзор матчей →
обмен сессии на место → дозвон → приветствие → реконнект → маршрут отказа). Остальные
~150 чистых модулей прототипа ждут своей причины.
