# RuStore: учение удаления и проверка сборки — 18 октября 2026

Статус: техническая подготовка player-клиента Void Dominion. Это не разрешение
на публикацию и не юридическое заключение. [Порядок выпуска](../security/rustore-preparation.md).

## Удаление и восстановление

`node deploy/account-erasure-drill.mjs` создаёт собственный PostgreSQL-контейнер
из закреплённого compose image. Production URL не принимает. Игра и корпорации
намеренно находятся в одной БД, как на текущем playtest-сервере. Настоящий
`proto-server.mjs` работает с минимальными runtime-правами; `PROD=0`, listener
только loopback. Проверяется boot guard и DB privileges, а не весь public-release
preflight. Данные и ключи синтетические; рабочие БД не копировались.

Пройдено на PostgreSQL 16.15:

1. Реальная HTTP-регистрация двух аккаунтов; вход с пустым паролем отвергнут.
2. Три события телеметрии с общей установки: анонимное и два авторизованных.
3. Подписанный Ed25519, зашифрованный age бэкап **до** запроса удаления через
   штатный `deploy/backup.sh` и `pg_dump` той же версии, что PostgreSQL.
4. Проверка пароля удаления, очередь 202, повтор того же запроса после условной
   потери ответа и немедленный отказ во входе удаляемому аккаунту.
5. Отказ maintenance executable при работающем runtime, включая idle-подключение.
6. Остановка сервера и очистка общей БД/JSONL: профиль, прогресс, кошелёк,
   регистрационная награда и членство удалены; чужие данные побайтно сохранены.
   Корпорация сохранилась, другой участник стал главой. Личная квитанция удалена,
   общая сохранилась без удалённого участника. Чужое событие на общем устройстве
   сохранено без install/session-связи.
7. Штатный `deploy/restore.sh` восстановил старый зашифрованный бэкап: удалённый
   пользователь снова присутствовал в закрытой БД, очередь ещё отсутствовала.
   Guard был установлен, runtime отказался запускаться с `E_DB_BOOT`.
8. Независимый реестр повторил удаления; повторный replay безопасен. После
   перезапуска удалённый аккаунт не входит, второй входит, прежний ник зарезервирован.
   Проверка `--pending` возвращает штатный код 3 для пустой очереди.

Подтверждены и исправлены два дефекта: CLI создавал два pool при одинаковых URL
и блокировал сам себя; служба обращалась к executable, который сборка не создавала.
Регрессия CLI проверяется на реальном PostgreSQL, защита от живого подключения
сохранена. Отдельные существующие тесты покрывают две БД и отказ start-hook.

[Машинный отчёт](rustore-release-drill-2026-10-18.json) хранит время, image digest,
SHA-256 входных исходников, бэкапа и двух тестовых APK.
Время восстановления маленькой синтетической базы — измерение только этого
учения, не обещание RTO production. Приватные ключи, дампы и содержимое реестра
в Git не включаются.

## Android

Проверка выполняется с отдельным `com.voiddominion.syntheticdrill`, временным
тестовым сертификатом, локальным HTTPS-fixture и явно синтетическим текстом
политики. Такой APK не предназначен для магазина или реальных игроков.
Использованы Capacitor 8.5.3, OpenJDK 21.0.12.1, Gradle 8.14.3, Android platform
36; AGP выбрал build-tools 35.0.0, подпись и zipalign проверены tools 36.0.0.
Java и SDK извлечены в отдельный рабочий каталог, глобальная конфигурация VPS
не менялась. Linux command-line tools 15859902 сверены с SHA-256 официальной
[страницы загрузки Android](https://developer.android.com/studio).

Реальный `assembleRelease` обнаружил `HardcodedDebugMode`: запрет отладки перенесён
из исходного Manifest в release build type; финальная проверка отвергает debug APK.
Отсутствующий флаг допустим: его [значение по умолчанию — false](https://developer.android.com/guide/topics/manifest/application-element#debug).
Проверено внутреннее разрешение AndroidX Core
[для неэкспортированных receiver](https://developer.android.com/agents/skills/security/android-intent-security/SKILL):
разрешён только собственный package ID и `protectionLevel=signature`. Любое
постороннее разрешение или ослабление защиты блокирует артефакт.

Финальная проверка также сверяет точный текст политики и её инертную HTML-обёртку
с approved hash; одного наличия CSP недостаточно. Упакованный Capacitor config
должен иметь тот же appId, https-схему, `cleartext=false` и не содержать дополнительных
server overrides. Это защищает от случайного копирования dev-конфига при пересборке.
`allowBackup=false` проверяется, но поведение переноса между устройствами зависит
от производителя и остаётся частью device QA (ограничение описано в Android docs).

Собраны и проверены две версии с одним тестовым сертификатом
`5b8401e09189a8b26059ee2634363d903677e631d5e3c3cec56c4413c31224c3`:

| versionCode | versionName | SHA-256 APK |
| --- | --- | --- |
| 1 | 0.0.1-drill | `6e397589c564a9c7f6a1f34bd52959f94ab8f7b653b4853e815f77a95b2434a1` |
| 2 | 0.0.2-drill | `b915a336c6754b9a93bce8f310d9f5fc0e6a36e928abf5230ba04072a675c333` |

Обе прошли `zipalign -c -P 16 4`, `apksigner verify` и `verify-rustore.mjs`.
Проверка разрешений нашла только INTERNET и внутреннее signature-разрешение AndroidX.
Подготовлен повторяемый `mobile/rustore-smoke.mjs` и workflow
`.github/workflows/rustore-smoke.yml`: настоящий assembleRelease, одноразовый ключ,
локальный HTTPS-fixture, проверка подписанного APK. В CI сохраняется только JSON
проверки; тестовый APK и ключ удаляются. Workflow не имеет production-секретов.

Физическое устройство и аппаратное ускорение Android Emulator здесь недоступны;
установка/обновление и поведение Android WebView этим прогоном не подтверждены.

## Проверка рабочего сервера без изменения данных

18 октября: 10 legacy `meta_economy_receipts` с `account_ids IS NULL`, очередь
удаления пуста, guard снят. Проверка только на чтение доказала принадлежность всех
10 записей: 2 reward-facts по исходному ключу и SHA-256 исходного JSON, 2 settlement
по проверенным reward-facts и canonical fingerprint, 6 season-day по точным хешам
исходного дня и пары accountId/requestId. Догадки по response не используются.
Обработчик повторяет проверку при остановленном runtime и заполняет только
`account_ids` в транзакции; ключи, ответы, fingerprint и балансы не меняются.
Неизвестные, неоднозначные или повреждённые записи по-прежнему блокируют удаление.
Изолированное учение включает legacy-квитанции обоих игроков: своя удалена,
чужая сохранена после точного восстановления принадлежности.

В текущем каталоге журналов 6 JSONL, права каталога 0700 и файлов закрыты от
группы/остальных. Найдена одна analytics salt в действующих и сохранённых конфигурациях;
все 10 уникальных actor в текущих журналах воспроизводятся этой солью
по существующим аккаунтам. Необъяснённых actor в текущем inventory нет. Production-удаление пока выключено.

## Что требует владельца

- Определить оператора, адрес для обращений, географию основной и резервной копий;
  утвердить политику, сроки хранения, обращения и применимые организационные меры
  по [чек-листу ПДн](../security/rf-personal-data-readiness.md).
- Утвердить итоговый package ID и владельца release key, обеспечить защищённую
  независимую резервную копию ключа. Тестовый ключ учения не использовать.
- Предоставить доступ к RuStore Консоли и сведения издателя. Подтвердить возрастную
  анкету и фактическую монетизацию; текущий профиль допускает выключенный Commerce.
- Проверить установку и обновление на физических Android-устройствах, работу
  WSS/CORS, офлайн-обучение, удаление, политику, поворот и слабую сеть.

После этих решений инженерные действия остаются за сопровождающим: применить проверенное заполнение
legacy-принадлежности, настроить независимый защищённый ledger и резервирование,
обработчик из текущего подписанного image, hooks и timer, проверить maintenance/restart на production,
затем включить кнопку удаления. Не перекладывать настройку сервисов на игрока.


## Черновик описания для карточки

Название: **Void Dominion**. Краткое описание: «Космическая стратегия: развивайте
владения, собирайте флот и объединяйтесь в корпорации».

Текст: «Возглавьте космические владения в стратегии реального времени. Развивайте
планеты, управляйте флотами и участвуйте в сетевых партиях. Объединяйтесь с другими
игроками в корпорации и выбирайте направление развития. Для сетевой игры нужны
интернет и аккаунт; знакомство с управлением доступно в обучении».

Это заготовка на основе действующего player-профиля, а не опубликованная карточка.
Перед отправкой сверить с финальным APK и статусом тестирования. Скриншоты для
магазина нужно снять с финального Android-профиля: вход, карта реальной партии,
управление флотом, корпорация. Не использовать dev-панели, синтетическую политику,
генерированные макеты и чужие игровые аккаунты. Возрастную анкету не заполняли
предположениями; наличие пользовательского общения должен оценить издатель.
