# Персональные данные игры: защита и подготовка к запуску в РФ

Рабочий реестр обработки и критерии допуска Galactic War / Sector Zero к публичному релизу. Технические меры, решения оператора и доказательства проверяются раздельно.

## Статус и границы

На 2026-10-18 оператор, его реквизиты, контакт для обращений и размещение всех
хранилищ владельцем ещё не определены. Поэтому это **подготовительный комплект,
не опубликованная политика и не заключение о соответствии 152-ФЗ**. Плейтест с
данными реальных людей не считается освобождением от требований к обработке.
Синтетические фикстуры предпочтительны для разработки, CI и пентеста.

Исполняемая точка входа контейнера — `prototype/netserver.ts`; второй серверный
вход — `packages/server/src/main.ts`. Общие auth/profile/WS-модули защищают оба.
Автоматическая установка подписанного образа не означает правового допуска.

## Реестр данных и потоков

| Данные | Цель и место обработки | Кто получает | Правило подготовки |
| --- | --- | --- | --- |
| Позывной, внутренний ID, scrypt-хеш, nonce отзыва | `users`, вход и связь с игровым аккаунтом | Auth и ограниченные runtime-роли | Не собирать ФИО/паспорт/телефон для обычной игры; хеш и nonce никогда не выдавать |
| Необязательная почта | `users.email`, восстановление через SMTP | Auth, выбранный почтовый обработчик | Не использовать для рекламы; занятый адрес не перепривязывается; проверки владения адресом отдельного подтверждения сейчас нет |
| Session/join/reset JWT | Авторизация, браузерное хранилище, HTTP/WS | Только свой клиент и нужный сервер | Не включать в логи, URL отчётов, тикеты, CI; выход отзывает все сессии и join-токены аккаунта |
| IP и сетевые признаки | TLS-прокси, transient rate-limit, сетевой стек провайдера | Инфраструктурный оператор | Уточнить логи провайдера отдельно: отсутствие access-log приложения не означает отсутствие обработки IP |
| Места, действия, состояния и архивы матчей | `matches`, `seats`, `receipts`, JSONB состояния | Участники по правилам видимости, сервис игры | В дампах искать также позывные и свободный текст; удаление одной строки `users` не удаляет данные из матча |
| Профиль, прогресс, XP, медали | `player_profiles`, `profile_progress`, `profile_credits`, `commander_*`, `medals` | Владелец; другим — ограниченная карточка | Чужая карточка показывает позывной, XP, выбранные медали и их пороги; точные приватные счётчики не выдаются |
| Друзья, присутствие, членство корпораций | `friend_edges`, `corp_members`, `corp_ready`, `player_ready`, AvA | Сервисы и игроки по соответствующим API | Социальные связи тоже включены в реестр; accountId не считать анонимным только из-за UUID |
| Инвентарь, кошельки, рынок, квитанции | `arsenal`, `corp_arsenal_rent`, `meta_*`, `drop_*`, AvA-журналы | Владелец, контрагент в необходимом объёме, уполномоченный оператор | Не уничтожать чужие сделки; правовое основание и срок сохранения каждой квитанции определяются отдельно |
| Push endpoint и ключи | `push_subscriptions`, выбранный push-провайдер | Сервис уведомлений и провайдер | Проверить географию и трансграничную передачу; удаление аккаунта должно прекращать подписку |
| Подтверждённое присутствие аккаунта | `player_activity_channels`, `player_activity_days`: account FK, случайный канал/sequence, server time и union интервалов UTC | Game; Grafana получает только суточные общие числа | 30 календарных дней, очистка при pulse/scrape не чаще раза в час; erasure/FK cascade удаляют строки. Без IP/ника/почты; цель и основание входят в решение оператора. [Контракт](../../deploy/observability/PLAYER-ACTIVITY.md) |
| Install/session ID, HMAC actor, события, FPS | `playtest-logs/client-*.jsonl`, `match-*.jsonl` | Только операторская аналитика | Это псевдонимизация, не доказанное обезличивание; срок ниже; нужность каждого события обосновать |
| Резервные копии, WAL, выгрузки поддержки | Хост и отдельное backup-хранилище | Раздельные backup/restore роли | Включить все копии в географию, сроки, уничтожение и restore-учение |
| SDK площадок, SMTP, push, хостинг, поддержка | По включённым функциям/договорам | Названные обработчики | GitHub получает код и синтетические тесты; реальные дампы, логи и обращения не передавать в GitHub/ИИ-инструменты без отдельного основания и оценки потока |

Источник структуры: `packages/server/src/store/postgres.ts`, `profileStore.ts`,
`authApi.ts`, `telemetryApi.ts`, `analyticsActor.ts`, `playerActivity.ts`. При добавлении таблицы, SDK,
платежа или новой цели этот реестр пересматривается до включения функции.

## Уже реализованные технические меры

- TLS/CSP, проверка Origin/JWT, scrypt, ограничения запросов, контроль полномочий,
  отдельный мигратор и проверка минимальных прав runtime — существующая база.
- `POST /auth/logout`: nonce отзыва записывается в `users` до успешного ответа;
  старые session/join JWT отклоняются, игровые соединения аккаунта закрываются.
  Семантика — **все устройства**, а не выбор одной сессии. Пароль остаётся прежним.
  Отказ БД/сети не показывается клиентом как успешный серверный выход.
- `/metrics/recent`: только оператор, `n` — десятичное целое 1–200; читается
  асинхронно не более 1 MiB. `total` относится к прочитанному окну,
  `truncated` сообщает об отсечении; путь файла не выдаётся.
- Ответы API получают `Cache-Control: no-store`; необработанные ошибки HTTP
  не пишутся целиком в журнал, где могли бы оказаться SQL-параметры/почта/токены.
- Регистрация не выдаёт `E_EMAIL_TAKEN`: если почта уже занята, новый аккаунт
  создаётся без неё. Форма объясняет это заранее. Уникальность публичного позывного
  остаётся видимой (`E_LOGIN_TAKEN`); это явно выбранная граница, не обещание
  полной защиты регистрации от временного анализа и перебора публичных имён.
- Чужой профиль не содержит полных счётчиков прогресса. Для выбранных медалей
  возвращаются только пороги полученной степени, необходимые текущему клиенту.
- `DailyJsonl`: новые каталоги/файлы 0700/0600, строка до 64 KiB, очередь
  ограничена. Раз в UTC-день при flush удаляются только обычные файлы своего
  префикса с датой старше 30 дней. Симлинки и посторонние файлы пропускаются.
  Ошибка очистки даёт `E_JOURNAL_RETENTION`, не скрывается как успешная очистка.
  Права уже существовавших файлов автоматически не меняются.

30 дней — инженерный лимит диагностических журналов, **не срок, назначенный
законом всем данным игры**. Это до 31 календарного дня с учётом дневных файлов;
на выключенном сервере очистка произойдёт при следующем flush. Доказательства
инцидента перед истечением срока переносятся в отдельное защищённое дело с
основанием, ответственным и сроком пересмотра. Docker/systemd/провайдерские логи
и резервные копии требуют собственных настроек ротации.

## Применимость требований РФ

Сверка источников: 2026-10-18. Перед фактическим релизом нужна повторная проверка
действующих редакций и фактической модели бизнеса.

- По [152-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_61801/) фиксируются
  цели, основания, минимальный состав, получатели и сроки. Для необходимой
  обработки аккаунта оценивается договорное основание; рекламу и необязательную
  аналитику нельзя автоматически включить в него. Политика должна быть доступна
  до сбора; оператор оформляет уведомление РКН либо документирует применимое
  исключение, а не предполагает его из статуса «игра».
- Согласие, когда оно является основанием, оформляется отдельно от других
  подтверждаемых документов; отказ от необязательной цели не закрывает игру.
  Нужны версия текста, цель, момент выбора и отзыв; предустановленная галочка
  не заменяет действие пользователя. Основание:
  [ст. 9](https://www.consultant.ru/document/cons_doc_LAW_61801/6c94959bc017ac80140621762d2ac59f6006b08c/).
  Публикация ПДн неограниченному кругу лиц проверяется отдельно по
  [ст. 10.1](https://www.consultant.ru/document/cons_doc_LAW_61801/591acc70f577873c1ee54765eda110b7a0271eaf/).
- Для баз, используемых при сборе ПДн граждан РФ, проверяется локализация;
  в проектной конфигурации game/corp/telemetry/backup размещаются в РФ.
  Флаг `RU` и IP-геолокация не доказывают физическое размещение. Нужны договор
  и сведения провайдера, включая копии. Трансграничные SDK/SMTP/push — отдельный
  анализ и, когда применимо, уведомление до передачи. См.
  [разъяснение Минцифры от 12.05.2025](https://www.consultant.ru/document/cons_doc_LAW_511584/)
  о ч. 5 ст. 18 и ст. 12; это разъяснение, не самостоятельный закон.
- Модель угроз, оценка вреда, определение уровня защищённости и подбор мер
  оформляются по фактической ИСПДн. Автоматически приписывать игре «УЗ-4» нельзя.
  Основания: [ст. 19](https://www.consultant.ru/document/cons_doc_LAW_61801/ca9e5658710519f09ab2fdb8196fcb3eb024a051/),
  ПП РФ №1119 и [приказ ФСТЭК №21](https://www.consultant.ru/document/cons_doc_LAW_146520/).
  TLS, сканер или шифрование диска сами по себе не закрывают все меры.
- Для несовершеннолетних определить возрастную аудиторию и порядок участия
  представителя, если он требуется; не собирать паспортные сканы «на всякий случай».
  Для игрового чата отдельно оценить применимость обязанностей по 149-ФЗ,
  а для контента, рекламы и платежей — возрастную маркировку, 38-ФЗ, 54-ФЗ и
  потребительские требования по реальной модели распространения. Эти вопросы
  **не признаны автоматически применимыми или закрытыми**: нужен отдельный вывод.

## Обращения: проект регламента для утверждения

1. Опубликовать контакт и назначить ответственного/замещающего. Завести закрытый
   журнал: номер обращения, тип, дата получения, срок, основание, исполнитель,
   результат. Не использовать публичный GitHub issue для обращений с ПДн.
2. Проверить принадлежность аккаунта соразмерным способом; чужой ник или знание
   email не являются доказательством. Не выдавать токены, парольные хеши,
   чужие сообщения или данные контрагентов в ответе.
3. Доступ/исправление/ограничение/отзыв/удаление рассматриваются отдельно.
   Для доступа ориентир — 10 рабочих дней, предусмотренное законом продление
   требует мотивированного уведомления. См.
   [ст. 20](https://www.consultant.ru/document/Cons_doc_LAW_61801/7aeb0acd5aa76dbc888a07e52ca06a92568c6e96/).
4. Для удаления составить перечень по реестру выше: обе БД, JSONB матчей/чат,
   социальные связи, подписи push, файлы по actor/install, выгрузки, обработчики
   и резервные копии. Отдельно назвать сведения, сохраняемые на ином основании,
   срок и ограничение доступа. Обезличенный игровой результат может сохраняться
   только после проверки отсутствия возможности связать его с человеком.
5. Выполнение проводить на проверенном плане с транзакциями и журналом результата.
   `DELETE FROM users` недостаточен и может оставить данные/сломать экономику.
   Перед возвратом восстановленной БД в сеть повторно применить журнал исполненных
   удалений. Учение должно показать, что старый backup не возвращает удалённые ПДн.
6. Сообщить результат и оформить доказательство уничтожения по применимым
   требованиям РКН; данные самого обращения также имеют обоснованный срок.

Сроки уточнения/прекращения/уничтожения различаются по основанию; не назначать
один универсальный срок. В частности, ст. 21 предусматривает 7 рабочих дней
для подтверждённого уточнения, 3 рабочих дня для прекращения неправомерной
обработки, 10 рабочих дней для требования о прекращении с предусмотренными
исключениями, и случаи 30-дневного уничтожения. Для невозможности своевременного
уничтожения предусмотрен отдельный режим блокирования. См.
[ст. 21](https://www.consultant.ru/document/cons_doc_LAW_61801/d3fe43a7c415353b17faab255bc0de92bea127da/).

**Статус исполнения:** подготовлены очередь удаления, обработчик двух БД/журналов
и replay после restore ([инструкция](rustore-preparation.md)). До включения на проде
обязательны утверждённые сроки, конфигурация обслуживания и сквозное учение.
Автоматический export всех данных пока не реализован; обращения на доступ
обрабатываются по этому регламенту с проверкой полноты.

## Инцидент: карточка и учение

Зафиксировать время обнаружения UTC, версию, затронутые системы/категории,
предполагаемый объём и вред, ответственного, меры ограничения и контрольные сроки.
Изолировать утечку, отозвать необходимые учётные данные, сохранить ограниченный
набор доказательств с контролем доступа; не публиковать дамп в отчёте.
При установленном инциденте, подпадающем под ч. 3.1 ст. 21, первичное уведомление
РКН — в течение 24 часов от выявления, результаты расследования — в течение 72
часов от выявления. Ожидание полного расследования не переносит первый срок.
Источник: [ст. 21](https://www.consultant.ru/document/cons_doc_LAW_61801/d3fe43a7c415353b17faab255bc0de92bea127da/).
Отправляет уполномоченный человек через действующий канал РКН; приложение ничего
не отправляет автоматически. Учение использует синтетические данные и проверяет
замещение ответственного, часы отсчёта, доступ к форме и доказательства доставки.

## Исполняемая проверка запуска

`deploy/privacy-release.example.json` намеренно пустой и проверку **не проходит**.
После утверждения заполнить копию вне репозитория. Для evidence указать абсолютный
путь и SHA-256 документа; все четыре хранилища требуют подтверждения размещения.
Запуск: `python3 deploy/privacy-readiness.py /absolute/path/privacy-release.json`.
Проверяется комплектность, хеши, права файлов и свежесть ревью (до 90 дней);
содержимое/ПДн в диагностический вывод не попадает. Checker не читает договор
как юрист, не определяет географию по сети и не подтверждает истинность заявления.

Для публичного релиза в host env: `PUBLIC_RELEASE=1`, `PROD=1`,
`PRIVACY_RELEASE_MANIFEST=/absolute/path/privacy-release.json` и рабочая проверка
независимых backups. `production-preflight.sh` отказывает до изменения работающего
стека, если privacy evidence отсутствует либо backups отложены как playtest.
По умолчанию PUBLIC_RELEASE не включён: это защита штатного пути выпуска,
не способ юридически переименовать публичную обработку в «тест».
Прямой запуск контейнера в обход deploy-preflight этим checker не контролируется.

Владелец должен утвердить факты и пройти оставшиеся проверки. До этого нельзя
объявлять игру полностью соответствующей требованиям РФ или считать набор
документов заменой исполненным процедурам.


## Подготовка RuStore и обработчик удаления

Реализован технический путь удаления и барьер восстановления; включение и учение
описаны в [инструкции RuStore](rustore-preparation.md). Production-учение ещё обязательно. Чат
`MatchRoom.chatHistory` хранится в памяти, а не в JSONB матчей; остановка runtime
очищает его. Реестр удалений — отдельное защищённое хранилище ПДн и тоже входит
в локализацию, сроки хранения, резервирование и контроль доступа.
