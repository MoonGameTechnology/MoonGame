# Publish PR — единый ритуал публикации

Цель: готовая работа должна оказаться в удалённой ветке GitHub и получить PR без
прыжков между несовместимыми транспортами и без циклов на auth.

## 0. Что считается готовым

До публикации должны быть известны:
- целевой репозиторий и base = `main`;
- локальная ветка/рабочее дерево с законченным изменением;
- критерий готовности задачи;
- проверки выполнены, если владелец не просил их пропустить.

Если владелец явно сказал «без проверок», не добавляй тесты/гейт самовольно, но
финальный sync с `main` и проверку публикации всё равно делай.

## 1. Финальный sync перед публикацией

Сразу перед удалённой записью:
1. обнови сведения о текущем `main`;
2. сравни локальную задачу с ним;
3. если работа начата от старого `main`, перенеси её на свежий `main` до PR;
4. если перенос мог изменить поведение — повтори затронутые проверки;
5. после sync зафиксируй локальный diff/commit, который именно и должен попасть в PR.

Не открывай заведомо stale/diverged PR.

## 2. Выбери ОДИН write-транспорт

В hosted/web-сессии при доступном GitHub connector/API **предпочитай его сразу**.

Не делай `git push` просто потому, что `git fetch` сработал: публичное чтение не
доказывает наличие terminal write-credentials.

Если terminal `git push` уже был выбран и один раз вернул auth/credentials error:
- НЕ повторяй его;
- НЕ переключайся потом обратно на terminal push;
- переходи к GitHub API fallback ниже.

### 2.1 MCP transport failure — отдельный класс блокера

Ошибки уровня transport/session происходят **до нормального ответа GitHub API**. К ним
относятся, в частности:
- `Invalid MCP request metadata`;
- connector unavailable / disconnected;
- malformed or invalid request metadata на границе MCP;
- session/transport failure, когда GitHub HTTP status/response вообще не получен.

При такой ошибке:
1. Считай текущий GitHub MCP transport неисправным для write-операций в этой сессии.
2. **Не повторяй тот же MCP-вызов.** Один transport failure уже достаточен.
3. **Не переходи на `create_blob/create_tree/create_commit/update_ref` через тот же MCP.**
   Это не другой fallback, а тот же сломанный transport под другой GitHub операцией.
4. Разрешён максимум **один переход на действительно другой write-транспорт**:
   - terminal Git, только если write-credentials уже подтверждены;
   - отдельно авторизованный GitHub client/app/connector, если он реально независим от
     упавшего MCP-сеанса.
5. Если независимого write-транспорта нет — публикация считается заблокированной.
   Не повторяй реализацию задачи и не создавай новые ветки «на удачу».

Перед остановкой зафиксируй recovery checkpoint:
- имя локальной ветки;
- локальный commit SHA (если работа ещё не закоммичена — сначала создай локальный commit);
- SHA свежего `main`, относительно которого подготовлена работа;
- краткий список changed files, отдельно отметив бинарные ассеты;
- какие проверки уже прошли / какие были пропущены по просьбе владельца;
- точный текст transport error.

Сообщение владельцу должно говорить, что **код/арты готовы локально, но remote branch/PR
не созданы из-за transport failure**. Никогда не выдавай локальный commit за опубликованный.

Новая сессия/восстановленный независимый transport должна продолжить **с recovery
checkpoint**, а не выполнять задачу заново.

## 3. Preflight GitHub до PR

Проверь:
- нет ли уже remote-ветки для этой задачи;
- нет ли уже открытого PR с тем же head;
- если PR есть — переиспользуй его, не создавай дубль;
- если PR уже в merge queue, ветку не обновляй: queued head считается замороженным.

Если remote-ветка ещё не существует и terminal push недоступен — используй раздел 4,
**но только если GitHub connector/API transport исправен**. После transport-level ошибки
из §2.1 этот API fallback через тот же connector запрещён.

## 4. GitHub API fallback: локальная ветка → remote без git push

Это канонический fallback для готового локального commit/дерева.

GitHub Git Data API позволяет создать blobs, tree, commit и затем передвинуть branch ref.
Это работает и для текста, и для бинарных ассетов.

### 4.1 Зафиксируй точный набор файлов

Возьми агрегированный diff готовой локальной ветки относительно свежего `main`:
- added / modified;
- deleted;
- режим файла (обычно `100644`, executable — `100755`).

Не переноси временные файлы, build outputs или локальные артефакты, которых нет в
намеренном diff.

### 4.2 Создай remote branch от свежего main

Через GitHub connector/API создай новую branch ref от SHA текущего `main`.

Не создавай ветку от старого локального base SHA.

### 4.3 Создай blobs

Для каждого added/modified файла:
- UTF-8 текст → create blob с encoding `utf-8`;
- PNG/WebP/JPG/другой бинарный файл → прочитай точные байты локального файла,
  закодируй base64 и создай blob с encoding `base64`.

**Для портретов и других изображений нельзя использовать только текстовый
create/update-file путь. Бинарные ассеты идут через blob.**

Для deleted-файла blob не создаётся.

### 4.4 Собери tree поверх свежего main

Создай tree с `base_tree` = tree SHA свежего `main`.

Tree entries:
- added/modified: `path`, исходный `mode`, `type: blob`, созданный blob SHA;
- deleted: `path`, `mode`, `type: blob`, `sha: null`.

Никогда не создавай неполный tree без `base_tree`: иначе неуказанные файлы могут
выглядеть удалёнными.

### 4.5 Создай commit и обнови ref

1. Создай commit:
   - tree = новый tree SHA;
   - parent = свежий `main` SHA;
   - message = смысл задачи.
2. Передвинь созданную remote-ветку на новый commit через update-ref без force.

API fallback намеренно может схлопнуть несколько локальных рабочих коммитов в один
remote commit: источник истины здесь — итоговое дерево файлов, а не локальная история.

Не force-rewrite уже опубликованную чужую/queued ветку.

## 5. Проверка публикации ДО create PR

Обязательно сравни GitHub `main...remote-branch`:
- `ahead > 0`;
- `behind == 0`;
- список changed files соответствует намеренному diff;
- бинарные ассеты присутствуют в changed files.

Если сравнение не соответствует ожидаемому — PR не создавай. Один раз исправь
публикацию другим способом; повтор той же неудачной операции запрещён правилами anti-loop.

## 6. Create / reuse PR

Только после успешного preflight:
- создай PR в `main`, либо обнови существующий;
- описание = что сделано + как проверено;
- draft только если ещё ожидаются изменения;
- если задача закончена — ready PR.

## 7. Merge queue

Не вызывай generic auto-merge и не вызывай `enqueuePullRequest` вручную.

`.github/workflows/automerge.yml` сам поставит eligible ready PR в merge queue после
required checks. Очередь повторно проверит «свежий main + PR».

Если PR не едет:
1. прочитай sticky-комментарий «🚦 Почему этот PR не вливается»;
2. открой `docs/pr-merge-rule.md`;
3. исправь названный blocker один раз или сообщи владельцу точную причину.

## 8. Definition of done

Публикационная задача закончена, когда:
- remote branch существует;
- GitHub показывает ожидаемый diff;
- PR существует и ссылается на эту ветку;
- если PR ready — он оставлен штатному `automerge.yml`;
- нет готового кода/артов, оставшихся только в локальной среде.
