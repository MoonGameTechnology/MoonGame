# TLS-автодоставка: server и Caddy одной парой

ZTP-1.5 расширяет pull-агент: `DOMAIN` в постоянном `server.env` выбирает TLS-профиль.
Без `DOMAIN` сохраняется прежний путь с одним образом. План —
[zero-touch-prod-roadmap.md](zero-touch-prod-roadmap.md), общая установка —
[deploy/README.md](../../deploy/README.md).

## Что проверяется при каждой выкатке

1. Агент разрешает теги сервера и Caddy в неизменяемые digest refs. Проверяет обе
   cosign-подписи **текущим доверенным** verifier с identity конвейера `image.yml`.
2. Скачивает оба образа. Подписанные OCI labels `org.opencontainers.image.revision`
   должны содержать одинаковый полный SHA исходного коммита. Если один publish job
   ещё не закончен, `E_DEPLOY_AWAIT_IMAGE_PAIR` оставляет текущий стек работать;
   такая пара не попадает в список сломанных релизов.
3. Из server-образа без запуска достаётся его `deploy/`. Для пары выделяется каталог
   `releases/<первые 24 hex SHA-256 от двух refs>/deploy`. Поэтому замена только Caddy
   не удаляет текущую версию скриптов с тем же server digest.
4. Production-preflight проверяет DB-флаги и принятую политику восстановления.
   При `DB_AUTO_MIGRATE=0` сначала поднимается только PostgreSQL (`stack.sh db-up`)
   с ожиданием health не более 60 секунд: старый systemd unit останавливает и БД.
   Затем отдельный job мигрирует схему через host-only `migration.env`; Game до этого
   не запускается. Отказ health БД отменяет миграцию и запуск Game.
5. `stack.sh` собирает base + TLS + release + release-TLS и при наличии host-policy.
   Порт игры остаётся loopback-only. Проверяются локальные `/health`, `/ready` и
   `https://${DOMAIN}/ready` с обычной проверкой TLS-сертификата.
6. Только после успеха атомарно записывается `last-good-release`, затем переключается
   `current`. При отказе возвращаются оба предыдущих образа и прежний `deploy/`.
   Пара, на которой выкатка отказала, не повторяется таймером; `moongame update`
   позволяет оператору сделать осознанный повтор после исправления окружения.

Checkpoint — данные, его никогда не исполняют через `source`:

```text
version=1
server=ghcr.io/moongametechnology/moongame@sha256:<64 hex>
caddy=ghcr.io/moongametechnology/moongame/caddy@sha256:<64 hex>
```

`stack.sh up` читает именно пару: отсутствие/повреждение checkpoint останавливает запуск,
а не смешивает образы разных выпусков. После reboot используются уже скачанные refs
(`--pull missing`); политика backup-preflight при этом продолжает действовать.
Если процесс прерван после записи checkpoint, но до переключения `current`, следующий
прогон завершает принятие проверенной версии скриптов без повторного рестарта игры.
Systemd units принадлежат root и автоматически не переписываются агентом.

## Подготовка существующего хоста

Нужны сервисная учётка с доступом к Docker, Compose с `!override`, действующий TLS/DNS,
сохранённые JWT/DB secrets, выделенные DML/migration роли и файл мигратора. Для установки
нестандартного daemon unit задайте `DOCKER_SYSTEMD_UNIT=moongame-docker.service`
(по умолчанию `docker.service`). `SERVICE_USER`, `INSTALL_DIR`, `STATE_DIR` также
переопределяются; изменение пользователя требует отдельно сверить владение файлами.

Если у хоста есть собственный Caddyfile или Compose-policy, заранее создайте постоянный
оверлей вне каталогов релизов. В `server.env` или окружении установщика задайте:

```dotenv
COMPOSE_EXTRA_FILE=/var/lib/moongame/playtest-policy.yml
```

Этот абсолютный файл применяется последним; только обычный файл без symlink,
root/deploy-owner и без group/world-write. Его каталог, родители и подключаемые файлы
тоже должны быть доверенными. Например, постоянный mount Caddyfile сохраняет запрет
пользовательского `POST /matches`, фильтрацию логов и прочие настройки конкретного хоста.
Перед переходом проверьте итоговый Compose без вывода secrets в общий журнал.
Тома сохраняют имена проекта `deploy`; никаких `down -v` или очистки БД переход не требует.

По умолчанию `BACKUP_POLICY=required` требует реальный host verifier независимого
backup/restore. Если владелец явно отложил это для плейтеста, допустимо заранее задать
`BACKUP_POLICY=deferred-playtest`. Preflight пишет `W_DEPLOY_BACKUP_DEFERRED` и отдельный
маркер DEFERRED; VERIFIED остаётся 0. Это не доказательство восстановления и не разрешение
отключать auth/TLS/DB guards. Ни один из маркеров не сохраняют в `server.env`.

## Доступ к приватным образам

VPS требуется чтение **обоих** пакетов. GitHub-подключение в чате не даёт Docker на VPS
registry credentials. Для приватных пакетов GitHub документирует classic PAT с
`read:packages`; сам пользователь должен иметь Read обоих пакетов, а при SSO токен
нужно отдельно авторизовать. См. [официальную инструкцию GHCR](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).
Права публикации/удаления для хоста не нужны.

Секрет вводят на сервере, не в чат, Git, URL или аргументы командной строки. Для передачи
оператору автоматизации можно создать root-only файл вне checkout с двумя строками
`VOID_REGISTRY_USER=...` и `VOID_REGISTRY_TOKEN=...`, режим 0600, и сообщить только путь.
Установщик принимает эти значения через окружение, сохраняет в `registry.env` (0600)
и делает `docker login --password-stdin` в отдельный `$STATE_DIR/docker` сервисной учётки.
Игра эти credentials не получает. После ротации повторите login/установку, после
отзыва токена таймер перестанет получать новые образы, текущие контейнеры продолжат работать.

## Первый переход и ограничения

До остановки старого юнита установщик делает preflight и `--prepare-bootstrap`:
верификация, pull и извлечение скриптов. Полученные refs сохраняются в `prepared-release`;
`--bootstrap` использует их, даже если за это время тег `main` изменился. Недоступный
реестр или отказ подписи на этапе подготовки не останавливают работающую игру.

Локально собранные образы нельзя объявить проверенным подписанным checkpoint.
При первом переходе такого хоста root-установщик оставляет прежний unit и возвращает
его при отказе bootstrap; checkpoint новой пары появляется только после readiness.
Таймер включается лишь после успешного bootstrap и установки новых units.
Последующие обновления откатываются на прежнюю подписанную пару.

**Перезапуск разрывает WebSocket-соединения.** Время обновления ограничивает
`AUTODEPLOY_WINDOW` (default 04:00–07:00 по часам хоста). Drain/выкатка без разрыва —
отдельная задача OPS-1.1. Изменения module manifest/dataHash могут быть несовместимы
с текущими матчами; перед первым переходом или таким выпуском проверьте кандидата
на изолированной восстановленной БД. Readiness не доказывает восстановление всех матчей.
Мигратор прежнего образа проверяет/согласует SQL-схему, но не отменяет произвольные
изменения данных и не заменяет восстановление БД.

На VPS плейтеста 2026-10-16 доступ GHCR без credentials вернул `unauthorized`, поэтому
активация не выполнена. Для кода проверены shell-сценарии агента/rollback. На настоящем Docker под `moongame`
в отдельном Compose-project подтверждены запуск только PostgreSQL, восстановление
остановленной БД через `db-up` и сохранение probe-данных; тестовый стек удалён. Настоящая
GHCR/cosign-выкатка и восстановление текущих матчей на кандидатном образе ещё не подтверждены.
Полный GitOps (`release.json`, release-PR и одобрение выбранных refs) остаётся ZTP-2.2.
