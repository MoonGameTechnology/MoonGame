# Metrics roadmap — что и зачем измеряем

Метрики Void Dominion: что снимаем на плейтестах, как ловим десинки/баги,
производительность, баланс, продуктовую аналитику (retention/воронка) и (позже)
прод-нагрузку. Брики в формате репозитория (`фаза · id · зона · «Готово, когда»`).
Парные доки: `multiplayer.md` (как тестим), `game-integrity-roadmap.md`
(честность/анти-чит), `operations-roadmap.md` (прод-ops), `deep-technical-roadmap.md`
(ядро), `engineering-review.md` (инженерия), `accounts-roadmap.md` (identity —
фундамент продуктовой аналитики).

Зоны: `[core]` shared-core · `[server]` сервер/комната · `[cli]` клиент/рендер ·
`[tools]` харнесы/скрипты · `[docs]` процесс.

**Исследование для обсуждения:** [вовлечение, удержание и покупки — 13.10.2026](research/2026-10-13-player-engagement-research.md).

**Дополнение для обсуждения:** [игровой маркетинг, метрики и аналитика магазина — 14.10.2026](#marketing-metrics-research-2026-10-14).

## Инвариант: метрики — ТОЛЬКО наблюдение

Сбор метрик не имеет права влиять на симуляцию. Источник данных — уже эмитируемые
доменные события (шина), серверные `ActionReceipt`/`StateDelta` и чистые хелперы
(`hashState`, `diffState`) **вне редьюсера**. Никаких `Date.now()`/счётчиков внутри
`applyAction`/`advanceTo` — иначе ломается детерминизм и реплеи (см. `CLAUDE.md`).
Поэтому все метрики либо считаются на сервере/клиенте поверх событий, либо
постфактум по логу.

## Категории и KPI

### A · Плейтест и связь — приоритет сейчас (ручные тесты 2-х) `[server][cli]`

| Метрика | Что показывает | Как снять | Цель |
|---|---|---|---|
| Connect success rate | надёжность входа | сервер: upgrade-попытки vs выданные `welcome` | > 95% |
| Time-to-connect | задержка входа | клиент: Connect → первый кадр мира | < 3 c |
| Lobby wait | сколько ждали второго | сервер: первый join → старт часов (есть лобби-гейт) | информативно |
| Disconnects / session | стабильность сокета | сервер: `close`-события на матч | < 1 |
| Reconnect success | восстановление | сервер: повторный `welcome` после `close` | > 90% |
| Session length | вовлечённость | сервер: join → последнее действие | информативно |
| RTT (latency) | «отзывчивость» | `ping`/`pong` (есть в протоколе; клиент считает RTT в `MultiplayerClient.onPong`, оверлей показывает FPS · RTT · sync) | p95 < 150 мс |
| Errors / crashes | баги | `pageerror` (клиент) + пойманные throw (сервер) → лог | 0 |

### B · Детерминизм и корректность — инвариант ядра `[core][server]`

| Метрика | Что показывает | Как снять | Цель |
|---|---|---|---|
| **Desync rate** | расхождение клиент↔сервер | `hashState`: сервер кладёт хеш в `delta`, клиент сверяет со своим | **0** |
| Action reject rate + коды | сколько и почему отклонено | сервер: `ActionReceipt {ok, code}` агрегатом | < 5%, без `E_INTERNAL` |
| Replay fidelity | стабильность RNG/реплеев | golden-тесты (`rng.test`) + record→replay→hash в CI (`replayDeterminism.test`, бит-в-бит) | green ✅ |
| Dedup / idempotency | повтор не применяется дважды | receipts по `action.id` (уже есть) | 100% |
| Fog leak = 0 | сервер не шлёт скрытое | проверка: в `delta` игрока нет чужих скрытых сущностей | 0 утечек |

### H · Продуктовая аналитика — retention и воронка `[server][tools]` (нужны аккаунты)

Ключ всех метрик — `accountId` (псевдонимный ID, уже штампуется в join-токен, см.
`accounts-roadmap.md` AC-0.1). **Никакого PII в аналитических событиях** — только
`accountId` + таймстемп + факт события; приватность/консент — брик AC-2.3
(GDPR-база). Жанровая поправка: игра асинхронная (зашёл → приказы → вышел), поэтому
«здоровая» сессия — короткая-но-частая; чек-ины в день важнее длины сессии.

| Метрика | Что показывает | Как снять | Цель |
|---|---|---|---|
| DAU / WAU / MAU + stickiness | ядро аудитории | уникальные `accountId` по логинам за день/неделю/месяц; stickiness = DAU/MAU | stickiness > 20% |
| Retention D1 / D7 / D30 | возвращаются ли | когорта по дню регистрации → доля вернувшихся | D1 > 30%, D7 > 15% (альфа: тренд) |
| Онбординг-воронка | где теряем новичков | события: регистрация → первый матч → первое действие → первый бой → второй заход | падение < 50% на шаг |
| Time-to-first-match | скорость «ага-момента» | регистрация → первый `match.join` | < 5 мин |
| Чек-ины / день на игрока | асинхронная вовлечённость | число сессий `accountId` за день | ≥ 2 (по дизайну жанра) |
| Матчей на игрока / повторные матчи | «второй матч» = крючок | `match.join` по `accountId` | доля со 2-м матчем > 50% |
| Churn signals | кто уходит и когда | нет логина N дней после активности | информативно |
| Донат-воронка (задел) | монетизация | пока нет — колонка на будущее, когда появится магазин | — |

## Роадмап

### M0 · Снятие данных с ручных тестов `[server][cli][docs]` — ✅ реализовано
**Цель:** после каждого живого теста 2-х есть машинные + ручные данные.
**Подзадачи:** (1) ✅ комната принимает `observe`-колбэк (наблюдение, не влияет на
симуляцию) — `RoomObservation` для join/leave/lobby/action/end; прото-сервер
(`prototype/netserver.ts`) пишет per-match **JSONL** в `playtest-logs/` и печатает
сводку по `SIGINT`. (2) ✅ опция `emitStateHash` кладёт `hashState(view)` в каждый
полный снапшот и в дельту игрока раз в 3 с; клиент (`MultiplayerClient.onPong` + сверка
хеша) считает RTT и desync, прото-оверлей показывает **FPS · RTT · sync ✓ / desync ✗**. (3) ✅
`docs/playtest-template.md` — чеклист после теста (связь, баги, что путало, фан 1–5).
**Готово, когда:** один тест → JSONL + заполненный чеклист. *(механика готова и
покрыта тестами `matchRoom.test.ts`; ждёт первого живого прогона на двоих.)*

### M1 · Инструментирование ядра (детерминизм-safe) `[core][server]` — ✅ реализовано
**Цель:** измеримые корректность и нагрузка без влияния на симуляцию.
**Подзадачи:** (1) ✅ read-only **metrics-наблюдатель**: комната эмитит новые
наблюдения `events` (доменные события коммита — бои/захваты/прибытия; спаны
`time.advanced` отфильтрованы как шум), `broadcast` (ms фан-аута + размер
сериализованной дельты per-player) и `timing` (`submit` = advance→apply→(persist→)
broadcast, `advance` = heartbeat-догон); `MetricsAggregator`
(`packages/server/src/metrics.ts`) сводит поток в счётчики/avg/max. (2) ✅
**desync-детектор**: хеш едет в снапшотах (M0) — `MultiplayerClient` сверяет с ним свою
реконструкцию (по куску за кадр), при mismatch шлёт серверу
`desync`-репорт (`ClientDesyncMessage`) и получает **полный `state`-ресинк без
реконнекта** (один запрос за раз; сервер наблюдает `desync` всегда, отвечает с
cool-down 2 с — репорт-шторм не станет DoS). (3) ✅ тайминги + размер дельты в
observe-поток; прото-сервер пишет аномалии (медленно/жирно) в JSONL и печатает
агрегаты (submit/advance/broadcast ms, delta KB, battles/captures/desyncs) в
сводке по SIGINT.
**Готово, когда:** desync измеряется (цель 0), реджекты и тайминги в логах. ✅

### M2 · Клиентская перф-телеметрия + перф-гейт `[cli][tools]` — ✅ реализовано
**Цель:** регресс FPS виден до мерджа.
**Подзадачи:** (1) ✅ headless перф-харнес `prototype/perf.mjs` (`pnpm run perf`) —
реальный рендер-цикл прототипа на fake-DOM (паттерн `uitest.mjs`, без новых
зависимостей — НЕ Playwright, которого в репо и не было): CPU-стоимость кадра
avg/p95/max в сценариях **idle / pan / zoom** (реальные pointer/wheel-хендлеры),
бюджет p95 ≤ 20 мс (idle) / 25 мс (интеракции); нон-блок отчёт в CI (`ci.yml`,
`continue-on-error`), `PERF_STRICT=1` — локальный гейт с exit 1; строка
`PERF_JSON {...}` для трекинга трендов. Меряет main-thread (draw-вызовы — no-op
прокси), не GPU. (2) ✅ клиентский перф-сэмпл: прототип раз в 30 с шлёт
`{fps, rttMs, memMb}` и долгие кадры окна (`MultiplayerClient.sendPerf`, сообщение
`perf`): `longFrames`/`worstFrameMs` по интервалам кадров (порог 50 мс, любой
браузер) и худшую блокировку главного потока `loafMs`/`loafScriptMs`/`loafLayoutMs`/
`loafBy` из Long Animation Frames (только Chromium; `decisions/frameTelemetry.ts`) — сервер
только наблюдает (`client_perf` в observe-поток, per-player rate-limit 5 с,
значения range-валидируются при parse — вне диапазона сообщение дропается / поле опускается, не клампится), агрегатор сводит fps avg/min + rtt avg/max в
сводку плейтеста.
**Готово, когда:** падение FPS на прототипе ловится автоматически. ✅
*(CPU-регресс кадра — харнесом в CI; GPU-замер реального браузера — за скоупом,
если понадобится, это отдельный кирпич с Playwright.)*

### M3 · Сборщик телеметрии + отчёт по матчу `[server][tools]` — ✅ реализовано
**Цель:** из сырья — читаемый отчёт.
**Подзадачи:** (1) ✅ коллектор — append-only JSONL (`playtest-logs/`, писался с M0);
прото-сервер теперь дописывает **последней строкой** `{kind:'summary'}` с полными
агрегатами `MetricsAggregator` при выключении (перед этим в JSONL едут только
аномальные broadcast/timing — иначе отчёту неоткуда взять полные латентности);
Postgres-стор — позже, со Stage 3 (см. `persistence-roadmap.md`). (2) ✅ скрипт
`pnpm run metrics [файл]` (`prototype/report.mjs`, по умолчанию — свежайший лог):
длина матча + лобби, микс действий по типам/игрокам, реджекты по кодам, события,
**контроль во времени** (таймлайн `planet.captured` — кто когда что взял), desync
(с криком при ≠0), клиентские fps/rtt-сэмплы и долгие кадры, латентности submit/advance/broadcast
и размер дельты из summary-строки (без неё — деградация с оговоркой), исход матча.
**Готово, когда:** один матч → один отчёт одной командой. ✅

### M4 · Балансная аналитика + self-play `[tools][core]` — ✅ реализовано
**Цель:** баланс мерить без людей и быстро.
**Подзадачи:** ✅ headless **self-play харнес** `pnpm run selfplay [N] [seed]`
(`prototype/selfplay.mjs`) — AI vs AI на реальном ядре (тот же драйвер-цикл, что
netserver: advance + `aiOrders` каждые 2 игровых часа), seeded и детерминированно
(`SetupConfig.seed` прокинут в `newGame`, покрыто тестом); фэйрнесс — старты и
фракции переставляются по индексу матча, так что win rate по слоту/фракции/старту
разделяются чисто. Агрегаты: win rate по слоту/фракции/**старту**, длина + исходы,
время до первого боя, **snowball index** (доля матчей, где лидер середины выиграл),
usage юнитов/построек + список «мёртвого» контента; `SELFPLAY_JSON` для трендов.
Скорость: ~100 матчей / 3 с (1000 — за полминуты, цель перекрыта).
**Готово, когда:** 1000 сид-матчей → таблица баланса за минуты. ✅
*Первые находки харнеса (и их судьба): старт `C5R1` выигрывал 100% — карта
симметризована по обеим осям, все 4 угла эквивалентны (30/120/210 очков в 1/2/3
переходах у каждого); бот-матчи были гонкой без боёв — ИИ теперь объявляет войну,
отстав на ≥50 очков, гарнизонит планеты-призы милицией, копит ударные группы на
rally-точке и берёт десант (войны в 100% матчей, snowball ~53%, камбэки есть);
мёртвый контент сжался 19 → 15 (mine/refinery/tax_office/militia/scout ожили).
Остались как балансные кирпичи: фракция «экономика» бьёт «урон» ~73/27 — в
бот-мете атакующий структурно проигрывает (усиление урона red до +15% сделало
хуже: 100% blue) — red, вероятно, нужен пассив другого типа; остаточный перекос
стартовой пары ~77/23 — эмерджентные тай-брейки динамики на симметричной карте;
15 продвинутых юнитов/построек ИИ пока не строит (носители, дивизии, форты).*

### M5 · Ops-дашборды и алерты `[server]` 🔒(Stage 3)
**Цель:** прод под наблюдением.
**Подзадачи:** реал-тайм метрики (матчи/игроки, msg/s, p95 latency, error rate,
CPU/mem, cost) + алерты на **desync rate**, error rate, recovery time. Стыкуется с
`operations-roadmap.md`.
**Готово, когда:** дашборд живой + алерт срабатывает на искусственный десинк.

### M6 · Продуктовая аналитика (категория H) `[server][tools]` ⏳
**Цель:** retention, DAU и воронка онбординга считаются из логов, без PII.
**Подзадачи:** (1) **схема аналитических событий** — минимальный набор
(`account.registered`, `session.start`/`session.end`, `match.join`, `match.first_action`,
`match.end`) с `accountId` + таймстемп, пишется в тот же телеметрический стор, что M3
(observe-колбэк сервера — симуляция не трогается); (2) **скрипт `analytics`**: лог за
период → отчёт DAU/WAU/MAU, retention-когорты D1/D7/D30, воронка, чек-ины/день,
доля вторых матчей; (3) приватность: событие несёт только псевдонимный `accountId`
(консент/удаление — AC-2.3, сюда лишь ссылка).
**Готово, когда:** неделя тестов → одна команда → отчёт retention + воронка;
в событиях нет PII (проверено ревью схемы).

## Критический путь

`M0 → M1` — measureable correctness + базовая нагрузка (этого хватает, чтобы тесты
2-х были не «вслепую»). Дальше параллельно: `M2` (перф-гейт), `M3` (отчёты),
`M4` (баланс через self-play). `M5` подключается со Stage-3 сервером; `M6`
(продуктовая аналитика) — после M3, когда есть телеметрический стор и аккаунты
на играбельном пути.

> Старт: **M0–M4 сделаны** — observe-JSONL + хеш состояния (M0); metrics-наблюдатель
> (`MetricsAggregator`), desync-детектор с авто-ресинком, тайминги/размер `delta`
> (M1); перф-харнес `pnpm run perf` в CI + клиентские fps/rtt/mem-сэмплы (M2);
> отчёт по матчу `pnpm run metrics` (M3); self-play баланс `pnpm run selfplay` (M4).
> Остались **M5** (ops-дашборды — со Stage-3 продом) и **M6** (продуктовая
> аналитика — после аккаунтов на играбельном пути).

Материал продолжает [исследование вовлечения от 13.10.2026](research/2026-10-13-player-engagement-research.md).
Область: Sector Zero и основная PvP-игра. Этот раздел не включает SDK, не собирает
данные, не меняет баланс, цены, платежи или статусы M0–M6.

**Граница проверки.** При подготовке прочитан текущий текст этого roadmap; наличие
плана не доказывает наличие работающей продуктовой аналитики. Здесь не проводился
новый аудит всего кода или реальных данных игроков. Научные результаты ниже
пересказаны по доступным страницам публикаций и аннотациям; технические правила —
по официальной документации. Это обзор для проектных решений, не систематический
метаанализ и не обещание роста продаж.

### 1. Ответ на исходную идею: измерять время в магазине стоит

Предложение владельца — засекать, сколько игрок находится во вкладке покупок.
**Принимаем как полезную диагностическую гипотезу, но не как KPI «чем дольше, тем лучше».**
Долгий визит может означать заинтересованный выбор, непонятное описание, ожидание
оплаты или оставленную открытой вкладку. Короткий — как отказ, так и удобную покупку.
Это наши возможные объяснения, а не диагнозы по одному таймеру. Подход к выбору
метрик: сначала цель пользователя, затем сигналы и измерения [R1].

Предлагаемая цель: игрок понимает предложение, принимает свободное решение,
может надёжно получить оплаченный товар и продолжить игру. Измеряем путь
**источник → игровой опыт → возвращение → изучение предложения → оплата → выдача → дальнейшая игра**.
Время просмотра помогает объяснять этот путь, но не заменяет его результаты.

| Наблюдение | Гипотеза, а не установленная причина | Следующая проверка |
|---|---|---|
| Долго изучает детали и покупает | Осмысленный выбор | Какие сведения помогают решению |
| Долго держит магазин открытым без действий | Читает, запутался или отвлёкся | Наблюдение за выполнением задачи, понятность экрана |
| Возвращается к одному товару без покупки | Есть интерес и нерешённое препятствие | Польза, условия, цена и доступность оплаты |
| Быстро покупает и возвращается в игру | Удобный путь для знакомого товара | Подтверждение и своевременная выдача |
| Начинает оплату, но нет подтверждения | Отмена, ожидание или ошибка | Статусы платежа и срок наблюдения |

Не вводить целевое «игрок должен провести в магазине N минут» и не создавать
трение ради увеличения времени. Сочетание «покупок больше, времени меньше» может
быть хорошим результатом для гипотезы о понятности интерфейса.

### 2. Доказательная база и пределы переноса

| Источник | Что удалось проверить | Что применяем к проекту | Ограничение |
|---|---|---|---|
| Rodden, Hutchinson, Fu, 2010, HEART [R1] | Методика пользовательских метрик и перехода от целей продукта к измерениям | Для магазина разделить удобство, успешность, вовлечённость и возвращение | Не исследование эффективности конкретного игрового магазина |
| Sifa et al., 2015 [R2] | На данных 100 000 игроков исследуются прогноз покупки и количества покупок с помощью деревьев решений/регрессии | Поведение можно анализировать совместно; начинать с понятных сегментов и воронок | Предсказание не устанавливает причинность и не доказывает эффект увеличения времени просмотра |
| Hamari et al., 2017 [R3] | Опрос 519 участников; разные мотивы покупки, включая социальные причины, экономическую целесообразность и доступ к контенту | Один визит в магазин может иметь разные цели; проверять мотивы добровольными вопросами | Опросные связи не равны результату рандомизированного вмешательства |
| Dmitriev et al., 2017 [R4] | Обобщены ошибки интерпретации метрик на опыте тысяч экспериментов Microsoft | Не объявлять успех по росту одного промежуточного показателя | Методические примеры из других продуктов, не прогноз эффекта для наших игр |
| GameAnalytics, 2026 Mobile & PC Gaming Benchmarks [R5] | Отчёт обновлён 24.08.2026; данные за 2025 год; мобильная выборка 16 000+ игр с порогом 1 000 MAU; жанровой разбивки нет | Внешний ориентир и напоминание проверять состав выборки | Не норматив для небольшого браузерного PvE/PvP-проекта |

В отчёте [R5] мобильные недельные медианы D1 находятся около 22%, D7 — немного
ниже 4%. Это не наши значения и не рекомендуемые цели. Существующие ориентиры
в категории H выше также нельзя представлять как результаты измерений проекта.
Нужны собственный исходный уровень, определения и сопоставимые когорты.

Официальные руководства GA4 и GameAnalytics описывают события электронной
коммерции, прогресса, реальных покупок и виртуальной экономики [R6][R11]. Это
практическая основа схемы событий, а не доказательство, что установка SDK сама
увеличит продажи. Выбор поставщика аналитики этим документом не производится.

### 3. Как организовать профессиональную работу с метриками

Предлагаемый цикл: сформулировать вопрос → определить событие и знаменатель →
проверить качество данных → найти проблемный участок → проверить объяснение →
испытать изменение → оценить основной результат и побочные эффекты. Такой порядок
опирается на методики выбора метрик и достоверных экспериментов [R1][R4][R9].

Для небольшой команды роли могут совмещаться. Маркетинговая задача — понять,
какой источник приводит подходящую аудиторию; продуктовая — почему она остаётся
или уходит; дизайнерская — что человек понимает и выбирает; инженерная — можно ли
доверять регистрации событий, платежам и выдаче. Нужен один согласованный словарь.

Ниже — **предлагаемые определения v1 для нас**, а не утверждение об одинаковых
определениях во всех сервисах. Активность, границы дня и окно наблюдения должны
быть записаны рядом с каждым отчётом.

| Блок / метрика | Предлагаемый расчёт | Решение и ограничение |
|---|---|---|
| CTR объявления | Клики / показы одного объявления | Проверка привлекательности рекламы; не качество игроков |
| Цена первого запуска | Расход источника / уникальные первые запуски | Для браузера не называть посещение установкой |
| Цена активированного игрока | Расход / игроки источника, достигшие заранее выбранного первого полезного действия | Более содержательная оценка, чем стоимость клика |
| Загрузка и онбординг | Успешная готовность игры / попытки запуска; завершение обучения / начавшие обучение | Отличать техническую потерю новичка от трудного обучения |
| DAU / WAU / MAU | Уникальные игроки с квалифицирующей игровой активностью за день / 7 / 30 дней | Не считать фоновые пинги самостоятельной активностью; не смешивать с прежним отчётом по логинам без маркировки версии |
| Точный D1 / D7 / D30 | Вернувшиеся именно в соответствующий календарный день после первого запуска / исходная когорта | Согласовать UTC или иной единый календарь; не путать с возвратом хотя бы раз за период |
| Продвижение PvE | Начало, исход и повторные попытки миссии; переход к следующей | Не смешивать завершение попытки с успешным завершением миссии |
| Асинхронный PvP | Осмысленные чек-ины, повторные матчи, принятие следующего решения | Длительность сессии сама по себе не цель |
| Конверсия магазина | Уникальные покупатели / уникальные посетители магазина в заданной когорте и окне | Не подменять показателем на визит или на платёжную попытку |
| Выручка на активного игрока | Выручка периода / активные игроки того же периода | Определить состав выручки и валюту; явно указывать включение рекламной выручки |
| ARPPU | Выручка от покупок / уникальные платящие за тот же период | Нужна вместе с долей платящих, не вместо неё |
| Выручка когорты за 7/30 дней | Выручка новых игроков за фиксированный срок / все новые игроки этой когорты | Знаменатель включает ушедших и неплатящих |
| ROAS за выбранное окно | Выручка, отнесённая к рекламной когорте, / её рекламные расходы | Это не прибыль и не доказательство дополнительного эффекта рекламы |
| Товарная и платёжная надёжность | Подтверждения, отмены, ошибки, выдача в срок, возвраты | Отделять платёжный процесс от интереса к предложению |
| Виртуальная экономика | Источники, расходы, остатки и время до доступности улучшения | Не считать трату купленной виртуальной валюты второй реальной продажей |

**Иллюстрация, не наши данные.** При расходе 10 000 ₽ канал А привёл 1 000 игроков,
из них 50 вернулись на D7; канал Б — 500 и 100 соответственно. Первый запуск стоит
10 ₽ против 20 ₽, но вернувшийся на D7 — 200 ₽ против 100 ₽. Дешёвый вход не равен
лучшей аудитории; для вывода о прибыльности этих чисел всё ещё недостаточно.

На раннем этапе опираться прежде всего на наблюдаемую выручку за известный срок.
Прогноз пожизненной ценности игрока (LTV) держать отдельно от фактических данных,
с предпосылками и проверкой на последующих когортах. Не превращать слабый прогноз
в основание для увеличения рекламного бюджета.

### 4. Таймер магазина: что именно считать

Предлагаем различать четыре сигнала, а не один `time_in_store`:

| Сигнал | Определение / интерпретация |
|---|---|
| Открытый магазин | Игровой экран магазина открыт; это не доказательство видимости |
| Видимый просмотр | Магазин открыт, страница/приложение видимы и предложение не закрыто блокирующим экраном; не доказательство внимания человека |
| Наблюдаемые взаимодействия | Открытие описания, смена товара, прокрутка, просмотр примера; это дополнительный сигнал, не обязательное условие чтения |
| Техническое ожидание | Загрузка магазина, блокирующие переходы и платёжная фаза учитываются отдельно |

**Основной диагностический таймер v1:** сумма неперекрывающихся интервалов видимого
просмотра до первого начала оплаты в визите, без блокирующей загрузки. Возврат из
отменённой оплаты начинает отдельную фазу просмотра; её нельзя задним числом
добавить к времени «до первой оплаты». Для визитов без оплаты учитывается видимый
просмотр до известного завершения либо последнего надёжного измерения.

В браузере Page Visibility API даёт сведения о видимости документа; состояние
магазина внутри игры учитывается отдельно. Видимость и фокус — разные свойства.
Для iframe также нужна информация от игрового интерфейса/платформы: простое
CSS-скрытие встроенной области не превращается автоматически в событие смены
видимости документа [R7]. Реальную внимательность этот API не измеряет.

**Предложения по реализации, ещё не код:**

- Использовать монотонные часы на уровне UI/адаптера, не внутри симуляции. Начислять
  интервалы по переходам состояний, а не по количеству срабатываний таймера.
- Передавать порции накопленного времени с `visit_id` и последовательным номером;
  сохранять при смене состояния и периодически. Финальный callback не гарантирован.
  Сервер должен отличать дельты от накопительных снимков и не складывать повторы.
- Помечать незавершённые визиты как неполные. Потерянный хвост не равен нулю; не
  приписывать ожидание до таймаута целиком внимательному просмотру.
- Не считать отсутствие кликов 30 секунд доказательством ухода: игрок может читать.
  Возможная эвристика бездействия — отдельная версионируемая метрика, не замена видимости.
- Разделять визиты, вкладки и игроков. Для пользовательского времени перекрывающиеся
  интервалы нельзя автоматически суммировать; правило агрегации должно быть явным.

Показывать медиану, p75/p90 и распределение наряду со средним; отдельно — долю
неполных визитов. Сравнивать одинаковые единицы: первый визит нового игрока,
повторный визит, все визиты или один агрегат на игрока. Эти выборки не взаимозаменяемы.

### 5. События магазина и покупочная воронка

Названия ниже — **проектный контракт для обсуждения**, не существующий API.
Он адаптирует стандартный принцип событий торговли [R6] и отделение реальных
денежных операций от виртуальных ресурсов [R11]. Корзина не обязательна.

| Событие | Когда возникает | Важные поля / источник |
|---|---|---|
| `store_opened` | Открыт магазин | `visit_id`, источник перехода, контекст прогресса; клиент |
| `offer_impression` | Карточка действительно видима по согласованному правилу | `offer_id`, `offer_version`, место, правило показа; клиент |
| `offer_details_opened` | Открыты подробности | Товар и визит; клиент |
| `checkout_started` | Передана попытка оплаты | `checkout_attempt_id`, товар, цена и валюта |
| `checkout_cancelled` | Площадка явно сообщила отмену | Попытка, нормализованный статус; не выводить из молчания |
| `checkout_failed` | Получена явная ошибка оплаты | Попытка, безопасный код, этап; без реквизитов |
| `purchase_verified` | Доверенный источник подтвердил покупку | Уникальный ключ транзакции провайдера, сумма, валюта; доверенный платёжный контур |
| `entitlement_granted` | Право или товар выданы | Связь с подтверждённой покупкой; авторитетный контур выдачи |
| `purchase_refunded` | Подтверждён полный или частичный возврат | Связь с покупкой и сумма возврата; доверенный источник |
| `store_visit_summary` | Порция или итог визита | Интервалы, счётчики, последовательность, флаг полноты и известная причина завершения |

Для показа карточки можно начать с проектного правила «не менее половины карточки
видимо не менее секунды», проверить его на реальном UI и сохранить версию правила.
Это **не универсальный отраслевой стандарт**. Загрузка товара ниже видимой области
не равна просмотру. Повторные показы дедуплицировать в соответствии с единицей
отчёта; хранить возможность отличить первое знакомство от повторного рассмотрения.

**Путь не всегда линейный.** Подробности можно пропустить и купить с карточки.
У одного визита бывает несколько попыток оплаты. Подтверждение может прийти
позже закрытия магазина. Отсутствие немедленного подтверждения — состояние
ожидания/неизвестности, а не автоматический отказ. Окно конверсии и допустимая
задержка выдачи фиксируются заранее.

Минимальные общие поля: `schema_version`, `event_id`, псевдонимный идентификатор,
время события и получения, платформа, версия игры, визит, товар/версия предложения,
цена и валюта там, где применимо. Источник трафика — из разрешённого перечня,
а не произвольный URL с возможными персональными данными. Для эксперимента —
вариант, назначенный до воздействия. Не передавать весь объект игрового состояния.

Цену хранить целым числом минимальных денежных единиц с кодом валюты; не
предполагать два десятичных знака для любой валюты. Сведение валют, возвратов,
комиссий и рекламного дохода описать отдельно. Статус оплаты не выводить из клика.
Google Play рекомендует проверку покупки в доверенном контуре и защиту от
повторного использования покупки [R8]; у каждой нашей площадки нужно реализовать
её собственный подтверждающий механизм, а не переносить контракт Google Play вслепую.

**Иллюстрация, не реальные данные:** 1 000 посетителей магазина → 600 увидели
предложение → 120 начали оплату → 60 получили подтверждение → 59 получили товар
к установленному сроку. Здесь предполагается один рассматриваемый товар и не
более одной попытки/покупки на участника; в реальном отчёте игроки и попытки считаются
отдельно. Разбираем доступность предложения, понятность/интерес, отмены и ошибки,
а затем одну просроченную выдачу. Среднее время на всех этапах не объяснит эти
разные проблемы. Подтверждённая, но не выданная покупка — задача обслуживания
покупателя, не повод усиливать рекламу.

Отдельные события виртуальных `source`/`sink` нужны для экономики. Покупка валюты
за 300 ₽ и последующая трата валюты на модуль не образуют 600 ₽ реальной выручки.

### 6. Когорты, сегменты и защита от неверных выводов

Предлагаемые разрезы: Sector Zero / основная PvP-игра; платформа; версия игры;
источник привлечения; стадия обучения/кампании; первый или повторный визит;
наличие ошибок; платил ли игрок **до** рассматриваемого визита. Не дробить маленькую
аудиторию на десятки почти пустых групп и не интерпретировать случайный скачок
в одном из многочисленных разрезов как доказанный эффект.

Для каждого отчёта фиксировать начало когорты, квалифицирующую активность, часовой
пояс, длительность наблюдения и доступность данных. D7 считать только для когорт,
у которых седьмой день уже полностью наблюдался. Для выручки за 30 дней нужны
полные 30 дней. Пропуски телеметрии, тестовые аккаунты, боты и неизвестный источник
показываются отдельно; правила исключения задаются до сравнения.

Различать отказ от аналитики и отсутствие активности. Нельзя без оговорки
переносить результаты доступной измерению части аудитории на всех игроков.
Гостевой идентификатор не гарантирует подсчёт людей: очистка хранилища, другой
браузер и другое устройство могут разделить одного человека на несколько записей.
Не заменять эту неопределённость скрытым fingerprinting.

Связь «дольше смотрит → чаще покупает» может отражать исходный интерес, опыт,
стадию игры или источник трафика. Аналогично, покупатели могут чаще возвращаться
уже до покупки. Сравнение покупателей с непокупателями не доказывает, что именно
покупка улучшила удержание. Атрибуция рекламной выручки также не доказывает, что
без рекламы покупки бы не было: для причинного вопроса нужна отдельная контрольная
схема. Общее правило — не подменять причинный вывод описанием группы [R2][R4][R9].

### 7. Применение к Sector Zero и основной PvP-игре

**Sector Zero — предлагаемый путь:** первый запуск → обучение → осмысленное
действие → первая миссия → результат → изменение подготовки → следующая миссия →
возвращение в другой день. На уровне кампании связывать магазин с номером этапа,
попытками и выбранным улучшением; не записывать посещение магазина как завершение
основной игровой цели.

Исследовательские вопросы: понимает ли новичок следующую задачу; что происходит
после первого поражения; умеет ли применить полученное улучшение; какое описание
модуля помогает оценить его пользу. Примеры привязки к спасению учёного, союзным
пингам и другим миссионным механикам — предложения для будущего инструментирования,
а не заявление, что по ним уже собираются данные.

**Основная PvP-игра — предлагаемый путь:** первый вход → матч → приказ → результат
→ следующее решение → возвращение → повторный матч. Сохраняется жанровая поправка
из категории H: короткий осмысленный чек-ин не следует считать плохой сессией
только из-за его длины. Полезно проверить понимание модулей, аукциона, роли Хранителя
и доступных действий, но по каждому вопросу сначала нужен конкретный сценарий.

Не предлагать намеренно усиливать поражения или создавать искусственную нехватку
ресурсов ради продаж. Не превращать время визита и историю неудач в скрытую
персональную наценку. Изучать понятность, добровольную ценность и надёжность покупки.
Для PvP отдельно оценивать справедливость: изменение боевой силы одного участника
влияет на опыт других, поэтому обычная независимая рандомизация по игроку может
не подойти [R9].

### 8. Первые эксперименты и исследования интерфейса

Первый кандидат: «Игроки изучают модуль, но не понимают его эффект. Понятный пример
применения поможет принять решение». Это гипотеза, не обнаруженный дефект.

| Элемент теста | Предложение |
|---|---|
| A / B | Прежнее описание / то же предложение с понятным примером; цена и состав одинаковы |
| Участники | Заранее выбранные подходящие игроки, стабильно назначенные в вариант до показа изменения |
| Основная метрика | Доля назначенных участников с подтверждённой покупкой за фиксированное окно |
| Диагностика | Видимость карточки, подробности, время просмотра, попытки оплаты |
| Защитные показатели | Ошибки, просроченная выдача, возвраты, дальнейшее возвращение в игру |
| Решение | Оценка эффекта и неопределённости; возможен честный результат «данных недостаточно» |

Сравнение только кликнувших или оплативших после воздействия может сломать
рандомизацию. Основной анализ — по первоначальному назначению в вариант; анализ
фактически увидевших предложение допустим лишь с заранее обоснованным правилом,
не создающим смещения отбора. Зафиксировать гипотезу, окно, минимально полезный
эффект, выборку, исключения и правило остановки; проверить баланс распределения
и доставку событий. Не останавливать тест при первом привлекательном результате [R9].

**Иллюстрация мощности, не норма:** для изменения конверсии с 2% до 2,4% обычное
нормальное приближение для двух независимых долей при двустороннем уровне 5%,
мощности 80% и равном распределении даёт около 21 100 участников на вариант.
Формула расчёта: `n ≈ [z(0.975)·sqrt(2·p̄·(1−p̄)) + z(0.8)·sqrt(p1·(1−p1)+p2·(1−p2))]² / (p2−p1)²`,
где `p1=0.02`, `p2=0.024`, `p̄=(p1+p2)/2`. Это не учитывает кластеризацию,
множественные проверки, пропуски и иные особенности конкретного теста.

При небольшой аудитории сначала полезнее наблюдать выполнение конкретной задачи,
проверять понимание цены/срока действия/места выдачи и устранять крупные ошибки.
Предлагаемый добровольный вопрос: «Что помешало принять решение?» с возможностью
не отвечать. Это источник гипотез, не репрезентативная оценка доли всех недовольных.
Разница «три покупки против двух» сама по себе не основание объявлять победителя.

Следующие кандидаты: заметность предложения без навязчивого перекрытия игры;
понятное объяснение выдачи; сравнение вариантов представления одного и того же
набора. Изменять по одной проверяемой причине, не одновременно цену, баланс,
визуал и рекламный источник.

| P0 | Базовый путь первого запуска и качества | Видны попытка запуска, готовность, первый полезный шаг, ошибки; тестовые события отделены |

### 10. Надёжность, приватность и обязательные сценарии проверки

Сбор остаётся **наблюдением вне детерминированного ядра**, как установлено выше.
Сбой необязательной аналитики не должен блокировать игру и завершение покупки.
Это не отменяет необходимость штатного доверенного платёжного учёта и выдачи.
Очередь событий ограничена по объёму; повторная отправка идемпотентна; версии схем
и статусы качества измерений видимы. Клиентские события нельзя считать доказательством
выручки или источником прав на товар.

**Уточнение терминологии категории H:** «без PII» здесь следует понимать как
запрет лишних прямых идентификаторов и чувствительного содержимого, а не обещание
анонимности. Псевдонимные данные, которые можно снова связать с человеком, могут
оставаться персональными [R10]. Необходима отдельная проверка требований рынков,
площадок, целей обработки и механизмов согласия; этот обзор не заменяет её.

Предлагаемый минимум: не включать email, имена, платёжные реквизиты, токены,
свободные тексты чата, полные URL и дампы состояния; ограничить доступ к сырым
данным; определить сроки хранения и удаление; передавать только нужные поля.
Сервисные журналы платёжных обязательств и необязательная маркетинговая аналитика
должны иметь явно разделённые цели и правила хранения. Не собирать скрытый
fingerprint для восстановления личности после отказа от аналитики.

| Сценарий при внедрении | Ожидаемое свойство |
|---|---|
| Магазин открыт, вкладка скрыта/приложение свёрнуто | Видимое время не растёт |
| Игрок читает без кликов | Чтение не обнуляется из-за произвольного idle-порога |
| Товар загружен ниже видимой области | Нет ложного `offer_impression` |
| Долгая загрузка или платёжное окно | Ожидание отдельно от просмотра предложения |
| Возврат из отменённой оплаты | Новая фаза просмотра, предыдущие интервалы не удваиваются |
| Вкладка закрыта без завершающего события | Неполный визит отмечен; неизвестный хвост не выдуман |
| Дубликаты, офлайн-очередь и поздняя доставка | Нет двойного учёта времени, транзакций или выдачи |
| Несколько вкладок или гостевых устройств | Явное правило объединения и известные ограничения идентичности |
| Подтверждение пришло после закрытия магазина | Платёж связан с попыткой и попадает в правильное окно |
| Покупка подтверждена, выдача не состоялась | Есть отдельная ошибка и процесс восстановления |
| Отказ/отзыв согласия там, где оно требуется | Необязательный сбор прекращён; продукт остаётся работоспособным |
| Сравнение воспроизведения с аналитикой и без неё | Наблюдатель не меняет результат симуляции |

### 11. Первый набор отчётов и порядок разбора

Предлагаются четыре небольших отчёта вместо панели из десятков несвязанных чисел:
**привлечение и первый опыт**, **возвращение и продвижение**, **магазин и платежи**,
**качество данных и технические ошибки**. В каждом — размер аудитории, период,
определения, версия игры/схемы и пропуски. Для магазина дополнительно распределение
времени, показы предложений, попытки, подтверждения, выдача и возвраты.

Платёжные проблемы разбираются оперативно независимо от объёма маркетинговой
статистики. На продуктовый разбор выносится один вопрос: где произошло существенное
изменение, какое объяснение проверяется и какое решение принято. Периодичность
подбирается по накоплению сопоставимых данных, а не ради ежедневного победного графика.

Шаблон результата: **вопрос → когорта и окно → качество данных → наблюдение →
альтернативные объяснения → проверка → эффект и неопределённость → решение →
защитные показатели**. Допустимые решения включают «не менять», «исправить ошибку»
и «данных недостаточно», а не только «раскатывать».

**Итоговое предложение владельцу:** включить таймер видимого просмотра как часть
покупочной воронки и сначала обеспечить надёжность данных. Оптимизировать понятность,
добровольную ценность и успешность покупки, а не длительность пребывания в магазине.
