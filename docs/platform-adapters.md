# HTML5 platform adapters — единая сборка для игровых платформ

> Решение о границе: одна HTML5-сборка Void Dominion на общем ядре плюс тонкий слой
> адаптеров, за которым живут SDK площадок. Игровой код зовёт только контракт
> `GamePlatform` (auth, save, ads, iap, analytics) и принимает продуктовые решения по
> capability, а не по названию площадки. Первый порт — PvE для Яндекс Игр; следующая
> площадка подключается новым адаптером, а не форком клиента.
>
> Раздел «Взгляд на монетизацию» — **гипотезы на проверку, а не утверждённый дизайн
> экономики**. Файловая раскладка каталогов здесь тоже не фиксируется: документ задаёт
> границу, а не преждевременный рефакторинг.

## Решение

Void Dominion не должен иметь отдельную кодовую базу под Яндекс Игры, CrazyGames или будущие HTML5/Mini Game-платформы.

Делаем **одну качественную HTML5-сборку игры** поверх общего игрового ядра и вводим тонкий платформенный слой. Игровой код не импортирует SDK конкретной площадки и не знает, где он запущен. Все различия платформ проходят через стабильные интерфейсы-адаптеры.

Первый целевой порт — PvE-версия Void Dominion для Яндекс Игр. Архитектура при этом сразу проектируется так, чтобы следующая площадка подключалась новым адаптером, а не новым форком клиента.

## Зачем

Цель — превратить HTML5-клиент в переносимый канал распространения Void Dominion:

- одна игровая логика и один набор данных;
- исправление баланса или PvE-механики автоматически доступно всем платформам;
- SDK площадок изолированы от доменной логики;
- платформу можно добавить или заменить без переписывания игры;
- platform-specific ограничения (авторизация, облачные сейвы, реклама, покупки, аналитика) не загрязняют `shared-core`;
- Яндекс Игры становятся первым validation-каналом, а не архитектурным тупиком.

## Граница архитектуры

Игровой код обращается только к платформенному контракту:

```ts
export interface GamePlatform {
  auth: PlatformAuth;
  save: PlatformSave;
  ads: PlatformAds;
  iap: PlatformIAP;
  analytics: PlatformAnalytics;
}
```

Конкретная площадка реализует этот контракт:

```text
                       ┌──────────────────────┐
                       │   Void Dominion UI   │
                       │ gameplay / meta / PvE│
                       └──────────┬───────────┘
                                  │
                         GamePlatform contract
                                  │
          ┌───────────┬───────────┼───────────┬────────────┐
          │           │           │           │            │
        Auth         Save        Ads         IAP       Analytics
          │           │           │           │            │
    ┌─────┴───────────┴───────────┴───────────┴────────────┴─────┐
    │                         adapter                            │
    └───────┬──────────────────┬──────────────────┬──────────────┘
            │                  │                  │
         Yandex            CrazyGames          Web/dev
          SDK                 SDK              fallback
```

Например, игра вызывает:

```ts
await platform.ads.showRewardedAd({ placement: 'pve_result_bonus' });
```

Она **не** вызывает `YaGames` или API CrazyGames напрямую. Решение о том, какой SDK и каким способом выполнить запрос, принадлежит адаптеру.

## Три уровня: SDK, площадка, игра (решение владельца 2026-09-22)

Вопрос «что идёт на уровень SDK, а что на уровень площадки» стоит задать до первого
адаптера, потому что ответ на него определяет, где живёт ИДЕНТИЧНОСТЬ игрока — а она
тянет за собой сейв, покупки и требования модерации.

### A. Уровень SDK площадки — внутри адаптера, наружу не видно ничего

`YaGames.init()` и версия лоадера, `ysdk.getPlayer()`, окно авторизации Яндекс ID,
`player.setData/getData/setStats` с их квотами, `payments.*` с подписью и консумированием,
`adv.*`, `getFlags()`, `serverTime()`, `environment.i18n`. Всё, что называется по имени
конкретной площадки.

**Правило, которое это охраняет:** имя `YaGames`/`ysdk` не встречается нигде, кроме
`prototype/src/platform/yandex.ts`. Держится не соглашением, а тестом-сторожем
(`YAG-1.2`): он падает, если `shared-core` узнает про SDK или если в игровом коде появится
`if (platform === 'yandex')`.

### B. Уровень площадки — наш контракт `GamePlatform`, это знает игра

`auth`, `save`, `ads`, `iap`, `analytics` + `capabilities`. Здесь у сущностей НАШИ имена и
наша семантика: три исхода вместо `boolean`, `PlatformPlayer` вместо чужого объекта,
`PortableMetaSave` вместо форматов площадки.

### C. Уровень игры — идентичность Sector Zero

Профиль подготовки (`sector-zero.progress.v1`: модули, звёзды, навыки, Варранты) и то,
ЧЕЙ он. **Владелец профиля — `PlatformPlayer.id`, а не аккаунт нашего сервера.**

### Что из этого следует — и это главное

**Серверный логин Void Dominion (ник+пароль, JWT) в Sector Zero не участвует вовсе.**
Не «пока не подключили», а по устройству: требование площадки 1.2 запрещает требовать
регистрацию или авторизацию на сторонних сервисах, а наш сервер для площадки — сторонний
сервис. Он остаётся там, где он нужен по существу: в основной игре, где есть authoritative
сервер и мультиплеер.

**Гость — полноправное состояние, а не ограниченный режим** (требование 1.2.2). Гостевой
профиль живёт локально, прогресс сохраняется, играть можно всё.

**Повышение до аккаунта площадки — по кнопке и с объяснением выгоды** (требование 1.2.1).
Выгода настоящая и называется прямо: сейв в облаке и доступ с других устройств.

**Покупки — только авторизованному.** Требование 1.13.3 обязывает прогресс при
инап-покупках храниться на сервере и быть доступным одному игроку с разных устройств; у
гостя такого прогресса нет по определению. Документация площадки покупку гостю формально
разрешает, но тогда купленное живёт в одном браузере — это возврат и жалоба. Поэтому наше
правило строже площадки: перед покупкой предлагаем вход, объясняя ровно эту причину.

### Контракт от этого подрос: авторизацию нужно уметь ЗАПРОСИТЬ

До `YAG-1.4` `PlatformAuth` умел только «скажи, кто играет». Требование 1.2.1 обязывает
авторизацию происходить по осознанному нажатию — значит игре нужен способ её попросить, а
UI нужно знать, есть ли кому её показать:

```ts
interface PlatformAuth {
  player(): Promise<PlatformPlayer>;
  /** Можно ли предложить вход ЗДЕСЬ. `false` — кнопки быть не должно (capability-правило). */
  canSignIn: boolean;
  /** Открыть окно площадки. Отказ игрока — это `cancelled`, а не ошибка. */
  signIn(): Promise<PlatformSignIn>;
}
type PlatformSignIn = { status: PlatformOutcome; player: PlatformPlayer };
```

Исходов снова три, и по той же причине: «отказался» и «здесь этого нет» — разные вещи.
**Первоисточник это поддерживает, а не только наш вкус** (`YAG-0.2`, 2026-09-22): окно
открывает `ysdk.auth.openAuthDialog()`, и **отказ игрока ОТКЛОНЯЕТ промис**, то есть
различие приходит от площадки, а не додумывается адаптером. Оттуда же порядок вызовов,
который легко упустить: после успешного входа игрока запрашивают **заново**
(`getPlayer()`), прежний объект остаётся неавторизованным — значит `signIn()` возвращает
НОВОГО `PlatformPlayer`, а не тот же самый с поднятым флагом. Именно поэтому в типе
`PlatformSignIn` рядом со статусом стоит `player`.

**Реализовано `YAG-1.4` (2026-09-23)** — `prototype/src/platform/types.ts` и оба адаптера.
Три детали, которых в наброске выше не было: уже вошедшему окно не показывается вовсе;
окно, закрывшееся «успехом» при всё ещё гостевом игроке, даёт `cancelled`, а не `ok`;
двойной тап ждёт исхода ОДНОГО окна. Веб-адаптер входа не умеет (`canSignIn: false`) даже в
симуляции: аккаунта площадки вне площадки нет.

### Развилка, которую нельзя оставить на потом: слияние прогресса

Гость играл локально, потом вошёл — а в облаке уже есть профиль с другого устройства.
Четыре прочтения, и три из них тихо уничтожают чужой прогресс:

| Вариант | Цена |
| --- | --- |
| (а) облако побеждает | молча теряется всё, что игрок наиграл гостем прямо сейчас |
| (б) локальный побеждает | молча теряется прогресс с другого устройства — хуже: его больше и он старше |
| (в) **спросить игрока, показав оба** | +1 экран выбора; единственный вариант, который ничего не уничтожает молча |
| (г) слить по максимуму каждого счётчика | звучит щедро, ломает экономику: Варранты сложатся дважды при повторной синхронизации |

**Решение: (в).** Экран показывается ОДИН раз, в момент первого входа, честными числами
(«здесь: 12 забегов, 340 ⍟ · в облаке: 40 забегов, 1200 ⍟»). Дальше выбранный профиль
становится единственным. Вариант (г) отклонён явно — записано, чтобы «а давайте просто
сложим» не всплыло второй раз как свежая идея.

**Реализовано `YAG-1.4` (2026-09-24)** — меню Sector Zero, `decisions/cloudSync.ts`. Экран
появляется всякий раз, когда сверка находит прогресс по обе стороны и он разошёлся
(исход `choose`), а не только при первом входе: так же расходятся и два устройства одного
вошедшего игрока. Чисел пять — забеги, главы, три валюты. Деталь, которой в решении выше
не было: «оставить этот» записывает профиль с номером правки ВПЕРЕДИ облачного
(`keepLocalMark`) — со своим номером облако оказалось бы позади сверки другого
устройства, и то молча отправило бы свой профиль поверх выбора игрока.

## Контракты v1

### `PlatformAuth`

Минимальные обязанности:

- определить доступность авторизации площадки;
- получить стабильную идентичность игрока там, где платформа её предоставляет;
- поддержать guest/anonymous fallback, если это разрешено продуктовым сценарием;
- не протаскивать platform-specific player object в игровой код;
- **уметь ЗАПРОСИТЬ вход** (`canSignIn`/`signIn`) — требование площадки 1.2.1 обязывает
  авторизацию происходить по осознанному нажатию игрока, а не при запуске.

Гостевой fallback перестал быть «если разрешено сценарием»: для Яндекс Игр он
**обязателен** (требование 1.2.2), и прогресс гостя обязан сохраняться.

Пример результата:

```ts
type PlatformPlayer = {
  id: string;
  displayName?: string;
  authenticated: boolean;
};
```

### `PlatformSave`

Единая семантика загрузки/сохранения метапрогрессии:

```ts
load(): Promise<string | null>;
save(snapshot: string, options?: { flush?: boolean }): Promise<void>;
fits?(snapshot: string): boolean;
```

Снимок — строка в нашем формате (`decisions/cloudSync.ts`: профиль Sector Zero, дескриптор
забега и точный мир идущего забега — `AUD-24`). Ограничения площадки (размер, сериализация,
квоты, повторы) решает адаптер; промис записи не отклоняется и не висит — облако копия,
источник прогресса локальный (у Яндекса запись без ответа SDK за 20 с — сбой с обычным
повтором, `AUD-34`). `fits` — примет ли площадка снимок по размеру (нет метода — лимита нет):
хост спрашивает до записи и выкидывает из конверта мир забега, а не теряет запись целиком. `flush` — страница
уходит: отправить сразу, а не в окно квоты. `cloudSave` значит «у площадки есть облако для
ВОШЕДШЕГО игрока»; гость живёт локально, и `load()` для него отвечает `null` (`YAG-2.2`).

Важно: состояние активного большого multiplayer-матча не обязано помещаться в platform save. Платформенный save предназначен прежде всего для переносимого PvE/meta-клиента; серверный authoritative state основной игры остаётся серверным.

### `PlatformAds`

Минимальный контракт:

```ts
showRewardedAd(request): Promise<RewardedAdResult>;
showInterstitial(request): Promise<InterstitialResult>;
```

Награду выдаёт **игра только после подтверждённого результата адаптера**. SDK не должен самостоятельно менять мету.

Отсутствие рекламы — нормальное состояние (`unavailable`), а не исключение, ломающие игровой цикл.
Ответ приходит всегда: ролик, который так и не открылся (SDK молчит), адаптер Яндекса через
30 с называет `unavailable` (`AUD-34`) — иначе кнопки рекламы висели бы «занятыми» до конца
сессии. Открытый ролик срок не обрывает.

### `PlatformIAP`

Обязанности:

- запросить каталог доступных продуктов;
- инициировать покупку;
- восстановить/синхронизировать незавершённые покупки, если платформа это поддерживает;
- вернуть игре нормализованную квитанцию/результат;
- не давать игровому UI зависеть от формы ответа конкретного SDK.

Каталог товаров и правила выдачи награды остаются под контролем Void Dominion. Platform product id маппится на наш внутренний product id конфигурацией адаптера.

### `PlatformAnalytics`

Игра эмитит **наш** словарь продуктовых событий:

```text
session_started
onboarding_step
pve_started
pve_completed
pve_failed
rewarded_ad_offered
rewarded_ad_completed
iap_started
iap_completed
meta_unlock
```

Адаптер решает, куда и в каком формате их отправить. Благодаря этому D1/D7, воронка первого матча, повторный PvE, ad opt-in и IAP conversion сравнимы между площадками.

## Capability model

Не все платформы имеют одинаковые возможности. Нельзя разбрасывать по UI проверки вида `if (platform === 'yandex')`.

Адаптер публикует capabilities:

```ts
type PlatformCapabilities = {
  auth: boolean;
  cloudSave: boolean;
  rewardedAds: boolean;
  interstitialAds: boolean;
  iap: boolean;
  analytics: boolean;
};
```

UI принимает продуктовые решения по capability, а не по названию площадки.

Пример: если `rewardedAds === false`, кнопка бонуса за рекламу не показывается; PvE-награда при этом остаётся полностью получаемой без рекламы.

## Адаптеры первой очереди

### `WebPlatformAdapter`

Fallback для локальной разработки, обычного браузера и тестов. Не требует внешнего SDK. Позволяет запускать тот же клиент без Яндекса и детерминированно тестировать success/cancel/unavailable сценарии рекламы и IAP.

### `YandexGamesAdapter`

Первый production adapter:

- Yandex player/auth;
- platform/cloud save;
- rewarded/interstitial ads;
- IAP;
- platform analytics hooks там, где они нужны;
- lifecycle/SDK initialization.

### Следующие платформы

CrazyGames и другие HTML5-площадки подключаются только после стабилизации v1-контрактов на реальном Yandex-релизе. Добавление площадки не должно требовать изменения `shared-core` или PvE-механик.

## Сборка

Предпочтительная модель — общий HTML5 application bundle + platform entry/configuration layer.

```text
packages/
  platform/
    src/contracts/
    src/web/
    src/yandex/
    src/crazygames/       # позже

HTML5 game
  ├── shared-core
  ├── portable gameplay/meta UI
  └── selected platform adapter
```

Точная физическая раскладка каталогов определяется отдельным implementation PR после сверки с текущей PWA/prototype миграцией. Этот документ фиксирует **границу**, а не навязывает преждевременный файловый рефакторинг.

SDK площадки по возможности включается только в соответствующую platform build, чтобы чужие SDK не увеличивали вес и поверхность атаки остальных сборок.

## Взгляд на монетизацию HTML5/PvE — гипотезы на рассмотрение

> Этот раздел **не является утверждённым дизайном экономики**. Это набор продуктовых гипотез, которые имеет смысл проверить на реальных данных первой площадки. Конкретные цены, размеры наград, частоты рекламы и состав пакетов должны приниматься только после плейтестов и первых retention/monetization cohorts.

### Главный принцип

Предлагаемая модель: **донат ускоряет мета-прогрессию, но не создаёт эксклюзивную игровую силу**. Игрок без платежей способен получить gameplay-контент игровым путём; платящий сокращает время до новых вариантов сборки.

Для HTML5 PvE это особенно удобно: монетизация находится преимущественно **между матчами**, а не вмешивается в решения внутри боя.

Целевой цикл:

```text
PvE-матч
   ↓
награды / XP / salvage / meta resources
   ↓
открытие героя / учёного / модуля / варианта сборки
   ↓
новый build
   ↓
следующий PvE-матч
```

Платёж или rewarded ad может ускорить отдельный участок этого цикла, но не должен превращаться в «проигрываю → плачу → победил».

### 1. Rewarded ads — основной рекламный формат

Предпочтение — добровольной рекламе с заранее понятной наградой. Возможные placements для проверки:

- бонус к **мета-награде после завершённого PvE**, а не к результату уже идущего боя;
- дополнительный salvage/контейнер после миссии;
- небольшая порция meta currency/XP;
- дополнительная ежедневная PvE-награда;
- дополнительный reroll/вариант награды, если такая система появится.

Нежелательный вариант — реклама, без которой невозможно продолжить прогрессию.

Награда за просмотр должна быть полезной, но ограниченной: rewarded ads не должны становиться оптимальной стратегией «смотреть рекламу вместо игры».

### 2. Interstitial/fullscreen ads — только естественные паузы

> **Sector Zero от этого формата отказался целиком** (резолюция владельца 2026-09-22, §0.6а [`sector-zero-economy-roadmap.md`](sector-zero-economy-roadmap.md)): реклама там только rewarded по нажатию игрока. Раздел остаётся как гипотеза платформенного слоя — он про любой продукт на любой площадке, а не про первый из них.

На рассмотрение: показывать fullscreen-рекламу только там, где игровой цикл уже остановился сам, например между PvE-сессиями/экранами результатов, и ограничивать частоту.

Не показывать interstitial:

- во время боя;
- во время принятия тактического решения;
- сразу после ошибки/поражения как наказание;
- поверх обучения в момент, когда игрок ещё осваивает управление.

Если данные покажут заметное ухудшение repeat-match rate или retention, interstitial можно уменьшить или убрать: для стратегии долгий LTV потенциально ценнее краткосрочного ad revenue.

### 3. IAP — ускорение меты

Кандидаты для первой товарной матрицы:

- **Starter Pack** — ограниченный набор модулей/мета-ресурсов для более быстрого знакомства со сборками;
- **Module Pack** — тематический набор вариантов модулей;
- **Premium/Meta Currency** — ускорение открытия доступного игровым путём контента;
- пакеты вокруг героев/учёных — только если они расширяют варианты игры, а не продают недостижимую F2P силу;
- косметические товары позднее, когда визуальная идентичность и аудитория достаточно зрелые.

Пакет лучше продавать как **«быстрее открыть новые способы играть»**, а не «стать сильнее всех».

### 4. Чего не стоит продавать в PvE v1

На старте предлагается не продавать напрямую:

- победу в текущей миссии;
- неограниченное воскрешение/перемотку поражения за деньги;
- эксклюзивный модуль, объективно превосходящий доступный F2P аналог;
- обязательный energy gate, который не даёт играть без платежа/рекламы;
- ресурсы активного матча в объёме, превращающем экономические решения в фикцию.

Это не запрет навсегда на любые convenience-механики, а guardrail первой проверки: сначала нужно доказать, что **сам gameplay удерживает**, и только потом оптимизировать монетизацию.

### 5. Реклама и IAP не должны конкурировать друг с другом

Полезно рассматривать две аудитории:

- игрок, который не платит, но добровольно смотрит rewarded ads;
- игрок, который ценит время и покупает ускорение меты.

Не стоит заставлять платящего пользователя проходить через ту же рекламную нагрузку, что и полностью бесплатного. Возможная гипотеза для теста — покупка/пакет, снижающий или убирающий принудительные interstitial, при сохранении добровольных rewarded placements.

> **В Sector Zero эта гипотеза непроверяема, и это следствие §2 выше:** принудительной рекламы там нет, значит снижать нечего, а «покупка отключения рекламы» продавала бы пустоту. Замена, которая там работает, приходит от самой площадки: `player.getPayingStatus()` отличает платившего от неплатившего (§1.1 [`yandex-games-roadmap.md`](yandex-games-roadmap.md)), и документация площадки прямо предлагает показывать такому игроку инап-товар **вместо** предложения рекламы. То есть разгружается платящий не покупкой тишины, а тем, что ему просто не предлагают ролик.

### 6. Ranked и будущий multiplayer

HTML5 PvE не должен заставлять нас проектировать будущий competitive режим как P2W.

Предложение на рассмотрение для основной игры:

- **Ranked 1v1** — нормализованная/честная соревновательная среда без платёжного преимущества;
- обычные режимы используют мета-прогрессию по правилам основного GDD;
- покупка ускоряет получение вариантов сборки, но Ranked не должен определяться стоимостью аккаунта.

Этот принцип не обязательно реализовывать в первом HTML5 PvE-релизе, но platform economy не должна закрыть такую возможность архитектурно.

### 7. Аукцион и корпорации — отдельный будущий экономический слой

Глобальный аукцион и корпоративная экономика намеренно не входят в HTML5 v1, но монетизация не должна подрывать их будущую роль.

Если обычные игроки в дальнейшем добывают ресурсы в матчах и продают их на аукционе, а корпорации расходуют ресурсы на здания и изнашиваемые корпоративные модули, прямой магазин не должен бесконечно печатать те же конечные товары и обходить player-driven economy.

Иначе цепочка

```text
игроки → ресурсы → аукцион → корпорации → производство → война → износ → новый спрос
```

потеряет смысл.

Поэтому premium/meta currency, auction currency и корпоративные ресурсы следует проектировать как **разные экономические контуры**, пока не доказана необходимость их обмена.

### 8. Что измерять до изменения экономики

`PlatformAnalytics` должен позволить сравнивать монетизацию между площадками одним словарём. Минимальный набор продуктовых показателей для первой проверки:

- tutorial completion;
- first PvE completion;
- доля игроков, начавших второй PvE;
- D1 / D3 / D7 retention;
- matches per player;
- session length;
- rewarded ad offer → start → completion;
- rewarded ads per active player;
- IAP store view → purchase start → purchase complete;
- payer conversion;
- ARPPU / ARPDAU там, где достаточно выборки;
- какие unlock'и предшествуют повторному матчу;
- изменение retention после показа interstitial/rewarded;
- время от первого запуска до первой покупки.

Главный validation-вопрос первой версии — не «сколько рекламы удалось показать», а **возвращается ли игрок ради следующего матча и новой сборки**.

### 9. Порядок проверки гипотез

Предлагаемая последовательность, чтобы не оптимизировать деньги раньше продукта:

1. Выпустить PvE с метапрогрессией и аналитикой.
2. Проверить первый → второй матч и ранний retention.
3. Включить ограниченные rewarded placements.
4. Проверить, не ухудшился ли retention и насколько игроки добровольно ими пользуются.
5. Добавить маленькую понятную IAP-матрицу (starter/meta/module), без десятков SKU.
6. Снять реальные conversion/ARPDAU/ARPPU.
7. Только затем экспериментировать с ценами, пакетами, частотой рекламы и более сложными предложениями.

### 10. Platform-specific экономика остаётся конфигурацией

Площадки отличаются правилами, рекламой, валютами, SKU и аудиториями. Поэтому бизнес-настройки могут различаться, но gameplay не должен ветвиться по платформе.

Например:

```ts
platform.iap.listProducts();
platform.ads.showRewardedAd({ placement: 'pve_result_bonus' });
```

А Yandex/CrazyGames/другой адаптер маппит наши внутренние product/placement id на возможности своей площадки.

Это позволит тестировать разные цены и доступность форматов, сохраняя одну экономическую семантику Void Dominion.

## Инварианты

1. `shared-core` никогда не импортирует SDK площадки.
2. Gameplay/meta logic никогда не проверяет строку `yandex`, `crazygames` и т.п.
3. Platform SDK не изменяет `GameState` напрямую.
