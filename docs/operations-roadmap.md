# Эксплуатация: масштаб, наблюдаемость, live-ops — технический roadmap

> **Блок 7/7** из `tech-research.md` (§9 масштаб/ops, §10 наблюдаемость + пробелы live-ops/
> контент-пайплайн/модерация). Как игра живёт в проде: горизонтальный масштаб и мульти-регион,
> деплой при долгих соединениях, наблюдаемость/телеметрия, live-ops (контент-пайплайн, feature-flags,
> баланс), модерация/анти-абьюз. Хардненинг инфры/контейнеров и DR — `secure-environment-roadmap.md`
> (SE-1/5/8/9). Формат — кирпичики. **Новый блок.** Статусы: ✅ · ⏳ · 🔒(dep).

## Текущее состояние (факт)

Game пока ведёт комнаты одним процессом (durable-Postgres — opt-in по `DATABASE_URL`);
Corp поддерживает отдельный процесс/БД через `CORPORATIONS_URL`, без подтверждения
живого cutover. [Роадмап сервисов](service-resilience-roadmap.md) продолжает эти границы
для Inventory/settlement, Auction и workers. Деплой-артефакты есть
(`Dockerfile`, `render.yaml`, `deploy/docker-compose.yml`) и базовая наблюдаемость тоже
(структурные pino-логи, минимальный `/metrics`). Горизонтального масштаба, игровой
телеметрии и модерации нет; OTel/Prometheus/Grafana/Sentry — нет.
SBOM/сканеры есть (SEC-0). Контент — `data/*.json` + manifest (валидируется), но без пайплайна
публикации/версий без даунтайма.

## Фаза 0 · Наблюдаемость (заложить с первого сервера)

### OPS-0.1 · Структурные логи + трейсинг `[srv][sec]` ⏳ — M
**Цель:** видеть, что происходит, без PII/секретов.
**Подзадачи:** структурный лог (pino) + OpenTelemetry-трейсинг сквозь match-actor; корреляция по матчу/игроку; централизованный сбор. **(Связка SE-8.1.)**
**Готово, когда:** запрос/действие трассируется end-to-end; логи без утечек.
Collector/log-audit store — отдельный операционный контур, async bounded доставка
вне горячего пути; SIEM/response имеют собственные identities и incident store.
[Топология и критерии отказов](security-operations-roadmap.md), владельцы — SE-8.1/8.4/8.5.

### OPS-0.2 · Метрики и трекинг ошибок `[srv][sec]` 🔒(OPS-0.1) — S
**Подзадачи:** Prometheus/Grafana (соединения/матч, исходящие байты/клиент, dropped/slow, due-события, лаг планировщика); Sentry (ошибки, без PII). **(= SE-8.3.)**
**Готово, когда:** есть дашборд состояния и поток ошибок.

### OPS-0.3 · Игровая телеметрия/аналитика `[srv]` 🔒(OPS-0.1) — M
**Цель:** данные для баланса async-экономики и удержания.
**Подзадачи:** события геймплея (без PII) → аналитическое хранилище; базовые воронки/удержание/баланс-метрики; разделение продуктовой телеметрии и тех-метрик.
**Готово, когда:** ключевые геймплей-события собираются и доступны для анализа.

## Фаза 1 · Деплой и устойчивость

### OPS-1.1 · Деплой при долгих WS-соединениях `[srv][sec]` ⏳ — M
**Цель:** релиз не рвёт идущие матчи.
**Подзадачи:** rolling/blue-green; **drain + graceful shutdown** (дренить WS, клиент reconnect+resume — SV-2.2); миграции БД без даунтайма (expand/contract); пин образов по digest (SE-5).
**Готово, когда:** деплой проходит без потери матчей; клиенты переподключаются.

### OPS-1.2 · Нагрузочное и хаос-тестирование `[sec]` 🔒(OPS-0.2) — M
**Цель:** проверить до публичности.
**Подзадачи:** k6/Artillery на N параллельных матчей + WS-обрывы; хаос (kill инстанса/БД) → проверка восстановления (SE-9); пороги в CI/прогон по релизу.
**Готово, когда:** известна ёмкость; восстановление после сбоев проверено.

### OPS-1.3 · Статус-страница и инцидент-комм `[docs][sec]` 🔒(OPS-0.2) — S
**Подзадачи:** статус-страница; runbook'и инцидентов (= SE-9.2); канал уведомлений игроков.
**Готово, когда:** при сбое есть статус и регламент коммуникации.

## Фаза 2 · Масштаб

### OPS-2.1 · Шардинг по матчу + горизонт `[srv]` ⏳ — L
**Цель:** много матчей на многих инстансах.
**Подзадачи:** распределение match-actor по инстансам; fan-out (Redis pub/sub) — = SV-4.1; балансировка/перемещение матчей; ёмкость на инстанс.
**Готово, когда:** матчи распределяются и масштабируются горизонтально.
Тот же поток SV-4.1 должен доказать изоляцию гибели worker и fencing старого writer;
отдельное учение проверяет readiness, backlog/latency, потерю ответа после commit и
восстановление без повторного эффекта ([MSVC-5](service-resilience-roadmap.md)).
Общий PostgreSQL/хост остаётся общей точкой отказа до независимого HA/DR-учения.

### OPS-2.2 · Мульти-регион `[srv][sec]` 🔒(OPS-2.1) — L
**Цель:** глобальная аудитория Bytro-жанра.
**Подзадачи:** регион хостинга по подбору (MM-2.2); глобальные аккаунты/лобби, региональные матчи; latency/данные по регионам; согласовать с приватностью (SE-10).
**Готово, когда:** игроки играют в близком регионе; аккаунты глобальны.

### OPS-2.3 · Стоимостная модель `[docs]` ⏳ — S
**Подзадачи:** посчитать always-on 24/7-матчи: Redis-горячее/Postgres/трафик/инстансы на N матчей; пороги для решений масштаба/региона.
**Готово, когда:** есть модель стоимости на единицу матча/игрока.

## Фаза 3 · Live-ops и контент-пайплайн

### OPS-3.1 · Пайплайн публикации контента + версии `[data][sec]` 🔒(CR-0.1) — M
**Цель:** данные-первый дизайн без даунтайма/поломок матчей.
**Подзадачи:** валидация/версионирование `data/*.json` (zod ✅) в пайплайне; публикация новой версии данных; новые матчи — на новой, идущие — на своей (CR-0.1); откат.
**Готово, когда:** контент публикуется версионно, не ломая идущие матчи.

### OPS-3.2 · Feature-flags и A/B `[srv]` ⏳ — M
**Подзадачи:** флаги для постепенного выката/kill-switch (= SE-9.2); базовый A/B для балансных экспериментов; согласовать с детерминизмом (флаг как часть config матча).
**Готово, когда:** фичу можно включать постепенно и гасить мгновенно.

### OPS-3.3 · Тулинг баланса экономики `[docs][core]` 🔒(PE-1.1) — M
**Подзадачи:** симуляции/дашборды по телеметрии (OPS-0.3) для настройки констант; прогон сценариев на ядре; рекомендации правок данных.
**Готово, когда:** баланс настраивается данными по симуляциям/метрикам.

## Фаза 4 · Модерация и коммуникации

### OPS-4.1 · Модерация и анти-абьюз `[srv][sec]` ⏳ — M
**Цель:** имена/чат/дипломатия — без абьюза.
**Подзадачи:** фильтр имён/чата; репорты; очередь модерации; баны (увязать с GI-3.1); хранение жалоб.
**Готово, когда:** игрок может пожаловаться; модератор разбирает; санкции применяются.
Единый workflow заявок и ограниченных полномочий — OPS-4.3/4.4/4.5 и
[служебный роадмап](staff-case-roadmap.md); GI-3.1 остаётся владельцем санкций/апелляций.

### OPS-4.2 · Транзакционная почта/коммуникации `[srv][sec]` ⏳ — S
**Подзадачи:** провайдер транзакционной почты (верификация/восстановление — AC-1.2, уведомления безопасности); анти-спам/rate-limit; без утечки.
**Готово, когда:** письма доставляются надёжно и безопасно.

### OPS-4.3 · Сервис заявок и два служебных пульта `[srv][cli][sec]` ⏳ — M

Отдельный Staff/Support service с собственной БД, очередями, доказательствами и
атомарным claim по версии/assignment epoch. Пульты модератора и игрового администратора
используют общий backend, раздельные функции и персональные staff identities/MFA.
Опора — существующий минимальный ADM-1; полного сервиса/модераторского клиента ещё нет.
**Готово, когда:** игрок видит только свои обращения; сотрудник берёт разрешённую
очередь и читает только допустимые материалы дела; конкурентное назначение имеет
однозначный исход, а отказ Staff не выключает Game readiness/обычный бой.

### OPS-4.4 · Временные полномочия по делу `[srv][sec]` 🔒(OPS-4.3) — M

Пересечение роли, дела, назначения, операции, цели, срока и лимитов; owner проверяет
grant через атомарный authorize/consume и исполняет команду с тем же actionId/receipt.
Закрытие/переназначение/отзыв роли запрещают новые принятия; неизвестный исход
восстанавливается по ID, без повторной выдачи эффекта/бюджета. Суммарные лимиты
по сотруднику не обходятся множеством тикетов; чувствительные действия требуют
независимого одобрения по policy. Перенести существующий kick без legacy-обхода.
**Готово, когда:** прямой вызов, чужой target/actor, просроченный epoch и изменённый
payload отказаны; разрешённая команда работает один раз; потеря consume/commit-ответа
и рестарт не удваивают эффект. Точка отсечения/принятые команды описаны в
[контракте](staff-case-roadmap.md), обычные команды игроков Staff не вызывают.

### OPS-4.5 · Аудит и проверки злоупотреблений сотрудников `[srv][sec][ops]` 🔒(OPS-4.4) — M

Доменные audit/receipt атомарны с эффектом; независимый append-only sink и
разбор по employee/case/action. Проверки самоодобрения, двух логинов одного
сотрудника, конфликтов интересов, обхода квоты, чтения чужих материалов и удаления
следов. Связать с SE-8 и MSVC-9, не обещать защиту от всего сговора/захвата issuer.
**Готово, когда:** отказы и разрешённые действия объяснимы в аудите без секретов;
сотрудник не меняет свою policy/историю, ослабление scope/epoch/quota обнаруживается
негативными тестами; недоступность Staff сохраняет обычную игру и подтверждённые результаты.

## Последовательность

- **С первого сервера:** OPS-0.* (наблюдаемость) — дешевле заложить сразу.
- **До публичности:** OPS-1.* (деплой/нагрузка/статус).
- **С ростом:** OPS-2.* (шардинг/регион) — не раньше нужды (`tech-research.md` анти-цели).
- **Live-ops/модерация:** Фазы 3–4 по мере живой игры; контент-пайплайн (OPS-3.1) — с CR-0.1.
- **До расширения пультов:** OPS-4.3 → OPS-4.4 → OPS-4.5; новый служебный
  доступ включается после проверки scope/отзыва/аудита. Независимые backup/logging
  и response-контуры идут по [операционной последовательности](security-operations-roadmap.md).
