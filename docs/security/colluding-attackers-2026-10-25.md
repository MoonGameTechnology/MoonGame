# Совместные действия внешнего и внутреннего атакующих

Проверка 25 октября 2026 года: основной сервер на `8093c358`, отдельный bot stage,
общий Caddy, локальные пользователи VPS и observer. Код stage подмонтирован из
отдельного release; старый label его образа не доказывает версию исполняемого кода.
Модель внутреннего атакующего разделена на обычный UID, UID мониторинга,
захваченное приложение в контейнере и более сильный доступ с UID приложения
непосредственно на хосте. Эти права не считаются взаимозаменяемыми.

## Подтверждённая цепочка: observer → операторский ключ → скрытые события

Непривилегированный `moon-observer` мог читать свою штатную копию полного
`METRICS_TOKEN` и соединяться с приложением. Сверка ключей выполнена в памяти,
значения не выводились. `HEAD /metrics/recent?n=invalid` без ключа дал 404,
с ключом observer — 400: операторская проверка пройдена, параметр отклонён
**до чтения журнала**. Исходник маршрута подтверждает, что корректный параметр
открывает JSONL с событиями до фильтра тумана войны. Реальные события не выгружались.

Условия: выполнение кода как observer либо кража его credential и доступ к
внутреннему HTTP-входу. Внешнему сообщнику достаточно получать данные от такого
процесса через доступный ему канал: публичный запрет Caddy сам по себе его не
отзывает. Реальную передачу данных внешнему получателю не выполняли. Это раскрытие игровой
информации, не доказательство RCE, root-доступа или записи в БД. Широкие права
старого ключа уже были отмечены в ранбуке exporter; проверка связала их с фактическими
правами отдельного observer на VPS.

Исправление:

- Отдельный `METRICS_READER_TOKEN` допускает только `/metrics`,
  `/metrics/summary`, `/metrics/activity`. Пустой reader не добавляет доступа;
  короткий или совпавший с операторским ключ останавливает запуск.
- Сводка фильтруется **в приложении** по списку разрешённых полей. Полная
  `MetricsSummary` также содержала экономику по игрокам и победителя; reader их
  не получает. Фильтрация только внутри exporter не защищала бы от его компрометации.
- Сырые события и `/metrics/health` сохраняют отдельную операторскую проверку.
  Reader не проходит игровую авторизацию и не получает прав через подмену XFF.
- Compose передаёт новый ключ, оба серверных входа используют одну проверку.
  Для завершения на VPS необходимы обновление образа, отдельный reader в credential
  observer и ротация прежнего полного ключа. Сам merge не меняет секреты.

Порядок перехода и проверки отказа — в [ранбуке exporter](../../deploy/observability/GAME-EXPORTER.md).

## Что проверено на VPS

Выполнено 255 конечных проверок: 50 попыток открыть файлы без чтения содержимого,
40 проверок прав записи без записи, 5 соединений с Docker socket без API-запросов,
80 TCP connect из пяти профилей хоста и 80 из пяти контейнерных сетевых пространств.
Root служил положительным контролем. Обычные UID запускались без дополнительных
групп и capabilities, с `no-new-privileges`.

UID-пробы не воспроизводят дополнительные ограничения systemd-unit. У штатного
observer `IPAddressDeny=any` и разрешён localhost: прямой внешний канал из этого
unit не считается проверенным или открытым. Избыточный доступ к игровому журналу
остаётся доступом к данным, даже когда следующий шаг вывода ограничен.

| Граница | Результат |
| --- | --- |
| Обычный UID / прежний пользователь `moongame` → секреты, Docker, служебные скрипты | Проверенные открытия/запись/соединение запрещены |
| Те же пользователи → прямые app/DB/admin-порты | Запрещены; публичный HTTPS Caddy доступен |
| Observer → секреты | Доступна его собственная credential; root env и Docker недоступны |
| Stage app → внутренние IP основного app/DB | TCP-соединения не установлены |
| Caddy → обе БД | TCP-соединения не установлены; оба HTTP backend доступны |
| Приложения → собственная БД | TCP доступен; это необходимая часть их полномочий |
| Контейнер → Docker socket / host env | Socket и путь host env отсутствуют; effective capabilities нулевые |
| DB runtime roles → superuser/create-role/create-db/replication/bypass-RLS | Все флаги выключены; членство в `vd_runtime`, не `vd_schema` |
| Stage и production → ключи JWT и метрик | Значения присутствуют и различаются; сверены без вывода |

Для namespace-проб менялось только сетевое пространство процесса: это проверка
маршрутизации, не эмуляция всех прав контейнера. Loopback внутри него обозначает
сам контейнер. Изоляция процессов отдельно проверена через `docker exec`:
видны приложение и диагностический процесс, host PID namespace не подключён.

Ещё 12 запросов к двум публичным HTTPS-входам с подставленными XFF и user-id:
`/ready`, `/auth/status` — 200; `/metrics`, summary, recent и admin — 404.
Запросы шли с VPS через публичный Caddy. Независимая внешняя точка web-инструмента
не смогла открыть адреса; это **не внешний скан портов** и не подтверждение всех
правил провайдерского firewall.

## Совместные сценарии в изолированных тестах

`colludingAttackers.test.ts` использует настоящие HTTP/WS проверки и синтетические
аккаунты, ключи и хранилище. Шесть сценариев проверяют:

1. Ключ stage, даже вместе с точными claims жертвы, не подписывает session/reset/join
   для production; корректный production join остаётся рабочим.
2. Одного ключа production без актуального fingerprint аккаунта недостаточно для
   выбранной подделки session/join. Это дополнительная проверка, не полноценная
   защита при захвате процесса, которому доступны и ключ, и база.
3. Настоящий украденный join bearer можно повторить с разрешённым Origin.
   Он не даёт другого места. Запрет чужого Origin защищает браузерный сценарий,
   но не мешает самостоятельному клиенту выставить разрешённый заголовок.
4. Logout закрывает соединение сообщника и отзывает исходную session, её refresh
   и скопированный join.
5. Если внутренний атакующий сохраняет ключ **и чтение текущей БД**, после logout
   он может выпустить новую сессию. Замена ключа без сохранения скомпрометированного
   previous key отвергает её. Также нужно устранить сам доступ атакующего.
6. Ключ метрик stage не даёт прав production; ключи мониторинга не являются
   игровыми сессиями, подмена XFF не создаёт операторских прав.

Live-тест exporter собирает и запускает тот же `proto-server.mjs`, что Docker:
пять источников с reader работают; raw/health запрещены; полная операторская
проверка остаётся рабочей; player economy/end отсутствуют в ответе reader.
Отдельный тест проекции проверяет также неизвестное будущее чувствительное поле.

## Оставшиеся границы и ограничения

**Одинаковый UID приложений на хосте.** UID 65532 на самом хосте смог открыть
`/proc/<pid>/environ` обоих приложений. Байты не читались. Обычные UID не смогли;
учётки для входа с UID 65532 нет. Получить выполнение с этим UID вне контейнера —
дополнительное условие, не найденный в этой проверке container escape.
Для более сильной изоляции нужны отдельные UID/диапазоны или отдельный хост stage.
Один общий `userns-remap` не разделяет одинаковые UID контейнеров друг от друга;
его включение на действующей установке требует переноса томов и bind mounts.
Основание: [Docker user namespaces](https://docs.docker.com/engine/security/userns-remap/),
[проверки доступа ptrace](https://man7.org/linux/man-pages/man2/ptrace.2.html).

**Захваченный app или общий Caddy.** Приложение имеет рабочие ключи и DML-доступ к
своей БД; edge обслуживает оба окружения. Это существенный ущерб при компрометации
соответствующего процесса. Проверенные сетевые запреты не делают его доверенным.
WAF не ограничивает уже захваченный процесс и не проверяет игровые WS-сообщения.

**Административный вход.** SSH root/password остаётся разрешён: рабочий вход
оператора по ключу ранее не был установлен. Проверка не отключала доступ владельцу.
Восстановление вне VPS отложено владельцем; эта проверка его не подтверждает.

Пробы не включали эксплуатацию ядра, container escape, нагрузочный DoS или
выгрузку production-данных. Отказы конкретных цепочек не доказывают отсутствие
всех уязвимостей и не доказывают отсутствие прежнего вторжения.
