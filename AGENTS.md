# Repository workflow

Before starting any backlog brick, refresh the repository from `main` first:

1. Require a clean working tree; never discard or overwrite another contributor's work.
2. Run `git fetch origin main`.
3. Rebase the current short-lived branch onto `origin/main`, or create the brick branch from
   `origin/main` when no feature work exists yet.
4. Re-open and re-read every file the brick will touch after the refresh. Do not rely on a stale
   copy, an earlier audit, or conversation context.
5. If `origin` or network access is unavailable, do not begin the brick. Report that the mandatory
   refresh could not be completed.

The detailed Git workflow remains in `CONTRIBUTING.md`.

## Fast navigation — use the indexes before broad search

Do not start by searching the whole repository when an existing project map or generated index can
answer where to look.

1. **`docs/state.md`** — first stop for what is already implemented and the current project
   snapshot. Check this before building something twice.
2. **`CODE-MAP.md`** — first stop for where executable code lives and which entry point actually
   runs in production, playtests, the prototype, server, and clients.
3. **`docs/bricks-index.md`** — first stop for “does a task for this already exist?”, its status,
   zone, source roadmap/backlog file, and exact location.
4. **`docs/index.md`** — first stop for “where is this topic documented?”. Use it to jump to the
   relevant roadmap/design document instead of opening many docs.
5. After the index points to the relevant area, read that roadmap/design doc and then the actual
   code/tests it names. Use repository-wide search only when these navigation sources are
   insufficient.

`docs/bricks-index.md` and `docs/index.md` are generated by `scripts/docs-check.mjs`; do not
hand-maintain their contents. Regenerate them through the existing docs-check workflow when their
source documents change.

When sources disagree, use this precedence for implementation state:

`main` code → tests on `main` → green CI for that SHA → open PRs → generated indexes →
thematic roadmaps/docs → old conversation context.

## Loop-prevention and execution discipline

Long or multi-step work must make observable progress and must never fall into repeated tool or
reasoning loops.

1. Before a long task, define the concrete completion condition: what must exist or be true for the
   task to count as done.
2. Retry the same failed action at most once.
3. Every next iteration must either change the task state or produce genuinely new information.
   If two consecutive steps do neither, stop that branch of work: switch to a materially different
   approach or report the current result and the exact blocker.
4. Treat authentication, permissions, missing repository state, unavailable dependencies, merge
   conflicts, and tool failures as blockers. Do not turn them into repeated probing loops.
5. If a third substantially similar tool call or action would be needed in the same branch of work,
   use it as a circuit breaker: do not repeat that action again. Change approach or stop with the
   useful partial result and blocker.
6. Prefer a useful partial result plus a precise blocker over indefinite retries.
7. Do not run extra checks when the owner explicitly asks to skip checks or to perform only a
   specific action such as creating a PR.
8. During long work, provide short progress updates that state what has actually changed, not merely
   that work is continuing.

## Task completion discipline

When a requested task is complete and ready for integration, do not leave the finished work only
on a feature branch and do not wait for a separate request to publish it.

1. Create the pull request immediately after the task is ready.
2. Make sure the PR contains the complete intended change and targets the current `main`.
3. Follow the PR through CI and review. If a check, conflict, permission error, or tool failure
   blocks it, make at most one retry of the same failed action; then report the exact blocker
   instead of looping.
4. When the PR is green and eligible, put it into the repository's merge queue / enable auto-merge
   so it is revalidated against fresh `main` and merged automatically.
5. A task is not considered fully handed off while completed code is stranded only in a branch.

## Project rules live elsewhere — read them before writing code

This file covers refresh, navigation, anti-loop execution, and completion discipline. The rules
that decide whether a change is *correct* in this repository are elsewhere:

- **`CLAUDE.md`** — the non-negotiable invariants: determinism of `packages/shared-core`
  (no `Math.random`, no `Date.now`, no implementation-approximated `Math.*`), purity of
  `applyAction`, modules talk only through the bus, fail-secure rejection (an error is a
  stable `E_*` code, never a leaked detail), server authority, fixed module order.
- **`CONTRIBUTING.md`** — the full Git and review regimen.
- **`.claude/skills/`** — the executable rituals: `brick` (take a backlog task),
  `localization` (player-visible text is a KEY, never a literal), `new-module`,
  `add-game-content`, `sync-state-doc`.

Run `pnpm run check` (lint + typecheck + test + docs-check) before every commit; it is the
gate CI mirrors.
