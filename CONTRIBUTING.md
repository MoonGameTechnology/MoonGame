# Contributing — как мы работаем

Короткий рабочий регламент команды. Архитектура и инварианты — в `CLAUDE.md`;
живой снимок состояния — `docs/state.md`; план — `docs/roadmap.md` и
`docs/deep-technical-roadmap.md`.

## TL;DR

1. Ветку — **от `main`**, маленькую, под одну задачу.
2. `pnpm install` → пиши код → **`pnpm run check`** зелёный.
3. PR **в `main`**. Зелёный CI + ≥1 ревью → мердж → ветку удалить.
4. **`main` — единственная точка интеграции.** Не мердж в чужие ветки.

## Окружение

- Node ≥ 20 (CI гоняет на 22). pnpm зафиксирован полем `packageManager` —
  включи `corepack enable`, дальше `pnpm install`.
- **Гейт перед коммитом:** `pnpm run check` = `lint` + `typecheck` + `test` + `docs-check`.
- Ещё: `pnpm test`, `pnpm run lint`, `pnpm run typecheck`, `pnpm run format`,
  `pnpm run prototype` (собрать играбельный `prototype/dist/void-dominion.html`).
- **В веб-сессиях Claude Code зависимости ставятся сами** — SessionStart-хук
  `.claude/hooks/session-start.sh` гоняет `pnpm install --frozen-lockfile` до старта
  сессии, чтобы гейт и тесты не падали на пустом `node_modules` в свежем контейнере.
  Локальные машины он не трогает (условие `$CLAUDE_CODE_REMOTE`) — там установка своя.
  Браузер для MCP хук СОЗНАТЕЛЬНО не качает: в веб-образе Chromium уже стоит, а на
  локальной машине это отдельная история — см. раздел про MCP ниже.

## Работа через Claude Code (веб / CLI)

Правила те же, что для человека:

- **Base-ветка сессии = `main`.** Одна задача → одна сессия → одна ветка → один PR.
- Веб сам генерит имя ветки (`claude/...`) — это нормально; важно, чтобы PR шёл
  **в `main`**, а не в чужую ветку.
- Не продолжай чужую длинную ветку — начинай от свежего `main`.
- **Перед публикацией PR синхронизируйся повторно.** После завершения работы ещё раз
  обнови `main` и сравни ветку с ним. Если ветка уже behind/diverged — сначала перенеси
  её на свежий `main` (для короткой ветки обычно rebase), разреши конфликты и повтори
  проверки, которые мог затронуть перенос. Не открывай заведомо устаревший PR.
- Подключение нового человека: его GitHub-аккаунт получает **Write**-доступ к репо
  (см. ниже) и ставит **Claude GitHub App** на свой GitHub. Среды у всех
  изолированы — общий только этот репозиторий.

## Спец-агенты по требованию

Под узкую тяжёлую задачу (security-ревью ветки, анализ баланса контента,
профилирование рендера, аудит детерминизма) запускай **сфокусированного
суб-агента** встроенным Agent tool Claude Code — с чётким ТЗ и проверяемой целью;
результат сверяй с гейтом и кодом, а не принимай на веру.

Почему так, а не плагин-каталог: мы намеренно **не берём фреймворки вроде
`template-bridge` целиком**. Они ставят «агентов» через неприпиннутый
`npx …@latest` — ровно тот supply-chain-вектор (OWASP A08), от которого защищает
наша SDLC-линия (SHA-пины actions, аудит зависимостей). Идею «специалист по
требованию» берём, но **без сторонних зависимостей и без неприпиннутого
внешнего кода**.

### Скиллы репозитория (`.claude/skills/`)

Повторяющиеся ритуалы записаны как **проектные скиллы** — обычные `.md`-файлы в
`.claude/skills/<имя>/SKILL.md`, версионируются и ревьюятся вместе с кодом. Это и есть
«специалист по требованию» без внешнего кода: ничего не ставится, ничего не скачивается.

| Скилл | Когда |
| --- | --- |
| `brick` | взять/закрыть кирпичик из `docs/backlog.md` |
| `publish-pr` | опубликовать готовую локальную работу, создать/переиспользовать PR; fallback через Git Data API, включая PNG/WebP |
| `new-module` | новая механика = новый модуль ядра |
| `add-game-content` | контент в `data/*.json` |
| `localization` | любой текст, который читает игрок: ключ в `/localization`, не литерал в коде |
| `sync-state-doc` | привести `docs/state.md` в соответствие с кодом |
| `determinism-audit` · `balance-analysis` · `render-profile` · `security-triage` | четыре тяжёлые задачи из списка выше |
| `playtest-report` · `refresh-scanner-digests` | периодика: журнал плейтеста, ежемесячный ре-пин образов |
| `thermo-nuclear-code-quality-review` | максимально жёсткий разбор качества структуры диффа (только явным вызовом) |

Последний — внешний скилл из [`cursor/plugins`](https://github.com/cursor/plugins/blob/main/cursor-team-kit/skills/thermo-nuclear-code-quality-review/SKILL.md),
скопированный в репозиторий как есть плюс местная секция «Как это ложится на Void Dominion»
(инварианты ядра сильнее любого «code judo», правило 1000 строк на фоне унаследованных
крупных файлов, текст только через `/localization`). Это markdown, а не код: ничего не
ставится и не запускается, так что правило «без неприпиннутого внешнего кода» выше не
нарушено. У него `disable-model-invocation: true` — сам он не включается, только
`/thermo-nuclear-code-quality-review`.

Claude Code подхватывает их сам; можно позвать и явно — `/brick`, `/new-module`, ….
Скилл — это **инструкция, а не гарантия**: `.claude/` исключён из `docs-check`
(`scripts/docs-check.mjs`), поэтому битые пути внутри скилла гейт не поймает. Меняешь
структуру, на которую скилл ссылается, — поправь и скилл; заводишь новый — сверяй каждый
путь и команду с репозиторием, а не пиши по памяти.

## MCP-серверы (`.mcp.json`)

MCP-сервер — это **исполняемый код с доступом к репозиторию**, то есть та же
supply-chain-поверхность, что и плагин-каталоги выше. Поэтому правило то же, что для
образов сканеров: ставим только то, что закрывает реальную дыру, берём официальное,
**пиним версию в `devDependencies`** (тогда её хеш держит `pnpm-lock.yaml`) и никогда
не запускаем через неприпиннутый `npx …@latest`.

Сейчас подключён один:

| Сервер | Пакет | Зачем |
| --- | --- | --- |
| `browser` | `@playwright/mcp` (Apache-2.0, пин в корневых `devDependencies`) | прогнать РЕАЛЬНЫЙ прототип в браузере |

Почему именно браузер: `prototype/` — играбельный клиент — исключён из ESLint и не
тайпчекается, то есть статических гарантий по нему нет вообще, а `perf.mjs`/`uitest.mjs`
работают на фейковом DOM и проверяют «код не бросил», а не «игра работает». Классы
багов, которые ловятся только настоящим браузером, в истории репозитория уже есть:
TDZ-ловушка `httpBase` (жила исключительно в собранном esbuild-бандле), click-through
в spotlight-онбординге, тач-прицеливание. Первый же прогон нашёл три живых: отладочные
`console.log` в boot-пути, необработанный `SyntaxError` в `probeAuthMode` при
HTML-ответе на `/auth/status`, и поле пароля вне `<form>` (ломает менеджеры паролей).

Запуск руками — `pnpm mcp:browser`; Claude Code поднимает сервер сам по `.mcp.json`.
Оба пути идут через обёртку `scripts/mcp-browser.mjs`, потому что окружения с
предустановленным браузером (Claude Code на вебе, CI-образы) держат Chromium другой
ревизии и запрещают докачку — там серверу нужен `--executable-path`, а на обычной машине
его передавать нельзя. Обёртка это резолвит; принудительный путь — `VOID_MCP_CHROMIUM`.
Сам порядок резолва лежит в `scripts/chromium.mjs` — ОДНОЙ копией на обёртку и на смоук
ниже: разойдись они, смоук качал бы браузер, который сервер потом не открывает (SEC-37).
Сессия всегда `--isolated`: прототип хранит в `localStorage` посадочные билеты и
session-JWT, и утаскивать их из прогона в прогон нельзя. Вывод (снапшоты, логи консоли)
падает в `.playwright-mcp/` — она в `.gitignore`.

**Первый запуск у нового участника: сервер нужно ОДИН РАЗ подтвердить.** `.mcp.json`
приезжает с клоном, но Claude Code не поднимает проектные серверы молча — это же
исполняемый код из репозитория, та самая supply-chain-поверхность, ради которой мы
пиним версию выше. Поэтому при первом запуске в корне проекта он спрашивает доверие, а
до ответа сервер висит неподключённым:

```
$ claude mcp list
browser: node scripts/mcp-browser.mjs - ⏸ Pending approval (run `claude` to approve)
```

Лечится запуском `claude` (интерактивно, **из корня репозитория** — путь в `.mcp.json`
относительный) и подтверждением запроса. Если запрос не появляется, значит выбор уже
сделан раньше и запомнен — сбросить обе стороны выбора можно так:

```bash
claude mcp reset-project-choices   # сбрасывает и approved, и rejected для этого проекта
claude                             # запустить снова и подтвердить
```

Проверка — `/mcp` внутри сессии: `browser` должен быть connected. Подтверждение хранится
в пользовательском конфиге, а не в репозитории, поэтому закоммитить его нельзя и сделать
это обязан каждый у себя — это не недоделка, а граница доверия.

**Postgres-сервер сознательно НЕ подключён.** Официальный
`@modelcontextprotocol/server-postgres` помечен `deprecated` («Package no longer
supported»), единственная живая замена (`@henkey/postgres-mcp-server`) — под AGPL-3.0,
что для проприетарного репозитория лишний юридический вопрос, а MIT-форки год не
обновлялись или сидят в версии `0.0.x`. При этом `psql` есть в окружении и покрывает
задачу: `pnpm db:psql` — консоль, `pnpm db:schema` — таблицы и индексы (обе читают
`DATABASE_URL`, по умолчанию локальный compose-Postgres). Пересматривать — когда
появится поддерживаемый сервер под пермиссивной лицензией.

**Обновление** — тем же ритуалом, что `refresh-scanner-digests` для образов: раз в месяц
или при выходе значимой версии поднять пин в `devDependencies`, прогнать `pnpm mcp:browser`
живьём (сервер обязан ответить на `initialize` и реально открыть страницу) и только
потом коммитить. Смена мажора Playwright тянет смену требуемой ревизии Chromium —
проверяй в среде с предустановленным браузером тоже.

### Браузерный smoke — `pnpm smoke:browser`

Тот же сервер, но без человека в цикле: `prototype/browsertest.mjs` собирает прототип
(если `dist/` пуст), поднимает статику, открывает игру в headless-браузере и **падает
на любой ошибке в консоли**. Проверяет три вещи: страница — это игра, экран входа
отрисовал локализованные кнопки, консоль пуста. Статик-хост сам отвечает на
`/auth/status` `{"enabled":false}` — честный контракт сервера без аккаунтов, поэтому
здоровый запуск даёт по-настоящему ПУСТУЮ консоль и allow-list не нужен (нечему
протухать). На машине без браузера: `pnpm smoke:browser:install` — там, где браузер уже
предустановлен, это осознанный no-op (см. выше), так что команда безопасна везде.

В CI шаг пока **не блокирующий** (`continue-on-error`, та же постура, что у `perf`), и
цена этой постуры уже была заплачена: смоук падал на резолве Playwright в каждом прогоне
с 2026-08-15 по 2026-09-11, а джоба оставалась зелёной — сторож молчал, и молчание
читалось как «всё хорошо» (SEC-37). Поэтому шаг теперь пишет на сводку прогона
аннотацию, и две беды в ней РАЗНЫЕ: `warning` — смоук не смог установиться (про код не
говорит ничего), `error` — смоук отработал и нашёл дефект в собранном бандле. Если
увидишь первое — бандл в этом прогоне не проверялся вообще.

Зачем отдельно от `uitest.mjs`: тот гоняет фейковый DOM и отвечает на вопрос «код не
бросил», а этот — «собранный бандл реально грузится». Класс дефектов, который виден
только здесь: esbuild-only баги (TDZ `httpBase`), необработанные исключения, ошибки и
предупреждения браузера. Первый прогон нашёл три (см. PR #403).

В `ci.yml` шаг стоит **нон-блокирующим** (`continue-on-error`, как `perf`): раннеру
нужно скачать Chromium, поэтому сначала пусть покажет себя в логе, и только потом —
если окажется стабильным — снимать поблажку. Тест обязан уметь краснеть: перед тем как
менять его логику, подсунь в `dist/*.html` строку `<script>console.error('x')</script>`
и убедись, что прогон падает.

своим вопросом, и все они гоняют настоящий Chromium через тот же `scripts/chromium.mjs`:

| Команда | Харнес | Что отвечает |
| --- | --- | --- |
| `pnpm smoke:browser` | `browsertest.mjs` | собранный бандл грузится, экран входа на месте, консоль пуста |
| `pnpm smoke:context` | `contexttest.mjs` | контекстные действия на карте |
| `pnpm smoke:zoom` | `zoomtest.mjs` | зум и семантические уровни карты |

| `pnpm smoke:startup` | `startuptest.mjs` | вход с нуля и запомненным командиром, ресайз, поворот, возврат в хаб — dev и `player` |
| `pnpm smoke:bootfail` | `bootfailuretest.mjs` | сбой запуска даёт локализованный экран с явным ретраем, а не пустое меню |
| `pnpm smoke:mobile` | `mobiletest.mjs` | телефон: тач, карточка флота, курс/стоп до редьюсера, раскладки RU/EN |

| `pnpm smoke:all` | все девять | одна команда перед PR, который трогает клиент (~3 мин) |
| `pnpm perf:pan` | `panperf.mjs` | экран загрузки карты + время кадра при панораме и зуме (цифры — диагностика, не порог) |
| `pnpm ui:shot` | `uishot.mjs` | снимок любого экрана и сводка «что на нём» — см. ниже |

До 2026-09-22 команда была только у первого, остальные лежали в `prototype/` без единой
ссылки. Это тот же класс дыры, что «модуль есть, а в список ядра не внесён»: проверка
существует, но сработать не может. Четыре из них, которых никто не запускал, успели
сгнить. Два при этом ловили **настоящий** баг: трёхсекундный мёртвый старт каждой
не-платформенной сборки (BRWH-2 в `docs/backlog.md`). Заводя новый харнес, заводи и
команду, иначе он умрёт молча.

**Новый харнес — на общей базе `prototype/harnessKit.mjs`**, а не копией соседнего:

- `waitForApp(page)` — ждать настоящего сигнала готовности (`bootstrap.ts` снимает
  `body.app-starting`). Карточка входа видна сразу, а обработчики появляются позже: тап
  раньше уходит в пустоту. При сбое запуска падает сразу, с кодом экрана ошибки.
- `enterSkirmish(page, { tap, fromWelcome })` — путь «вход → хаб → сетап → запуск». Если
  соло-сохранение уже есть, подтверждает диалог «Заменить сохранённую партию?».
- `withDiagnostics(page, label, run)` — при падении кладёт снимок и сводку экрана (открытые
  диалоги, видимые кнопки команд, классы `body`, ошибки консоли) в `HARNESS_OUT`, по
  умолчанию `$TMPDIR/void-harness`, и дописывает пути к ошибке.
- `instrumentedGame(hooks)` — игра, собранная заново с харнесовыми хуками (код в области
  видимости `main.ts`: видит состояние, выделение, камеру), без экспортов в проде.
  Отдаёт маршруты для `serve`. `bootstrap.ts` в эту сборку не входит, поэтому покров BOOT-1
  снимает строка `LIFT_BOOT_VEIL` в начале бандла. Своя сборка `main.ts` поверх готовой
  страницы начинается с неё же — иначе робот не увидит ни одной кнопки.
- `launchBrowser()`, `serve(routes)`, `builtPage(name)` — Chromium, локальный сервер с
  заглушкой `/auth/status` и собранная страница с понятной ошибкой «сначала
  `pnpm run prototype`».

**Посмотреть экран глазами — `pnpm ui:shot`.** Одна команда вместо харнеса:

```bash
pnpm run ui:shot -- --screen match --phone --locale en --out /tmp/match.png
```

`--screen` принимает `welcome`, `hub`, `setup` или `match` (партия на паузе, чтобы кадр был
воспроизводим). `--phone` даёт 390×844 с тачем, `--player` — сборку игрока. Команда печатает
ту же сводку экрана, что и диагностика, а при ошибках консоли завершается с ненулевым кодом.
Агент открывает PNG как картинку, так что этот путь работает и без MCP-браузера.

**Когда MCP-сервер не поднялся.** В сессии агента `browser` иногда приходит
`CONNECTION_CLOSED` (например, при первом старте до подтверждения доверия). Это НЕ значит,
что браузера нет: харнесы выше спавнят тот же сервер сами, по stdio, и работают независимо
от того, подключён ли он к сессии. То есть проверить поведение в настоящем браузере можно
ВСЕГДА — через `pnpm smoke:*`, даже когда интерактивные `browser_*`-инструменты недоступны.
Обратное тоже верно: если сервер подключён, агент водит страницу руками (снапшот дерева
доступности, клики, `evaluate`, чтение консоли) — и тогда UI-правку можно проверить
глазами, а не только тестом.

## Git-workflow

- **`main` защищён:** прямой push запрещён; только PR с зелёным CI и ревью.
- Ветки короткоживущие. Растёт задача — дроби на несколько PR.
- **Перед каждым новым кирпичиком обязательно возьми свежий `main`:** рабочее дерево
  должно быть чистым, затем выполни `git fetch origin main` и ребейз текущей короткой
  ветки на `origin/main` (либо создай новую ветку от `origin/main`). После обновления
  заново открой и перечитай все файлы, которых коснётся кирпичик — не работай по
  старому аудиту или копии из предыдущего контекста. Если `origin`/сеть недоступны,
  кирпичик не начинай: сначала явно сообщи о блокировке синхронизации.
- **Не мердж feature-ветку в feature-ветку.** Всё сходится в `main`.
- Конфликт двух PR на один файл: первый мерджится, второй ребейзится на `main`.

## Как делить работу (чтобы не конфликтовать)

Архитектура изолирует — держись границ:

- **Пакеты** (`packages/`): `shared-core` (детерминированное ядро-симуляция),
  `action-layer` (Этап 2 — валидация/идемпотентность), `server` (Этап 3),
  `client` (Этап 4). Бери пакет — минимум пересечений.
- **Новая механика = новый модуль** в `packages/shared-core/src/modules/` +
  данные в `data/*.json`. Модули **не импортируют друг друга**, общаются только
  через шину (события / хуки / реестр возможностей). Двое пишут разные модули, не
  трогая общих файлов.
- **Ядро (`kernel/`) заморожено** — его не редактируют под фичу.
- **Контент** (`data/*.json`) — отдельная зона почти без конфликтов с кодом.

Перед стартом застолби зону в issue/таске, чтобы не пересечься с напарником.

## Инварианты ядра (нарушение = баг, не стиль)

Полностью — в `CLAUDE.md`. Кратко:

1. **Детерминизм:** ни `Math.random`, ни `Date.now` в ядре; seeded RNG; время —
   параметр `ctx.now`.
2. **Чистота/иммутабельность:** `applyAction` не мутирует вход; `GameState` —
   JSON-сериализуем (без классов/Map/Date).
3. **Только через шину:** модули не импортируют друг друга; точки расширения
   деградируют мягко (нет модуля → базовый дефолт).
4. **Fail-secure:** любая ошибка → `{ ok: false, code }`; путь — `h.reject(code)`;
   без утечки деталей наружу.
5. **Server-authority:** клиент шлёт намерение, не состояние.

## Тесты и документация

- Тесты лежат рядом с кодом (`*.test.ts`). Новая логика → тесты (обычно
  «состояние А + действие Б → ожидаем В»). Красный гейт не мерджим.
- **Цикл TDD:** RED (падающий тест на поведение) → GREEN (минимум кода до зелёного
  гейта) → REFACTOR (почистить, гейт держать зелёным) → COMMIT (маленький коммит).
  Гейт — `pnpm run check`. Для тривиальных правок — по здравому смыслу.
- После изменения поведения обнови **`docs/state.md`** (живой снимок). Документацию
  **сверяй с реальностью** (читай исходник, гоняй гейт), не пиши по памяти.

## Pull Request

- На просьбы «пушь / опубликуй / создай PR» используй `.claude/skills/publish-pr/SKILL.md`.
  Он отдельно покрывает hosted-среды без terminal push credentials и бинарные ассеты.
- Маленький и сфокусированный; в описании — что и зачем. Чек-лист — в шаблоне PR.
- Ревьюера назначает `CODEOWNERS` (по зонам). Не мерджи красный CI.
- Задача выполнена и PR готов → без дополнительного запроса доведи его до штатного
  handoff: финально синхронизируй ветку со свежим `main`, опубликуй и открой/обнови PR.
  **Не вызывай `enqueuePullRequest` и не включай generic auto-merge вручную:** постановкой
  готового PR в merge queue владеет `.github/workflows/automerge.yml`. Обязательные
  проверки и ревью не обходи; прямой merge и `enablePullRequestAutoMerge` очередь не
  заменяют.

## Настройка репозитория (владелец, один раз)

1. **Доступ.** Settings → Collaborators → добавить человека с правами **Write**
   (или через организацию/команду). Для Claude он ставит Claude GitHub App у себя.
2. **Ruleset** на `main` (Settings → Rules → Rulesets → New ruleset, target `main`).
   Именно ruleset, а НЕ Settings → Branches: классический branch protection — вторая,
   параллельная система, и включённая заодно она даёт два независимых набора правил
   на одну ветку, из которых в UI виден только тот, что открыт.
   - Restrict deletions, Block force pushes.
   - Require a pull request before merging → Required approvals: **1**,
     Dismiss stale approvals when new commits are pushed.
   - Require status checks to pass — список в пункте 3.
   - Bypass-список оставить пустым: обход правил и прямой push в `main` запрещены.
3. **Required-чеки.** Брать только те, что действительно краснеют:
   `lint · typecheck · test · audit` (через ТОЧКИ — job из `ci.yml`; у него сервис
   Postgres и `DATABASE_URL`, поэтому контракты адаптеров в `store.test.ts` реально
   выполняются) плюс блокирующие сканеры SEC-1 — `SAST patterns (Semgrep)`,
   `Secrets — tree (Gitleaks)`, `SCA — osv.dev (OSV-Scanner)`,
   `Vuln + IaC — files (Trivy fs)`, `Vuln — built image base OS (Trivy image)`.
   - **Не бери `lint + typecheck + test + audit`** (через ПЛЮСЫ — job из
     `security.yml`): у шага стоит `continue-on-error: true`, а результат лишь
     пишется в JSON для сводного отчёта, так что джоба зелёная и при красном
     `pnpm run check`. Единственным обязательным чеком она защищает `main` на вид.
   - **Не бери `Vuln — third-party prod images (Trivy image)`** — он помечен
     `report — informational`, там CVE сторонних образов прода: репозиторий запрётся
     до апстрим-обновления caddy/postgres, которое от нас не зависит.
4. **Merge queue** (Require merge queue в том же ruleset'е). Раньше тут стояло
   «необязательно» — это устарело: очередь стала обязательной частью схемы, потому что
   на неё завязана авто-постановка (п. 5). Очередь собирает временную ветку «свежий
   `main` + PR» и ждёт required-чеков на НЕЙ, а воркфлоу попадает туда, только если
   подписан на событие `merge_group`. Подписаны и `ci.yml`, и `security.yml`.
5. **Авто-постановка в очередь — `automerge.yml`.** Последнее звено цепочки «PR →
   сканеры → зелено → очередь → мердж» больше не ручное: воркфлоу нажимает «Merge when
   ready» за человека. Что важно знать:
   - он зовёт `enqueuePullRequest`, а НЕ `enablePullRequestAutoMerge` — под очередью
     привычный `gh pr merge --auto` не работает, это разные мутации;
   - срабатывает по ЗАВЕРШЕНИЮ прогонов `CI`/`Security scan` (момент «required-чеки
     отчитались») и на `ready_for_review`;
   - ставит в очередь `CLEAN` и `UNSTABLE`. `UNSTABLE` — это «обязательные зелёные,
     необязательный красный», а информационные сканеры краснеют штатно; требуй он
     строгого `CLEAN`, один чужой CVE в caddy остановил бы авто-постановку для всех PR;
   - форки и черновики отсекает явно, гейт не обходит: очередь всё равно
     перепроверяет PR на своей ветке.

   **Заводишь required-чек в новом воркфлоу — правок ДВЕ:** добавь ему `merge_group`
   (иначе очередь вышибет каждый PR по таймауту) И допиши сам воркфлоу в список
   `workflows:` у `automerge.yml` (иначе авто-постановка сработает раньше, чем этот чек
   отчитается, и PR встанет).

   **PR висит и не вливается?** Не гадай по цвету галочек — открой в самом PR
   комментарий «🚦 Почему этот PR не вливается»: он обновляется на каждом прогоне
   авто-мержа и называет причину поимённо, отделяя находку сканера от упавшего скрипта.
   Правило целиком, таблица причин и три грабли, на которых мы уже наступили, —
   `docs/pr-merge-rule.md`.
6. **`CODEOWNERS`.** Заполни GitHub-ник'ами по зонам (см. `.github/CODEOWNERS`),
   когда распределите ответственность.
