# DevSecOps-пайплайн — зачем эти сканеры и как с ними жить

Учебно-боевой слой безопасности в CI (GitHub Actions, `.github/workflows/security.yml`;
мигрирован с GitLab — см. `audit-2026-06-27.md`). Цель — **shift-left**:
ловить уязвимости в пайплайне на каждый push/MR, а не в проде. Этот проект —
полигон: TS-монорепо сейчас, сервер/Docker/API (Этап 3) — впереди.

## Карта классов сканеров (что, зачем, OWASP)

| Класс                | Что анализирует             | Что ловит                                                                         | OWASP 2021 | Инструмент                        |
| -------------------- | --------------------------- | --------------------------------------------------------------------------------- | ---------- | --------------------------------- |
| **SAST**             | исходный код (статически)   | инъекции, eval/Function, prototype pollution, path traversal, ReDoS, XSS-паттерны | A03, A04   | Semgrep                           |
| **SCA**              | манифест/lock зависимостей  | известные CVE в чужом коде (supply chain)                                         | A06        | OSV-Scanner (`pnpm audit` снят: npm закрыл эндпойнты, 2026-07) |
| **SCA (второй движок)** | те же зависимости, другой способ сопоставления | CVE, не пришедшие записью GHSA/OSV: матчинг по CPE прямо из фида NVD | A06 | OWASP Dependency-Check (`dependency-check`, информационный — CPE шумит на npm) |
| **Secret detection** | код + git-история           | утёкшие токены/ключи/пароли                                                       | A02, A07   | Gitleaks                          |
| **IaC/misconfig**    | Dockerfile/k8s/yaml — и отдельно compose | небезопасные дефолты, открытые порты, root                            | A05        | Trivy config (Dockerfile/k8s/terraform/…) + KICS (`kics` — Docker Compose, формата которого у Trivy нет) |
| **Container scan**   | образ (ОС + libs)           | CVE в базовом образе и слоях                                                      | A06        | Trivy image (`trivy-image` — наш образ; `trivy-deps` — сторонние образы прода из `deploy/`, информационный) |
| **Smoke образа**     | ЗАПУЩЕННЫЙ собранный образ  | образ, который сканируется чисто, но не стартует (сканеры его не запускают)        | —          | `.github/scripts/smoke-image.sh` — блокирующий в `trivy-image` и перед push в `image.yml` |
| **Provenance**       | опубликованный образ        | «в проде крутится ровно то, что прошло гейт»                                      | A08        | cosign (keyless) в `image.yml` + `deploy/verify-image.sh` |
| **DAST**             | ЖИВОЙ запущенный API        | сломанная authz, инъекции в рантайме, заголовки                                   | A01, A03   | OWASP ZAP baseline (`dast-zap`, информационный — не в блокирующем списке ниже, пока нет триажа на реальном рантайме) |
| **SBOM**             | граф зависимостей           | «затронуты ли мы новым CVE?» + provenance                                         | A08        | Syft (CycloneDX)                  |

**Почему именно набор, а не один сканер:** у каждого класса своя слепая зона.
SAST видит твой код, но не чужие CVE. SCA видит CVE в депах, но не логические дыры.
Secret-скан не лезет в логику. DAST видит рантайм, но не покрывает мёртвые ветки.
**Defense-in-depth** = слои с осознанным перекрытием (поэтому Trivy fs дублирует
часть SCA/секретов другим движком — это норма, а не дубль ради дубля).

## Почему открытые инструменты, а не «магия GitLab»

Управляемые сканеры GitLab (`Security/*.gitlab-ci.yml`) удобны, но:

- полноценный UX (Security Dashboard, виджет в MR, vulnerability management) —
  **только Ultimate**; на Free джобы прогоняются, но без дашборда;
- это чёрный ящик. Для **развития навыков** полезнее гонять Semgrep/Gitleaks/Trivy/
  OSV напрямую: видно правила, форматы (SARIF), коды возврата, тюнинг.

В пайплайне оставлен `include:`-блок управляемых шаблонов как альтернатива.

## Gating: ratcheting, а не «сломать билд в день 1»

Включишь всё блокирующим — получишь красный пайплайн с сотней находок и команду,
которая отключит сканеры. Поэтому:

1. **Стоп-краны** (план): секреты (Gitleaks) и high/critical в зависимостях
   (OSV-Scanner по обоим lock-файлам). Их мало, они однозначны.
2. **Триаж → baseline → ужесточение.** Разобрал находки, ложные подавил (см. ниже),
   реальные починил — переводишь сканер в блокирующий. Планка едет вверх (ratchet),
   назад не падает.

**Фактическое состояние (SEC-1 выполнен, 2026-07-10):** оттриаженные сканеры —
**Semgrep, Gitleaks, OSV-Scanner, Trivy fs, Trivy image** — **блокирующие**: их
gate-шаг валит джобу при ЛЮБОМ ненулевом выходе сканера (находка ИЛИ сбой самого
скана — fail-secure: сканер, который не отработал, ничего не сертифицирует).
Артефакты/сентинелы выгружаются до gate, поэтому сводный отчёт собирается всегда.
CodeQL, TruffleHog, zizmor, Scorecard, `dast-zap` (SEC-6, свежедобавленный, ещё без
триажа на реальном рантайме), `trivy-deps` (SEC-11, тот же порядок: сторонние образы
несут CVE, которые чинятся не в этом репо, — блокирующим станет после первого триажа),
`dependency-check` (SEC-15, см. ниже), `kics` (compose/A05 — тот же порядок: сначала
триаж базовой линии, где много артефактов оверлеев, потом блокирующий),
`dependency-review` (атрибуция уязвимости к вносящему PR, `fail-on-severity: high`,
бежит только на `pull_request` — вне его нечего диффать) и джоба `check` — пока
информационные
(`continue-on-error`); блокирующий SCA-проход (OSV-Scanner) бежит и в основном гейте
`ci.yml` — `pnpm audit` из пайплайна убран, npm закрыл его эндпойнты (HTTP 410, 2026-07).

## Второй SCA-движок: зачем NVD, если уже есть OSV и Trivy

NVD и так лежит в основании обоих: база Trivy собирается в том числе из него, а osv.dev
импортирует те же CVE через GHSA. Ценность отдельной джобы `dependency-check` не в
«ещё одном источнике», а в **другом способе сопоставления**: OSV/Trivy опознают
уязвимость по идентичности пакета (запись адвизори привязана к имени в экосистеме),
Dependency-Check матчит CPE из фида. Разный матчинг — разные слепые зоны; это тот же
принцип, по которому рядом живут Semgrep и CodeQL.

Плата известна и принята заранее, а не «обнаружится потом»:

- **CPE шумит на npm** — пакет, чьё имя совпало с продуктом какого-нибудь вендора,
  наследует его CVE. Поэтому джоба информационная до первого триажа (SEC-15), и делать
  её блокирующей раньше нельзя.
- **`pnpm-lock.yaml` она не читает** (её Node-анализаторы знают package.json и
  npm/yarn-локи). Поэтому джоба сперва ставит зависимости и скармливает сканеру живое
  дерево `node_modules`; без этого шага она бы тихо просканировала почти пустоту — ровно
  та форма fail-open, против которой построен весь пайплайн.
- **Фид NVD качается долго**, поэтому каталог базы кэшируется между прогонами и
  обновляется инкрементально; отсюда же и увеличенный таймаут джобы.
- **Нет ключа — нет тихого зелёного.** Без `NVD_API_KEY` джоба не запускает скан и пишет
  сентинел `ok:false`, так что в сводке она помечается «⚠️ НЕ подтверждён».

**Что показал первый живой прогон (2026-07-30, run 30579763480) — две поправки к плану
выше.** Прогон УПАЛ через 40 минут: `Unable to obtain an exclusive lock on the H2
database` + `No documents exist`, exit 13. Причина — контейнер работает не от пользователя
раннера и не мог писать/лочить H2-базу в примонтированном каталоге; лечится запуском от
`uid:gid` раннера (это и есть документированный апстримом вызов). Пустой 185-байтовый кэш,
который тот прогон успел сохранить, — причина, по которой префикс ключа теперь `v2`:
старый префикс вечно восстанавливал бы отравленный пустой каталог.

Отсюда второе: **на push джоба больше не бежит**. Даже падение стоило 40 минут, успешная
первичная синхронизация дешевле не будет, и сканеру такой длительности не место в петле
обратной связи по PR — он живёт на недельном кроне и на ручном запуске, где его время
никому не мешает. На push он **пропускается по дизайну**, и сводка это знает: печатает
«⏭ пропущено (по расписанию/вручную)», а не тревогу «НЕ подтверждён» — та обязана
продолжать означать «скан, который должен был отработать, не отработал». Вернуть на push
можно, если измеренный успешный прогон окажется быстрым.

Долгоиграющая альтернатива, которая тут НЕ сделана: Dependency-Track поверх наших готовых
CycloneDX SBOM — он переоценивает состав уже задеплоенного билда непрерывно, без
пересборки. Требует внешнего инстанса (как DefectDojo в SEC-4), поэтому ждёт своего часа.

## От «сканируем контейнеры» до «сканируем то, что в проде»

Push-триггер сертифицирует **коммит**. Прод — это **работающий образ**, и между ними
две дыры, которые закрыты отдельно от гейта на PR:

1. **Время.** Базы пинены по дайджесту (это правильно), значит деплой месяцами гоняет
   ровно тот образ, что просканирован при мерже, — а ленты CVE едут под ним. Поэтому
   `security.yml` дополнительно ходит по расписанию (`cron '17 5 * * 1'`, SEC-10):
   те же джобы и те же блокирующие гейты по `main` раз в неделю. Новый CVE на пиненную
   базу становится красным прогоном в течение недели, а не «когда кто-нибудь запушит».
   На scheduled-прогоне сводный отчёт остаётся в job summary: PR нет, а коммент к тому
   же головному коммиту каждый понедельник — это шум, а не сигнал.
2. **Артефакт.** Раньше и Render, и VPS **пересобирали** Dockerfile у себя, то есть
   в проде работал образ, которого сканер не видел. `image.yml` (SEC-13) делает цепочку
   `build → trivy (блокирующий) → push в GHCR → cosign sign по ДАЙДЖЕСТУ`, а деплой
   начинается с `deploy/verify-image.sh` (`cosign verify` по identity воркфлоу +
   OIDC-иссуеру GitHub). Находка ⇒ пуша нет; подписи нет ⇒ деплой не стартует.
   Сборка из исходников (`up --build`) остаётся рабочим путём для playtest-хостов —
   она просто не даёт этой гарантии.
3. **Работоспособность.** Все сканеры выше читают файловую систему образа и ни один
   его не запускает. Значит образ, который умирает на старте, проходит блокирующий
   `trivy-image` идеально чисто (уязвимого кода в нём даже меньше) и уезжает в GHCR
   подписанным — подпись удостоверяет нерабочий артефакт. Это не гипотеза: шаг,
   выкидывающий devDependencies из образа, был написан как `pnpm prune --prod`, а
   `prune` в воркспейсе работает по ОДНОМУ проекту и оставляет каждый
   `packages/*/node_modules` пустым — сборка зелёная, контейнер падает на
   `Cannot find module 'ws'` (поймано на PR #502, чинится
   `pnpm install --prod --frozen-lockfile`). Поэтому `.github/scripts/smoke-image.sh`
   поднимает собранный образ и требует ответа от `GET /health` (сервер жив) и `GET /`
   (HTML игрока реально запечён). Он блокирующий в обоих местах: шагом внутри
   `trivy-image` (не даёт смержить) и перед `push` в `image.yml` (не даёт подписать).

**Рантайм-настройки контейнеров в `deploy/docker-compose*.yml`** (привилегии,
capabilities, лимиты) Trivy misconfig действительно не видит: он умеет
Dockerfile/k8s/terraform/cloudformation/helm/ARM, Docker Compose в этот список не входит.
Этот пробел закрыт отдельным движком — джобой `kics` (`checkmarx/kics`, `--type
DockerCompose`), информационной до триажа базовой линии. Две её особенности стоит знать
до того, как в неё полезешь: KICS опознаёт compose только по расширению `.yaml`, поэтому
копии файлов делаются внутри джобы, а пути в SARIF возвращаются к настоящим `deploy/*.yml`;
и она валится, если просканировано меньше файлов, чем скопировано, — пустой отчёт
неотличим от чистого.

**Чего этот слой по-прежнему НЕ покрывает:** того, о чём KICS не спрашивает, и того, что
он спрашивает мимо. Он читает каждый файл ОТДЕЛЬНО и не понимает мерж оверлеев, поэтому
у фрагментов `tls.yml`/`release.yml` штатно «нет healthcheck / cap_drop / security_opt»,
хотя те лежат в базовом файле и сливаются в рантайме. Поэтому чек-лист в
`deploy/README.md` (SEC-12) остаётся вторым слоем, а не рудиментом: при правке сервисов
проходить его руками.

**Запись триажа (baseline, 2026-07-10):** по коду и зависимостям находок — **ноль**.
Gitleaks v8.18.4 (версия из CI) локально по чистому дереву — 0 утечек; `pnpm audit` —
0 уязвимостей; CI-прогоны пиненных образов (Semgrep p/typescript+p/javascript+
p/security-audit, OSV по обоим lock-файлам, Trivy fs vuln+secret+misconfig) —
0 находок, сканы подтверждены сентинелами. Отдельная история — **Trivy image**: гейт
сразу вскрыл, что сборка образа молча падала с бампа node 22→26 (#106, corepack
выпилен из Node ≥25) и образ вообще не сканировался (fail-open). После починки
Dockerfile оживший скан нашёл 12 CVE базовой ОС рантайма (distroless
nodejs22-debian13: libc6 + zlib1g), все **без доступного фикса** и без runtime-пути
в Node-only сервере — приняты как документированный риск в `.trivyignore` (ревью
при бампе digest); прежние bookworm-записи (perl/ncurses) удалены как неприменимые
к distroless. `.semgrepignore` / `.gitleaks.toml` НЕ созданы намеренно: подавлять
нечего, а пустой файл подменил бы дефолтные списки игнора сканеров. Появится ложная
находка — создавай файл по правилам ниже.

**Запись триажа (SEC-14, 2026-07-30) — 71 находка после посадки `trivy-deps`.**
Разбор по полному списку из лога джобы `report` (не по топ-30 из комментария):

- **`postgres:16-alpine` → `/usr/local/bin/gosu`, 34 CVE (в т.ч. один CRITICAL).**
  Все — в Go stdlib v1.24.6 и x/sys, вкомпилированных в gosu. Gosu выполняется ОДИН раз
  на старте контейнера (chown каталога данных → сброс привилегий) и завершается до
  первого соединения с БД: не слушает сокеты, не парсит недоверенный ввод, не ходит в
  сеть, тогда как CVE лежат в net/http, crypto/tls, archive/*, encoding/*. **Принято как
  задокументированный риск** — `.trivyignore-deps.yaml`, ревью при бампе дайджеста (у записей
  есть `expired_at`: просроченное подавление само возвращает находку в отчёт).
- **`caddy:2-alpine` → пакеты образа (curl, libcurl, c-ares), 9 CVE.** Пакеты ОБРАЗА, а
  не зависимости caddy: он статический Go-бинарь и к ним не обращается; достижимы только
  через `docker exec`, то есть уже после компрометации хоста. **Принято** там же.
- **`caddy:2-alpine` → Go-бинарь самого caddy, 10 находок. НЕ ПОДАВЛЕНО — открытый
  риск.** Caddy единственный смотрит в интернет и его HTTP-стек обрабатывает запрос
  злоумышленника напрямую; «наверное, не наш путь» здесь не аргумент. Разобрано
  поимённо в SEC-18 ниже — прежняя формулировка «~10 CVE, ждём пересборки» заменена
  на пофайндинговый разбор, потому что «ждать» оказалось нерабочим планом (там же).
- **CodeQL `js/missing-rate-limiting` ×2 (`authApi.ts`) — подтверждённый false positive**
  (SEC-9): лимит там есть, но кастомный `slidingWindowIpLimiter` не моделируется CodeQL.
  Гасится кнопкой в Security UI — API-токен сессии без scope `security_events`.
- **Semgrep `bypass-tls-verification` (`wsServer.tls.test.ts`) — FP; подавление работало,
  а врал ОТЧЁТ.** Первая версия этой записи обвиняла синтаксис инлайн-директивы — прогон
  её опроверг: находка осталась на месте после правки. Настоящая причина в другом:
  Semgrep не выбрасывает подавленную находку из SARIF, а помечает её полем
  `suppressions` (и выходит с кодом 0 — для гейта её нет), а `summarize-security.mjs`
  это поле не читал и считал её наравне с живыми. Починено в саммарайзере: результаты с
  непустым `suppressions` в таблицы не попадают, но их число печатается отдельной
  строкой — молча прятать подавления тоже нельзя. Заодно: текст правила говорит про
  `NODE_TLS_REJECT_UNAUTHORIZED`, которого в репозитории нет вовсе — сработка на
  `rejectUnauthorized: false` в тесте с самоподписанным localhost-сертификатом.
- **TruffleHog ×2 «Postgres», unverified — FP.** Это строки `postgres://void:void@…` из
  `docker-compose.yml`, `server.env.example` и доков: документированные дев-дефолты, не
  секреты. На публичном пути пароль теперь обязателен (SEC-12, TLS-оверлей), так что
  дефолт живёт только в LAN-сценарии. Файла подавлений для TruffleHog не заводим —
  джоба информационная, а пустой конфиг подменил бы её дефолты.

**Итог, сверенный с прогоном (`0ab5f6e`): 71 → 20 находок**, из них Trivy 66 → 15. Не «до
десяти», как ожидалось, и вот почему: формат `.trivyignore` адресует только по id, без
пути, а пять CVE Go stdlib (`CVE-2026-27145`, `-39822`, `-42504`, `-42505`, `-42507`)
присутствуют И в gosu, И в бинаре caddy. Подавить их «для gosu» значило бы спрятать их
там, где риск настоящий, поэтому они оставлены видимыми — консервативно и осознанно.
Точный инструмент на будущее — `.trivyignore.yaml` с полем путей у записи.

Остаток: 15 Trivy (открытый риск по caddy + пять общих id), 2 CodeQL и 2 TruffleHog — все
четыре FP, ждут гашения в UI. `trivy-deps` останется информационной, пока не пересоберут
caddy: делать блокирующей джобу с открытым риском — значит выключить её первым же красным
прогоном.

**Запись триажа (SEC-18, 2026-08-06) — 10 находок Trivy в бинаре caddy, поимённо.**
SEC-14 разобрал их одной строкой («~10 CVE, открытый риск, ждём пересборки»). Здесь —
каждая по отдельности, и заодно исправлен сам план ожидания, который не работал.

**Дефект механизма, найденный первым.** SEC-14 записал: «еженедельный крон (SEC-10)
покажет пересборку». Показать он не может **по построению**: `trivy-deps` читает ссылки
из `deploy/docker-compose*.yml`, а они пинены по ДАЙДЖЕСТУ (`caddy:2-alpine@sha256:5f5c…`).
Trivy тянет образ по дайджесту, то есть один и тот же замороженный слепок — апстрим
пересоберёт хоть десять раз, отчёт не изменится ни на строку. Пассивное «подождём» здесь
означало «не узнаем никогда». Закрыто шагом «пин против тега» в джобе `trivy-deps`: он
спрашивает у реестра, на что ТЕГ указывает сейчас, и предупреждает, когда пин устарел.
Проверено обоими исходами — на реальных пинах молчит, на подделанном печатает
`::warning::` с обоими дайджестами.

**Состояние апстрима на дату записи (проверено запросом к реестру, не по памяти):**
`caddy:2-alpine` = `alpine` = `2.11-alpine` = запиненный `sha256:5f5c8640…` — то есть
пин УЖЕ самый свежий caddy-alpine (2.11.4), пересборки с фиксами не существует.
`postgres:16-alpine` — так же актуален. Бампом дайджеста сегодня не чинится ничего.

Разбор — по одному агенту на находку, каждый вердикт «недостижимо» отдельно проверялся
на опровержение; ни один опровергнут не был. Достижимость считается по НАШЕМУ
`deploy/Caddyfile` (ровно `encode zstd gzip` + `reverse_proxy server:8788`).

_Достижимо — 3:_

| id | пакет | что это | почему достижимо у нас |
|---|---|---|---|
| `CVE-2026-56852` HIGH | x/text 0.37.0 | бесконечный цикл в `unicode/norm` на битом UTF-8 | цепочка `certmagic → x/net/idna → norm`: на каждом хендшейке с незнакомым SNI `getNameFromClientHello` зовёт `idna.Lookup.ToASCII(hello.ServerName)`, а SNI полностью управляем атакующим. Путь висит на самой терминации TLS — общий для HTTP/1.1, HTTP/2 и HTTP/3 |
| `CVE-2026-27145` HIGH | Go stdlib 1.26.3 | квадратичная сложность `x509.VerifyHostname` при большом списке DNS SAN | путь не клиентский, а ACME: Caddy сам ходит к Let's Encrypt и проверяет цепочки. Потолок — срыв автопродления сертификата, требует позиции на маршруте к ACME/OCSP |
| `CVE-2026-42507` MEDIUM | Go stdlib 1.26.3 | `net/textproto` кладёт сырой ввод в текст ошибки | битая строка заголовка HTTP/1.1 от анонимного клиента → его байты в логе Caddy. Инъекция в логи (вплоть до ANSI-escape в `docker logs`), не DoS и не утечка |

_Недостижимо — 7, с конкретной причиной у каждой (не «чужое, значит не наше»):_

- `GHSA-hrxh-6v49-42gf` HIGH (grpc 1.81.0) — три дефекта: обход xDS RBAC, паника RBAC,
  обход митигации HTTP/2 Rapid Reset. grpc в бинаре — транзитивная зависимость OTLP-
  экспортёров, то есть КЛИЕНТ телеметрии; gRPC-сервера Caddy не поднимает, а флуд
  RST_STREAM из интернета попадает в `x/net/http2`, у которого свой код и свои CVE.
  Пакет `internal/xds/rbac` в графе модулей отсутствует, символов в бинаре — ноль.
- `CVE-2026-39822` HIGH (stdlib `os`) — обход песочницы `os.Root` по симлинку.
  `os.Root` в исходниках Caddy не используется вовсе.
- `CVE-2026-42504` HIGH (stdlib `mime`) — квадратичный разбор в `WordDecoder.DecodeHeader`.
  Уязвим ровно один символ; Caddy зовёт `ParseMediaType`, а `DecodeHeader` — MIME-почтовый
  путь, которого в HTTP-стеке нет.
- `GHSA-gcjh-h69q-9w9g` MEDIUM (cel-go 0.28.1) — утечка приватных полей `json:"-"` через
  `ext.NativeTypes`. Уязвимы только функции `ext/native.go`; в бинаре их нет, а CEL-
  матчеров (`expression`) в нашем Caddyfile нет тем более.
- `CVE-2026-42505` MEDIUM (stdlib `crypto/tls`) — PSK-идентификаторы утекают во внешний
  ClientHello при ECH. Затронут TLS-КЛИЕНТ с включённым ECH; наш ECH не настроен, а
  клиентский путь (ACME) к Let's Encrypt его не использует.
- `GO-2026-5932` UNKNOWN (x/crypto 0.52.0) — не баг, а объявление `openpgp` небезопасным
  by design; фикса нет и не будет. Уязвим только подпакет `openpgp`, в бинарь не слинкован.
- `CVE-2026-46600` UNKNOWN (x/net 0.55.0) — паника на битой SVCB/HTTPS DNS-записи в
  `dns/dnsmessage`. Пакет в бинарь не слинкован (символов `golang.org/x/net/dns/dnsmessage`
  — 0; вендоренная копия stdlib SVCB не разбирает вовсе). DNS-01 у нас не используется,
  а certmagic для DNS ходит через `miekg/dns` — другой парсер.

**Что принято.** Три достижимые находки остаются ОТКРЫТЫМ РИСКОМ и не подавляются:
конфигурацией ни одна не снимается (отключение HTTP/3 не помогает — все три висят либо
на терминации TLS, либо на ACME, либо на разборе HTTP/1.1), а пересборки образа с фиксами
не существует. Семь недостижимых тоже НЕ подавляются: `.trivyignore-deps.yaml` — список
для «недостижимо И надолго», а тут любая из них закроется тем же бампом дайджеста, что и
достижимые, и подавление пришлось бы снимать в тот же день. Разбор зафиксирован здесь;
сигналом к действию служит шаг «пин против тега», а не память.

**Ускоренный выход, если ждать надоест:** у сервера есть НАТИВНЫЙ TLS
(`TLS_KEY_FILE`/`TLS_CERT_FILE`, RS-5.1) — публичный путь можно поднять вообще без caddy,
и тогда все десять находок исчезают вместе с сервисом.

## Триаж и подавление ложных (важный навык)

- **Severity-порог:** начинай с HIGH/CRITICAL, шум среднего/низкого — позже.
- **Semgrep:** инлайн `// nosemgrep: rule-id` с обоснованием, или `.semgrepignore`.
- **Gitleaks:** `.gitleaks.toml` (allowlist по regex/пути/коммиту) для тестовых
  фикстур и заведомо публичных значений.
- **Trivy:** `.trivyignore` (по CVE-id) с датой ревью и причиной.
- **osv-scanner:** конфиг с `[[IgnoredVulns]]` + срок.
- Правило: **каждое подавление — с комментарием «почему» и датой**. Подавление без
  обоснования = технический долг безопасности.
- SARIF-артефакты у всех джоб → открываются в любом SARIF-вьюере; льются в GitHub Code
  Scanning (`Security → Code scanning alerts`, SEC-4 ✅) — залить ещё и в DefectDojo
  можно отдельным кирпичом, когда появится инстанс/API-ключ. Слово «безусловно» отсюда
  убрано по факту: у `trivy-deps` загрузка молча падала (SEC-19) — джоба пишет по SARIF
  на образ и грузила КАТАЛОГ под одной категорией, а CodeQL Action с 2025-07-21 такое
  отвергает. Шаг под `continue-on-error`, поэтому гейт был зелёный, а находки в панель
  не приезжали. Починено слиянием в один `run` до загрузки; на будущее общее правило:
  **одна категория = один `run`**, каталог из нескольких SARIF грузить нельзя.

## Что сознательно НЕ делаем и почему (анти-цели, сверено 2026-07-31)

Индустрия предлагает длинный список практик supply-chain. Ниже — те, что разобраны и
отклонены **осознанно**, чтобы через полгода не искать заново, почему их нет. Правило
одно: практика должна закрывать угрозу, реальную для инди-команды с одним VPS и Render,
а не для организации с кластером и командой безопасности.

| Практика | Вердикт | Почему |
| --- | --- | --- |
| **Admission control** (Kyverno, Connaisseur, policy-controller) | заменено эквивалентом | Это политика на входе в кластер, а Kubernetes у нас нет. Роль «не пустить неподписанное» играет `moongame update`: `verify-image.sh` до рестарта, отказ ⇒ сервер не тронут |
| **SLSA L3** | нет | Требует изолированного билдера, недоступного для сборки ключа и герметичных входов. Мы на L2-уровне: hosted-билдер + подпись + provenance-аттестация. Прыжок на L3 стоит перестройки всей сборки ради угрозы «скомпрометирован сам GitHub-раннер» |
| **Reproducible / hermetic builds** | нет | Дорого (пин всех входов вплоть до таймстемпов), а даёт в основном возможность независимой перепроверки третьей стороной. Для проекта без внешних аудиторов ценность околонулевая |
| **GitOps (Argo CD / Flux), канареечный выкат, quarantine-реестры, promotion dev→staging→prod** | нет | Всё это решает проблемы масштаба, которого нет: одно окружение, один хост, один оператор. Из этого набора взято единственное дешёвое зерно — **откат** в `moongame update` |
| **Vault / cloud KMS** | нет, но есть дешёвая форма | Отдельный секрет-стор для одного VPS — инфраструктура ради инфраструктуры. Дешёвый аналог, который стоит сделать: docker file-secrets вместо env-переменных (env видно в `docker inspect` и в дампе процесса) |
| **Dependency-Track + VEX** | ждёт инстанса | Единственная практика из списка, которую хочется по-настоящему: непрерывная переоценка уже задеплоенного SBOM без пересборки. Блокер тот же, что у DefectDojo в SEC-4 — нужен внешний инстанс. До него роль играет недельный крон |
| **npm provenance / trusted publishing** | неприменимо | Мы не публикуем пакеты в npm; наши артефакты — образ и APK, и у обоих provenance уже есть |
| **seccomp / AppArmor профили** | нет | Docker и так применяет дефолтный seccomp-профиль. Свой профиль требует трассировки сисколлов и ломается при каждом обновлении Node — цена выше пользы на нашем периметре |
| **Ограничение egress** | не выражается в compose | Самая недооценённая мера (превращает «зловред в зависимости» из кражи данных в неудачу), но реализуется на уровне firewall хоста, а не compose-файла. Кандидат в рунбук, не в код |
| **`read_only: true` для контейнера сервера** | препятствие СНЯТО, шаг остался | Блокировала не безопасность, а транспиляция в `/app` на каждом старте. Бандл теперь печётся при сборке образа, рантайм запускает готовый файл — стартовая запись в `/app` исчезла. Остался единственный писатель, `playtest-logs/`, и он уже на именованном томе. То есть `read_only: true` + `tmpfs` под временные файлы стал реалистичным следующим шагом, а не архитектурным тупиком |

## Безопасность самого пайплайна (часто забывают)

CI — это привилегированная среда исполнения и **сама поверхность атаки**:

- **Least privilege:** `permissions: {}` на уровне воркфлоу, каждая джоба объявляет
  только своё (`contents: read`, `security-events: write` там, где заливается SARIF).
  Работаем `GITHUB_TOKEN`'ом, который ротируется сам, а не долгоживущим PAT; секреты
  берутся только через `${{ secrets.NAME }}` (маскируются в логах автоматически).
- **OIDC вместо долгоживущих секретов**: подпись APK и образа — keyless cosign, без
  приватного ключа в хранилище секретов вообще.
- **Protected branches:** в `main` только через PR + зелёный пайплайн + ревью, слияние —
  через merge queue (см. `CONTRIBUTING.md`).
- **Не эхай секреты** в логи; артефакты со сканов не должны утаскивать исходники.
  `persist-credentials: false` на каждом checkout — токен не остаётся в `.git/config`.
- **Пинуй версии**: экшены по SHA коммита, образы по `sha256`-дайджесту. Чужой экшен в
  пайплайне = чужой код с твоими правами; `harden-runner` в audit-режиме показывает,
  куда этот код ходит.

## Запуск

Пайплайн стартует автоматически: push в любую ветку, `pull_request` (ради форков —
пуш в форк происходит в чужом репозитории и сюда не долетает), `merge_group` (иначе
очередь не увидит required-чеков и вышибет PR по таймауту), еженедельный крон
`'17 5 * * 1'` (прод крутит пиненный образ дольше, чем живут ленты CVE) и
`workflow_dispatch` вручную. Локально те же сканеры:

```bash
docker run --rm -v "$PWD:/src" semgrep/semgrep semgrep scan --config=p/security-audit /src
docker run --rm -v "$PWD:/src" zricethezav/gitleaks detect --source=/src --redact
docker run --rm -v "$PWD:/src" ghcr.io/google/osv-scanner --lockfile=/src/pnpm-lock.yaml
docker run --rm -v "$PWD:/src" aquasec/trivy fs --scanners vuln,secret,misconfig /src
docker run --rm -v "$PWD:/src" anchore/syft /src -o cyclonedx-json
```
